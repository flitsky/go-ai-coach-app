# 리그·승급 모드 리서치 — 급 구간(18급~1급)·단 구간(1단~9단)과 KataGo Human SL (최종본)

작성: 2026-09-28 · 아이디어 **I-1**(🔍 조사) · 가리키는 곳: `work/roadmap/260928-_APP_EVOLUTION_IDEAS.md`
v1 초안에 비평을 반영한 개정본이다. 비평이 다툰 사실은 2026-09-28에 다시 확인했다.

## 요약 (10줄)

1. **만들 수 있을 가능성이 높다. 엔진은 바꾸지 않아도 된다.** 앱의 KataGo 1.16.4는 `-human-model` 인자 하나로 Human SL 모델(`b18c384nbt-humanv0`, 99MB)을 붙이고, `rank_20k`~`rank_9d` 프로필을 요청마다 바꿀 수 있다. 모델은 상업적으로 써도 되지만 저작권 고지를 넣어야 한다.
2. **제안**: 리그를 JSON 분석 경로·별도 카탈로그·별도 저장소에 붙이면 5 캐릭터의 GTP 경로와 카탈로그는 그대로 둘 수 있다. 확정은 회귀 확인(§5.9)을 통과한 뒤다. 이어하기 슬롯이 하나뿐이어서 저장 쪽은 결정이 필요하다(§5.3.4).
3. **모델의 급/단은 KGS 척도다.** 한국 인터넷 서버(타이젬·야호)의 18급~9단은 대략 KGS 16급~5단(±1급)에 해당한다. 그래서 앱에는 "앱 기력"으로 적고, 실제로 재서 맞춘다.
4. **앱과 같은 주 모델로 사람과 둔 실측은 OGS의 go-bot 봇 다섯 개뿐이다.** 40방문에, 확률 1% 미만 꼬리만 온도로 누른 설정이다. 19x19 결과: rank_5k는 이름값을 한다. rank_1d는 KGS 1~2급, rank_5d는 KGS 1단 정도다. rank_9d의 원시 세기는 아무도 재지 않았다.
5. **양 끝이 위험하다.** ① 19x19에서 가장 약한 rank_20k도 KGS 14급 정도라, 18~16급 단계는 원시 프로필로 만들 수 없다. ② 13x13에서는 5k~5d 프로필이 OGS 1급 근처로 뭉친다. 그래서 단 리그가 갈리지 않을 수 있다. ③ 4단 이상은 탐색이나 정책 섞기가 필요한데, 섞기는 아직 재지 않은 가설이다.
6. **용량**: 리그를 여는 사용자만 99MB를 한 번 받는다. 리그 전용 PAD 주문형 팩이고, #57(주 모델 이전)과는 별개인 새 항목이다. 기기에는 +99~107MB가 쌓인다. **메모리**: 지금 구조에서는 신경망 3개가 동시에 올라가는 것이 기본이다. 실제 메모리 사용량(RSS)은 아무도 재지 않았다.
7. **속도는 신뢰도 낮은 추정뿐이다.** 급 한 수는 S22U에서 0.25~1초 이상이다. JSON 요청의 고정비는 아직 모른다. 중급폰에서는 0.5~2초다. 40방문 λ 탐색을 쓰는 단 리그는 중급폰에서 10초 상한을 넘길 수 있다.
8. **초안의 승급 규칙은 칭호를 부풀린다.** 초안 규칙은 최근 5판 중 3승, 강등 없음, 재도전 무제한이다. 시뮬레이션으로는 100~300판 뒤 칭호가 실력보다 4~6급 높다. "현재 기력(내려갈 수 있음)"과 "최고 칭호(내려가지 않음)"를 나누는 식의 대책을 골라야 한다(§5.3).
9. **먼저 할 일: P0 데스크톱 보정.** 사람 모델 99MB를 맥에 받으려면 승인이 필요하다. 2~3스레드, 맥 연산 반나절~2일(DERIVED)이다. 다음은 **P1 기기 측정**이다. 저사양 arm64 폰이 필요하다. 이와 별도로 **라이선스·고지 화면**은 지금도 빠져 있는 선행 과제다.
10. **P0/P1 숫자가 나오기 전에는 UI·저장소·PAD에 손대지 않는다.** 1차 출시 범위(급 몇 단계, 단 어디까지, 어느 판 크기)는 P0 결과를 보고 정한다(§9).

## 0. 결론과 권고

**한 줄 결론**
- 만들 수 있을 가능성이 높다. 엔진은 그대로 두고 모델 파일 하나를 더한다.
- 급 리그는 사람 모델을 수당 1~2회만 평가하면 된다.
  - **수당 CPU**는 지금 캐릭터(16방문)보다 적을 것으로 본다. 다만 이것은 DERIVED이고 측정한 값이 아니며, JSON 요청의 고정비를 모른다(§2.2).
  - **메모리는 더 무겁다.** 신경망이 지금은 1~2개인데 3개가 된다.
- 양 끝과 윗단은 불확실하다. **데스크톱 실험(P0)으로 먼저 판가름한다.**
  - 19x19의 18~16급
  - 13x13의 단 리그
  - 4단 이상

**핵심 사실** (근거는 본문에 있다)
- ✅ **엔진은 바꾸지 않아도 된다.**
  - 앱이 쓰는 KataGo 1.16.4가 Human SL을 지원한다.
  - 사람 모델은 실행 인자 하나(`-human-model`)로 붙는다.
  - 급·단 프로필은 **요청마다** 바꿀 수 있고, 프로세스를 다시 띄울 필요가 없다(§3.4).
- ✅ **모델 파일 하나에 모든 프로필 이름이 있다.**
  - `b18c384nbt-humanv0`(99MB) 하나가 `rank_20k`부터 `rank_9d`까지 받는다.
  - ⚠️ **이름이 다 있다는 뜻이지, 세기가 다 나온다는 뜻은 아니다**(§3.5).
- DERIVED: 구조(b18c384nbt)가 주 모델과 같으니 **평가 1회 비용도 같을 것**이다. 구조에서 끌어낸 추정일 뿐 측정은 아니다(§3.6).
- ⚠️ **모델의 급/단은 KGS 척도다.**
  - 코드가 모든 `rank_` 프로필을 KGS 출처로 만든다.
  - 한국 인터넷 서버(타이젬·야호)는 단 구간에서 KGS보다 2~4단 후하다.
  - 그래서 "모델 1단 = 앱 1단"으로 이으면 안 된다. 앱에는 **"앱 기력"**으로 표기하고, 실제로 재서 맞춘다.
  - DERIVED: 한국 인터넷 기준 18급~9단은 대략 **KGS 16급~5단(이상), ±1급**에 해당한다(§3.3).
- ⚠️ **탐색 없는 사람 모델의 세기는 이만큼만 쟀다.** 조건은 19x19, go-bot의 40방문 5k식 설정이다(§3.5).
  - rank_1d ≈ KGS 1~2급, rank_5d ≈ KGS 1단
  - **rank_9d의 원시 세기는 잰 적이 없다.**
  - 탐색 없는 천장은 **KGS 1단~5단 사이 어딘가**다. 탐색 없는 사람 모방 망이 역사적으로 KGS 4~5단 근처까지 갔다는 저자 발언이 있다 [S20].
- ⚠️ **아래쪽 한계**
  - 15급 이하 프로필끼리는 봇끼리 뒀을 때 세기 차이가 작다 [S18].
  - 19x19에서 가장 약한 rank_20k는 KGS 14급 정도(≈ 타이젬 15~16급)다. 그래서 **19x19의 1단계(18~16급)는 원시 프로필로 만들 수 없다.** 온도를 1 넘게 올리는 식의 추가 약화가 필요하다(§5.1).
- ⚠️ **판 크기마다 모양이 다르다.** OGS가 판 크기별로 따로 매긴 레이팅이다. 잡음이 크다(§3.5).
  - 13x13에서는 약한 쪽이 더 벌어진다. rank_20k가 OGS 26급이다.
  - 대신 5k~5d가 **OGS 1급 근처로 뭉친다.**
  - 그래서 13x13은 급 리그 아랫단은 오히려 잘 갈릴 수 있지만, **단 리그는 갈리지 않을 위험**이 있다.
- ⚠️ **사람과 둔 판으로 보정된 레시피는 go-bot의 것 하나뿐이다.**
  - 설정: 40방문, 사람 정책 100%, 패스는 KataGo가 판단, 확률 1% 미만 수에만 온도 0.85→0.70, 대칭 2개 [S43].
  - 문서가 권하는 "1방문 + 전체 온도 추출"은 사람과 둔 보정 자료가 없다.
  - 순수 추출일 **수도 있는** djma 봇들은 이름보다 2~4급 약했다.
  - **제안**: 앱 기본 레시피에 **"1% 미만 꼬리 누르기"**를 넣고, P0에서 두 변형을 모두 잰다(§3.4, §6.2).
- **급 리그 비용** (DERIVED, **신뢰도 낮음**)
  - S22U: 한 수에 신경망 평가 1~2회, 0.25~1초 이상
  - 중급폰: 0.5~2초
  - 바탕이 된 폰 벤치마크에 이상치가 있다: 방문 수가 늘어도 시간이 늘지 않은 구간이 있고, 표본은 3개다(§2.2).
- **단 리그 윗단을 메우는 후보는 두 가지다.**
  - (가설, 싼 쪽) **1방문 정책 섞기**: 사람 정책과 주 모델 정책을 섞는다. **효과는 모른다.** 앱의 b18 원시 정책이 얼마나 센지는 P0에서 처음 잰다.
    - KataGo 망을 1 playout으로 둔 OGS 봇 둘이 OGS 5.5~6.6단이었다. 하지만 하나는 b60 망이고, 다른 하나는 망이 밝혀져 있지 않다 [S22].
  - (검증된 레시피, 비싼 쪽) **λ 탐색 40방문 이상**: S22U 4스레드에서 약 3초(DERIVED, 신뢰도 낮음)다. 중급폰에서는 6~20초라 10초 상한을 넘길 수 있다(§3.6).
- ⚠️ **과제 전제의 "기본 모듈 150MB"는 옛 값이다.**
  - 지금 한도는 기본 모듈 500MB, 에셋 팩 하나당 1.5GB다 [S39].
  - 사람 모델은 **리그 전용 주문형 팩 하나**로 내려보낸다. 주 모델을 옮기는 #57과는 별개인 새 항목이다(§7).
  - 99MB는 Play의 "200MB 초과 시 동의" 선 아래다. 그래서 **모바일 데이터에서도 묻지 않고 바로 받는다.** 앱이 "약 100MB, Wi-Fi 권장" 안내를 직접 띄워야 한다.
- ⚠️ **메모리: 신경망 3개가 기본이다. 최악의 경우가 아니다.**
  - `analyze()`는 JSON 요청 전에 GTP 프로세스를 먼저 띄운다(`KataGoProcessEngineAdapter.kt:164-165`).
  - 그래서 GTP에 1개, 리그 분석 프로세스에 2개(주 + 사람)가 올라간다. 가중치만 약 320MB다(DERIVED).
  - 여기에 NN 캐시(`nnCacheSizePowerOfTwo=20`)와 배치 버퍼(`nnMaxBatchSize=96`)가 더해진다.
  - 아무도 재지 않았다(§3.6, §8).
- **제안: 5 캐릭터를 그대로 두는 조건은 지킬 수 있다.**
  - 방법: 선택지 A + 리그 전용 카탈로그 + 리그 전용 저장소
  - 조건: §5.9 회귀 확인(JSON 분석 기능 포함)을 통과할 것
  - 저장: 이어하기 슬롯이 하나뿐이다. 리그 판을 이어하기에 실으려면 `SavedGameSnapshot`에 선택 필드를 더하거나, 리그 전용 슬롯을 만들어야 한다(§5.3.4).
- ⚠️ **이미 있는 공백: 앱에 오픈소스 라이선스·고지 화면이 없다.**
  - 지금 들어 있는 KataGo와 주 모델의 고지도 들어갈 곳이 없다.
  - 네트워크 라이선스는 사본에 고지를 요구한다 [S19].
  - 그래서 리그 이전의 **선행 과제**로 둔다(§3.1, §9).
- ⚠️ **초안의 승급 규칙은 칭호를 실력보다 4~6급 부풀린다**(시뮬레이션). 대책 표는 §5.3.3에 있다.

**권고 — 먼저 할 일 (PoC 범위)**
1. **P0 데스크톱 보정.** 앱 코드는 바꾸지 않고 스크립트만 쓴다.
   - 준비물: 사람 모델 99MB를 맥에 받는 **명시적 승인**. 맥의 Homebrew KataGo 1.16.4와 주 모델은 이미 있다.
   - 13x13과 19x19에서 다음을 잰다.
     - 3급 차이가 나는 단계끼리 승률이 실제로 갈리는지
     - 레시피 세 가지의 차이: go-bot식, 앱용 싼 변형, 문서식(§6.2)
     - 19x19 18~16급을 만들 약화 손잡이
     - 단 리그 윗단을 "정책 섞기"로 메울 수 있는지
     - 5 캐릭터가 급/단 척도의 어디쯤인지(처음 재는 것이다)
2. **P1 기기 측정.** S22U와 저사양 arm64 폰 한 대에서 다음을 잰다.
   - 신경망 1·2·3개를 올렸을 때의 RSS(캐시·배치 상한을 바꿔 가며)
   - 사람 모델 로드 시간
   - 1방문 질의의 지연
3. **이 두 결과가 나오기 전에는 UI·저장소·PAD에 손대지 않는다.** 1차 출시 범위는 P0 결과를 보고 정한다(§9).
4. **리그와 별개로 지금 해도 되는 선행 과제**: 라이선스·고지 화면.

### 0.1 자주 물을 질문 (FAQ)

**Q. 용량이 얼마나 늘어나나?**
- 리그를 여는 사용자만 **한 번 99,066,230 B(94.5 MiB)**를 받는다.
- 기기에는 약 **+99~107MB**가 쌓인다. AGP가 `.gz`를 풀어 담는지에 따라 달라진다(§7).
- 설치 때 받는 크기는 **109MB 그대로다**(주문형 팩). AAB 파일 자체는 팩을 담으니 커진다.
- 설치 시 동봉으로 바꾸면 지금 주 모델처럼 APK 안 사본과 `filesDir` 사본이 생긴다. 그러면 **모든 사용자**에게 약 +200MB다.
- 받고 푸는 동안 임시로 필요한 공간은 **UNVERIFIED**다. 그래서 팩을 요청하기 전에 빈 공간을 확인한다.

**Q. 중급폰에서 AI가 한 수 두는 데 얼마나 걸리나?**
- 잰 적이 없다. 기기 간 공개 비교 자료는 BadukAI의 KataGo 20b 노드/초 표뿐이다 [S27].
  - 백엔드가 적혀 있지 않다. 가속 백엔드일 가능성이 높으니 **대용 지표로만** 쓴다.

  | 칩 | 노드/초 |
  | --- | ---: |
  | Snapdragon 8+ Gen 1 | 580 |
  | Snapdragon 888 | 330 |
  | Dimensity 8100 | 240 |
  | Snapdragon 778 | 120 |
  | Snapdragon 768 | 80 |
  | Snapdragon 855+ | 55 |

- 이 표로 보면 중급(SD7xx)은 8 계열보다 약 5~7배 느리다. Dimensity 8100은 약 2.4배다.
  - 다만 우리 앱은 CPU(Eigen)로 돈다. CPU끼리의 격차는 이보다 작을 수 있다(UNVERIFIED).
- 우리 측정 기기 SM-S908N은 한국판 S22 Ultra, Snapdragon 8 Gen 1이다(2차 사양 사이트 [S44]).

### 2.2 폰 속도 (SM-S908N = Galaxy S22 Ultra, Snapdragon 8 Gen 1 [S44], Eigen)

근거는 `docs/engine/measurements/engine-benchmark/search-mode-phone-20260613/summary.md`다.
- 조건: 9x9, 3수 둔 시작 국면, 방문 수마다 표본 3개, 시간 상한 10초

| 경로 | 방문 수 | 평균 시간 | 루트 방문(평균) |
| --- | --- | --- | --- |
| GTP 1스레드 | 16 / 32 / 64 | 3.8 / 7.6 / 10.2초 | 15 / 31 / **47**(상한 10초에 잘림) |
| JSON 4스레드 | 16 / 32 / 64 | **4.8** / 3.1 / 5.0초 | 17 / 35 / 67 |

**⚠️ 이 숫자를 믿기 어려운 이유**
- JSON 시간이 방문 수를 따라 오르지 않는다. 16방문(4.76초)이 32방문(3.07초)보다 느렸다. 표본이 3개뿐이라 원인을 가를 수 없다.
- GTP 64방문은 10초 상한에 잘려서 루트 방문이 47개에 그쳤다.
- 그래서 **"방문당 약 0.075초(JSON 4스레드)"를 1방문 질의로 줄여 쓸 수 없다.**
  - DERIVED: 32·64방문 두 점만으로 직선을 그으면 요청당 고정비가 약 1.2초 나온다. 표본 3개짜리 두 점이다.
  - 그렇다면 1방문 질의가 0.25초가 아니라 **1초대**일 수도 있다.
- GTP 쪽 방문당 약 0.24초는 16·32방문에서 일정해서 비교적 믿을 만하다.
- ⇒ 이 문서의 급 리그 수당 시간(0.25~1초)은 모두 **신뢰도 낮음**이다. P1에서 1방문 질의를 직접 잰다.

**판 크기**
- 측정은 9x9 판에서 했다(`scripts/run-katago-search-mode-benchmark.py:150, 226`).
- 그런데 Eigen 백엔드는 실제 판 크기가 아니라 **NN 버퍼 크기(기본 19x19)**로 합성곱을 돈다. v1.16.4의 `eigenbackend.cpp`는 타일 수를 `nnXLen`으로 계산한다 [S11].
- 그래서 이 숫자를 13x13·19x19에도 그대로 쓴다(DERIVED). P1에서 확인한다.
- 반대로, 판 크기를 하나로 고정한 리그 전용 프로세스라면 버퍼를 13으로 줄일 수 있다.
  - 그러면 평가당 비용을 최대 약 2배 줄일 여지가 있다.
  - upstream cfg 주석은 "성능이 좋아진다"고만 한다. 얼마나 좋아지는지는 UNVERIFIED [S8].

### 2.3 5 캐릭터가 세기를 내는 방식

**로스터**
- 정의: `shared/src/commonMain/kotlin/com/worksoc/goaicoach/application/botcharacter/BotCharacterCatalog.kt:42-71`
- ID는 `fast_beginner_$tier`다(:143). 세이브 스키마의 일부라서 바꿀 수 없다(`BotCharacter.kt:7-12`).
- 해금 방식
  - 판다: 무료
  - 돌뫼: 광고 조각 5개
  - 반상: 출석 7일
  - 꼬북: 광고 조각 10개
  - 천원: 출석 28일(:132)
  - 구독하면 다섯 모두 열린다(`BotCollectionState.kt:79-82`).

**엔진 예산**
- 16방문, 후보 8개, Lite 프리셋(`shared/src/commonMain/kotlin/com/worksoc/goaicoach/shared/policy/PlayLevel.kt:21-30`).

**착수 방식**
- 엔진이 준 후보를 세 버킷으로 나눈다: 최적(0번), 중간(1..N-2번), 최하(N-1번).
- 단계마다 정해진 비율로 버킷을 골라 둔다(`PlayLevel.kt:77-109, 283-297`). 어느 버킷을 쓸지는 상태를 저장하지 않고 매번 계산한다(:310-326).

| 단계 | 이름 | 최하 | 중간 | 최적 |
| --- | --- | --- | --- | --- |
| 1 | 초보 | 100% | – | – |
| 2 | 하수 | 60% | 40% | – |
| 3 | 중수 | 20% | 60% | 20% |
| 4 | 고수 | 10% | 30% | 60% |
| 5 | 초고수 | 후보를 1개만 요청해 그 수를 둔다(`shared/src/commonMain/kotlin/com/worksoc/goaicoach/match/AiMoveSelectionPolicy.kt:32`) | | |

- 패스: KataGo가 패스를 1위로 두면 따른다(`AiMoveSelectionPolicy.kt:53-68`).
- 고르기에 실패하면 GTP `genmove`로 넘어간다(`shared/src/commonMain/kotlin/com/worksoc/goaicoach/match/MatchTurnOrchestration.kt:76, 126`).

**⚠️ 급/단 절대 기력은 어디에도 없다.**
- 1단계(초보)조차 "일반 중급자를 상회한다"는 사용자 판단이 코드 주석에 남아 있다(`app-android/src/main/java/com/worksoc/goaicoach/ui/l10n/UiStringsBotCharacters.kt:74-78`).
- 유일한 세기 자료는 상대 비교 매트릭스 하나다. 그마저 9x9, 맥, 옛 3단계 체계에서 잰 것이다(`docs/engine/ENGINE_STRENGTH_RESEARCH.md` §2 「1차 150판 매트릭스 결과」).

**숨겨 둔 티어**
- 초급(7단계)·중급(5단계)·고급(5단계)은 코드에 살아 있다.
- 셋 다 주 모델 후보의 백분위 구간에서 고른다(`PlayLevel.kt:110-130`).
  - 예: 초급 1단계는 32방문 후보 16개 가운데 하위 30% 구간(`PercentileRange(70,100)`)에서 고른다. 대략 16개 중 12~16번째 후보다.
  - 이것은 16방문 후보 8개 중 8번째를 두는 초보보다 **약할 수도 있다.**
- "대국장" 로드맵에서 쓸 자리로 남겨 둔 것이다(`docs/spec/FAST_BEGINNER_TIER_DESIGN.md:184`, 백로그 `work/roadmap/261001-_REFACTORING_BACKLOG.md` #56 카드와 「사용자 결정 대기」 표의 #56 행).
- ⚠️ **보정된 적이 없다.** 18급에 닿는다는 근거도 없고, 순위가 낮은 후보를 고르는 방식은 부자연스러운 실수를 만든다. 사람 모델이 준비되기 전에 쓰는 "보정 안 된 임시 상대" 정도로만 쓸 수 있다.

    - 탐색을 붙이면 보통 프로필보다 세진다.
    - 승률·점수의 왜곡이 더 크다. 원인은 치석 편향, 기권, 틸트, 샌드배거, AI 부정 대국이 섞인 학습 데이터다.

- `includePolicy:true`를 주면 다음이 온다 [S4].
  - `humanPolicy`: 길이가 판 칸 수+1인 배열. 마지막 칸이 패스다.
  - 후보마다 `humanPrior`
  - 루트에 `humanWinrate`, `humanScoreMean` 등
- `query_models`의 `usesHumanSLProfile`로 사람 모델이 올라와 있는지 알 수 있다 [S4].

**GTP 원시 출력**

- ⚠️ v1.16.4의 GTP `kata-analyze`/`kata-search_analyze` 텍스트 출력에는 `humanPrior`가 없다 [S11]. 그래서 지금 5 캐릭터가 쓰는 경로로는 사람 정책을 볼 수 없다.

**레시피는 둘이다. 문서가 권하는 것과, 사람을 상대로 실제로 보정된 것이 다르다.**

| | 문서 권장 [S4] | go-bot(OGS에서 사람과 둠) [S43] |
| --- | --- | --- |
| 방문 | 1 | 40(패스·기권 판단용, 5k 예제와 같음) |

- **제안(앱 기본 레시피)**
  - 1방문 JSON 질의로 `humanPolicy`를 받는다.
  - 앱이 **go-bot식 꼬리 누르기**(1% 미만 수에만 온도 0.85→0.70)로 추출한다.

**설정 키** (기본값은 키를 안 적었을 때의 값) [S11]

| 키 | 기본값 | 하는 일 |
| --- | --- | --- |
| `humanSLProfile` | – | 흉내 낼 기력·스타일 |
| `humanSLChosenMoveProp` | 0 | 최종 착수를 사람 정책에 얼마나 맡길지. 온도보다 먼저 적용 |

**탐색 결과 활용** — lightvector, issue #1030 [S13]
- 방문을 1보다 많이 줘도 `policy`는 원시 망 출력 그대로다. 거기서 뽑으면 탐색이 낭비된다.
- 그가 제안하는 방법: 탐색한 수들 가운데 policy·exp(A·점수 + B·승률)에 비례해 고른다.
- 사람 망의 가치·점수는 사람답지 않다고도 경고한다.

**KaTrain "Human-like" AI** [S26]
- 프로필(기본 preaz_8k), max_visits 500, `ignorePreRootHistory=false`.
- humanPolicy에서 전체 온도로 한 수를 뽑는다(패스 포함).
- 표시하는 기력은 **프로필 이름 그대로다 — 보정은 없다.**

### 3.6 비용

**사람 망을 언제 평가하나**
- 루트에서만 평가한다. 단, Pla/Opp 탐색 확률을 0보다 크게 주면 모든 노드에서 평가한다 [S11].
- 루트 평가는 `rootNumSymmetriesToSample`개 대칭의 평균이다.

| 레시피 | 수당 신경망 평가 횟수 |
| --- | --- |
| 사람 모델 단독, 1방문 | 1(대칭 ×1~2) |
| 이중(주+사람), 1방문 | 약 2~3 |
| 5k 예제·go-bot | 주 모델 약 40 + 사람 약 2 |
| 9d 예제 | 주 모델 약 400 + 사람 약 2 |
| 탐색 전체에 사람 정책 섞기 | 방문당 약 2배 |

**평가 1회의 크기** (DERIVED)
- b18c384nbt는 파라미터 약 2,680만 개(FP32로 107.2MB), 19x19 평가 1회에 약 9.6 GMAC다.
- 사람 모델도 같다. 메타데이터 인코더는 작다.
- 비교: b10c128 약 1.1 GMAC, b28c512 약 26 GMAC.

**S22U에서 수당 시간** (Eigen, 19x19 버퍼, DERIVED, **모두 신뢰도 낮음** — §2.2 이상치와 JSON 고정비 미상 때문)

| 레시피 | 1스레드(평가당 약 0.24초) | 4스레드(방문당 약 0.075초, 고정비 미상) |
| --- | --- | --- |
| 사람 단독 1방문 | 0.25~0.5초 | 고정비에 따라 1초대일 수도 |
| 이중 1방문 | 0.5~1초 | 위와 같음 |
| λ 40방문 | 약 10초 | 약 3초 |
| λ 100방문 | 약 24초 | 약 7.5초 |
| 9d 예제 400방문 | 약 96초 | 약 30초 |

- 중급폰 배율은 §0.1의 BadukAI 표로 거칠게 짐작한다. 대용 지표일 뿐이다.
- **Eigen 평가 스레드 수(`numEigenThreadsPerModel`)의 기본값은 모드마다 다르다.**
  - GTP: `numSearchThreads`를 따른다 [S8]. 앱 GTP는 1이다.
  - 분석 엔진: `min(numAnalysisThreads × numSearchThreadsPerAnalysisThread, CPU 코어 수)`(`analysis_learning.cfg:96`). 앱은 분석 프로세스를 1 × 4로 띄우니 **4**다(DERIVED, `KataGoProcessRuntime.kt:66-68`, `KataGoProcessEngineAdapter.kt:509`).
  - 평가 1회가 여러 Eigen 스레드로 실제로 빨라지는지는 **UNVERIFIED**다.

**메모리**
- DERIVED: 가중치만 b18 하나에 약 107MB, 둘이면 약 215MB, 셋이면 약 320MB다.
- 여기에 더해지는 것
  - NN 캐시: 분석 cfg는 2^20칸이다(`analysis_learning.cfg:114`). 항목당 약 1.5KB라서, 다 차면 이론상 1.5GB에 이른다. 칸은 차는 만큼만 쓰인다.
  - 배치 버퍼: `nnMaxBatchSize = 96`(:90)
  - GTP cfg(`gtp_learning.cfg`)는 캐시 크기를 적지 않아서 KataGo 기본값을 쓴다. 그 값은 UNVERIFIED다.
- **제안**: 리그 프로세스는 `-override-config`로 캐시와 배치를 줄인다(5k 예제는 캐시 17). 두 값을 RSS 시험(P1)의 변수로 넣는다.
- GPU 사례: 두 망을 올린 봇 인스턴스 하나에 VRAM 약 1.5GB [S22].
- OpenCL, 6GB 그래픽카드에서 두 모델을 올리면 자원이 부족하다는 이슈가 해결되지 않았다 [S16].
- **Android에서의 RSS는 UNVERIFIED.**

**작은 모델과 폰 선례**
- 작은 공식 사람 모델은 없다. b10으로 증류하자는 제안만 있었다 [S17].
- BadukAI(Android), Go AI(iOS), A Master of Go(iOS 인앱)가 이미 폰에서 사람 모델을 돌린다 [S27][S28].

### 3.7 알려진 약점 [S4][S6][S13][S18]

- 읽기가 없어 사활·축 같은 수읽기가 약하다. 구체적인 실패율은 UNVERIFIED.
- 약한 급 프로필은 너무 일찍 패스한다.
- 고단 프로필은 탐색 없이는 이름값을 못 한다(19x19 rank_5d ≈ KGS 1단).
- 사람 망의 승률·점수는 사람답지 않고 편향돼 있다. 형세 표시에 쓰면 안 된다.
- 15급 이하 프로필끼리는 봇끼리 거의 동률이다(19x19, PR #1209).
- 9급 넘게 차이 나는 비대칭 프로필은 학습 분포 밖이다.
- 19x19 밖의 학습 데이터가 적다. 13x13에서는 급/단 간격의 모양이 19x19와 다르다는 신호가 있다(§3.5). 9x9에서의 충실도는 **UNVERIFIED**.

### 3.8 참고 — 사람 모델 없이 약하게 두는 방법

- 1 playout KataGo 봇 둘(하나는 b60, 하나는 망 미상)이 OGS 5.5~6.6단이었다. **앱 b18 원시 정책이 얼마나 센지는 재지 않았다** [S22]. 어느 쪽이든 급 상대로는 너무 셀 가능성이 크다.
- `chosenMoveTemperature*` 계열 설정은 탐색한 수들 안에서만 무작위로 고르고, 기력 보정은 없다 [S8].
- 작은 옛 망도 "훨씬 약하지만 탐색하면 여전히 프로 이상"이다 [S12].
- **KaTrain "Calibrated Rank"** [S26]
  - 정책만 쓴다. 합법수 N개를 무작위로 골라 그중 정책값이 가장 높은 수를 둔다.
  - N = round(10^(−0.05737·급 + 1.9482)), 여기에 몇 가지 보정이 붙는다.
  - 2020년에 GnuGo 3.8·Pachi를 상대로 보정했다. **12급~3단에서만 유효**하고, 망이 바뀌면 달라진다.
  - 기력↔Elo 상수 `CALIBRATED_RANK_ELO`는 한 급에 약 64.3 Elo인 직선이다(18급 −21.7 … 2단 1263.96, 4단 1700). 이 값이 어떻게 나왔는지는 코드에 적혀 있지 않다(UNVERIFIED) [S26].
  - OGS의 katrain 봇들은 2020년 6월에는 목표 기력과 "한 점 안"이었다.
  - 사용자 불만: 큰 돌의 단수를 무시함, 팻감 낭비, 지고 있을 때 이상한 수 [S36].

| **① JSON humanPolicy**(권장) | 분석 프로세스에 `-human-model`을 붙이고, 리그 요청에 `humanSLProfile`·`includePolicy`·maxVisits 1(최대 40)을 넣는다. 추출은 앱이 go-bot식 꼬리 누르기로 한다 | 요청마다 독립이라 상태가 없다. 프로필 전환 비용이 0이다. 5 캐릭터의 GTP 경로와 무관하다. **한 번의 요청으로 `policy`(주 모델)와 `humanPolicy`(사람), 주 모델의 루트 승률·점수를 같이 받는다**(기권 판단에 쓴다) | 파서·`AnalysisLimit`·결과 모델·캐시 코덱을 확장해야 한다. 신경망 3개가 기본이다 |
| ② GTP `kata-raw-human-nn` | GTP 프로세스에 `-human-model`을 붙이고, 수마다 `kata-set-param`으로 프로필을 바꾼 뒤 원시 출력을 받는다 | 가장 싸다(평가 1회, 한 프로세스에 망 2개). 기존 `kata-raw-nn` 파서를 재사용할 수 있다(`engine-android/.../KataGoAnalysisParser.kt:145`) | `EngineCoreApi`에 새 메서드가 필요하고 원격·스텁·가짜 어댑터도 고쳐야 한다(함정 70). **5 캐릭터가 쓰는 프로세스를 바꾸므로** 고정 조건과 충돌한다 |
| ③ GTP genmove + 사람 cfg | KataGo가 직접 착수한다(go-bot과 같은 방식) | 앱 코드가 가장 적다. 보정된 레시피를 그대로 쓴다 | 40방문에 약 10초(1스레드). 전역 설정이라 5 캐릭터의 genmove 폴백까지 사람처럼 바뀐다 → **앱에서는 비권장**, P0 데스크톱 기준점으로만 쓴다 |

### 4.3 단 리그 윗단을 메우는 방법

## 5. 리그 설계안 (제안)

### 5.1 구조 — 9단계

| 리그 | 단계 | 앱 기력(타이젬 척도) | 보정 전 시작 가설 |
| --- | --- | --- | --- |
| 급 | 1 | 18~16급 (≈KGS 16~15k) | ⚠️ **19x19에서는 원시 프로필로 못 만든다.** 가장 약한 rank_20k가 KGS 14급(≈ 타이젬 15~16급)이다. 온도를 1 넘게 올리는 식의 추가 약화가 필요한데, 그러면 사람답지 않은 실수가 나올 위험이 있다. KaTrain 불만과 같은 종류다 [S36]. 21k~25k 프로필은 미병합 PR #1209에만 있다. **13x13에서는** rank_20k가 OGS 26급으로 측정돼서 원시 프로필로 될 수도 있다. 오히려 너무 약할 수도 있다(§3.5) |
| 급 | 2 | 15~13급 | 19x19: 15k 이하가 봇끼리 동률이라 온도로 간격을 벌린다. 13x13: 20k~10k가 벌어져 있다 |
| 급 | 3 | 12~10급 | 사람 원시 추출(go-bot식 꼬리 누르기) |
| 급 | 4 | 9~7급 | 사람 원시 추출 |
| 급 | 5 | 6~4급 | 사람 원시 추출. 19x19에서 rank_5k가 이름값을 하는 구간이다 |
| 급 | 6 | 3~1급 | 사람 원시 추출. ⚠️ 13x13에서는 5k~5d가 뭉치기 시작한다 |
| 단 | 7 | 1~3단 (≈KGS 2k~1d) | 19x19: rank_1d(≈KGS 1~2급)~rank_5d(≈KGS 1단)로 닿을 가능성이 있다. ⚠️ 13x13에서는 갈리지 않을 위험 |
| 단 | 8 | 4~6단 (≈KGS 2~4d) | 원시로는 부족하다. **정책 섞기(가설)** 또는 λ 40방문 |
| 단 | 9 | 7~9단 (≈KGS 5d 이상) | 섞기의 윗단 ~ 주 모델 정책. 닿지 않으면 천장을 조정한다(§10 Q6) |

- 약 3급씩 묶는 방식은 야호의 급 구간 표(13~15급, 10~12급, 3~5급)와도 맞는다 [S33].
- 숫자 기력을 **항상 이름 옆에** 쓴다(예: "14급 · 이름"). 단계 이름과 그룹 이름이 헷갈렸던 전례가 있다(`docs/spec/FAST_BEGINNER_TIER_DESIGN.md` §3).
- **1단계 가능 여부와 단 리그 분리 여부는 P0 결과로 정한다.** 1차 출시 범위가 이것에 달려 있다(§9).

### 5.2 단계당 상대 수

| 안 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| **ⓐ 단계 캐릭터 9명 × 3레벨**(기본 제안) | 단계마다 캐릭터가 1명 있고, 급이 오를 때마다 한 칸씩 세진다 | 그림이 9장이면 된다. 단계 = 캐릭터라서 "관문"이 선명하다. 인접 급 차이가 작아도 어색하지 않다 | 캐릭터를 모으는 재미는 적다 |
| ⓑ 급마다 1명(27명) | 상대 = 그 급 | 칭호의 뜻이 가장 단순하다("14급 상대를 이기면 14급") | 그림이 27장 필요하다. 약한 쪽에서 이웃한 상대들이 똑같이 느껴질 위험이 있다 |
| ⓒ 단계당 1명 + 치석으로 칸 나누기 | 전통 방식 | 19x19에서는 자연스럽다 | 13x13은 1점이 2.5~3급, 즉 한 단계 전체라서 치석으로는 칸이 나오지 않는다 [S34] |

### 5.3 승급 규칙

#### 5.3.1 대국 조건

- 승급 대국은 **호선**이다. 조건을 하나로 통일해야 칭호가 의미를 가진다.
- **규칙과 덤을 사다리마다 고정한다**(§10 Q10).
  - 일본룰 빠른 계가는 "?" 불확실 점수를 낼 수 있다(`docs/engine/SCORE_AND_ENDGAME_DECISION.md`).
  - 처리 방법을 정해야 한다: 창에서 빼거나, 정밀 계가를 돌린다.
- **시계는 없다.** 앱에 대국 시계가 없다. 한편 프로필은 기본 20분 + 30초 × 5회 초읽기 대국을 흉내 낸다(`sgfmetadata.cpp` master :228-230) [S9].
- **리그의 시간 예산은 사용자의 전역 설정(끔 / 1 / 3 / 5 / 10초)과 따로 둔다.**
  - 1방문 단계는 시간 설정의 영향을 받지 않는다.
  - λ 탐색 단계는 1~3초 설정이나 느린 폰에서 탐색이 잘린다. 그러면 봇의 세기가, 곧 칭호의 뜻이 기기와 설정마다 달라진다.
  - ⇒ **제안**
    - 방문 수를 고정한다.
    - 리그 전용 시간 상한을 둔다.
    - 그 기기가 와치독 한도(상한 × 1.2 + 8초, `EngineTurnWatchdog.kt:57-68`) 안에 그 단계를 끝내지 못하면, **그 기기에서는 그 단계를 막는다.** 몰래 약하게 두지 않는다.
- 도움 기능(형세·추천 수·힌트·무르기)은 승급전에서 끈다. 쓰면 그 판을 비랭크로 돌린다(§10 Q11).

#### 5.3.2 한 급은 몇 Elo인가 — 가정 하나로 통일

- **가정: 한 급 = 64 Elo.** KaTrain의 `CALIBRATED_RANK_ELO`가 급당 약 64.3 Elo인 직선이다 [S26].
- 다른 값과의 관계
  - OGS의 기력 공식(레이팅 = 525·e^(순위/23.15)) [S23]으로 보면 한 급은 "레이팅 ÷ 23.15"다. 수준마다 다르다(DERIVED).

    | 수준 | 레이팅 | 한 급 |
    | --- | ---: | ---: |
    | 18급 | 약 870 | 약 38 |
    | 5급 | 약 1450 | 약 63 |
    | 1급 | 약 1850 | 약 80 |
    | 5단 | 약 2330 | 약 100 |

    64는 이 범위의 가운데다.
  - PR #1209의 "한 칸 100 Elo"는 그 사다리의 **설계 목표**다. 사람 기력 간격을 잰 값이 아니다 [S18].
  - v1 §6.3의 "3급 차 70%"(≈150 Elo, 급당 50)는 버린다.
- 이 가정에서 나오는 기대 승률(DERIVED)

  | 급 차이 | 기대 승률 |
  | --- | ---: |
  | 1급 | 59% |
  | 2급 | 68% |
  | 3급 | 75% |

  - 민감도: 급당 40이면 3급 차가 67%, 급당 100이면 85%다.
- §5.3.3의 시뮬레이션과 §6.3의 성공 기준은 모두 이 가정에서 나온다.

#### 5.3.3 승급 규칙 후보와 칭호 인플레이션

**v1 초안의 문제**
- v1 초안의 규칙: 최근 5판 중 3승(18~10급), 최근 6판 중 4승(9급~6단), 최근 7판 중 5승(7~9단). 강등 없음, 재도전 무제한.
- 이 규칙은 창에 M승이 차는 순간 승급한다.
  - 최소 판수가 없다.
  - 져도 잃는 것이 없다.
  - 재도전은 무제한이다.
- 그래서 **꾸준히 도전하는 사용자는 실력보다 몇 급 위의 칭호를 갖게 된다.** v1이 약속한 "칭호가 의미를 가진다"와 어긋난다.

**시뮬레이션 조건** (코드는 부록 A. 초안의 스크립트는 임시 폴더에 있었다)
- 사다리는 27칸(18급 … 1급, 1단 … 9단)이다.
- 사용자의 실력은 고정한다. 칸 r의 봇을 이길 확률은 p = 1 / (1 + 10^((r − 실력칸) × 64 / 400))이다.
- 사용자는 늘 지금 칸의 봇과 두고, 승급하면 다음 칸으로 간다. 재도전은 무제한이다.
- 한 칸짜리 칸은 20,000회, 사다리 전체 칸은 4,000회 반복했다.

| 규칙 | 제 실력 상대(p=0.50) 승급 판수 중앙값 | 1급 약한 사용자(p=0.41) 50판 안 승급 | 3급 약한 사용자(p=0.25) 50판 안 승급 | 9급 실력자가 18급에서 시작해 100판 뒤 칭호 − 실력(중앙값 / 90%) | 300판 뒤 | 9급 실력자가 9급 칭호에 닿는 판수(중앙값) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 최근 5판 3승 (v1) | 5~6 | 100% | **86%** | **+4 / +5** | **+6 / +7** | 34 |
| 최근 6판 4승 | 9 | 96% | 52% | +2 / +3 | +5 / +5 | 46 |
| 최근 7판 5승 | 14 | 81% | 22% | +1 / +2 | +3 / +4 | 60 |

| 7판 5승 + 강등(같은 조건) | 14 | – | – | 현재 +0, 최고 +1 / +2 | 현재 +0, 최고 +2 / +3 | – |

**읽는 법**
- v1 규칙(5판 3승)에서는 **3급 약한 사용자도 50판 안에 86%가 승급한다.** 9급 실력자가 100판 뒤 5급, 300판 뒤 3급 칭호를 단다.
- **최소 판수만 더하는 것은 거의 효과가 없다.**
- 창을 키우면(7판 5승) 부풀림은 줄지만, 제 실력 상대에게도 승급이 느려진다(14판).
- 고정 블록은 부풀림이 적은 대신, 제 실력에서도 승급 중앙값이 19판이다.
- **강등이 있는 "현재 기력"은 실력에 붙어 있다(+0).** 내려가지 않는 "최고 칭호"만 +1~+3 부풀어 오른다.
- 숨은 Elo 게이트는 부풀림이 +0~+2다. 대신 제 실력까지 오르는 데 82판이 걸린다(게이트가 없으면 34판). 시작 레이팅을 배치 대국으로 주면 줄어들 것이다(시뮬레이션하지 않음).

**시뮬레이션의 한계**
- 실력을 고정했다. 실제로는 사용자가 는다. 그래서 오른 칭호의 일부는 진짜 향상이다.
- 판마다 독립이라고 봤다. 틸트나 봇 공략법은 없다고 봤다.
- 급당 64 Elo로 봇 간격이 고르다고 가정했다. 실제 간격은 P0에서 잰다.

**트레이드오프**

| 방식 | 칭호의 정직함 | 승급의 맛(빈도) | 벌을 받는 느낌 | 구현 |
| --- | --- | --- | --- | --- |
| 굴러가는 창만(v1) | 낮음 | 높음 | 없음 | 쉬움 |
| 창을 키움 | 중간 | 중간 | 없음 | 쉬움 |

| 지면 진행을 잃는 규칙(별) | 중간 | 중간 | 약간 | 쉬움 |

| 숨은 Glicko/Elo가 칭호를 거름 | 높음 | 낮음~중간 | 잘 안 보인다 | 중간 |

**제안(기본안, 결정은 §10 Q4·Q5)**
- **현재 기력**은 내려갈 수 있고, 주 표시로 쓴다.
- **최고 칭호**는 내려가지 않고, 기록으로 쓴다.
- 승급 창: 18~10급은 최근 5판 3승도 괜찮고, 9급 위로는 6판 4승 이상.
- 강등: 같은 칸에서 최근 5판 1승 이하면 한 칸 내려간다.
- 인증서·공유 카드는 "그 급 승급"이라는 **사건**에 준다.

#### 5.3.4 판이 제대로 끝나지 않을 때

- **이탈·밀려남**
  - 이어하기 슬롯은 하나다(`GameSessionStore.kt:68`). 다른 대국을 시작하면 끝나지 않은 리그 판이 밀려난다(`GameBranchApplication.kt:26-28`).
  - **제안**: 랭크 판을 버리거나 밀어낸 것은 **패로 친다.** 다른 대국을 시작하기 전에 경고한다. 그렇지 않으면 사용자가 지는 판을 피해 간다.
  - 대안: 리그 전용 슬롯을 둔다.
- **이어하기**
  - 이어한 판이 랭크 판으로 남으려면 `SavedGameSnapshot`에 선택 필드가 필요하다. 넣을 것: 리그 ID, 단계, 사다리 버전, 랭크 여부.
  - `GameHistoryEntry`에도 같은 선택 필드를 둔다.
  - 옛 빌드는 이 필드를 모르고 버린다. 그러면 옛 빌드로 복원한 판은 비랭크가 된다. 허용한다.
  - ⚠️ 이것은 세이브 형식에 **선택 필드를 더하는 일**이다. 스키마 버전은 올리지 않는다(함정 69).
- **앱 프로세스가 죽는 경우**는 이어하기로 대비돼 있다(결함 아님).
- **다시보기 분기(#172)**: 리그 판에서 분기한 판은 **비랭크**로 두거나 분기 버튼을 막는다. 그렇지 않으면 이기던 국면에서 다시 시작해 승급할 수 있다.
- **사용자 기권**은 패다.
- **봇 기권**
  - 지금은 `allowResignation=false`(`EngineBootstrap.kt:83`)이고 수는 분석 결과에서 나온다. 그래서 약한 봇이 진 판에서도 끝까지 둔다(§11 D24).
  - **제안**: 앱이 자체 기권 규칙을 둔다. 기준은 주 모델의 승률·점수가 N수 연속 조건을 넘는 것이다. 참고값은 5k 예제·go-bot의 −0.99 / 20수 연속 / 40집 이상 / 판 넓이당 0.4수 이후다 [S6][S43].
    - 급이 낮을수록 늦게 던지게 한다. 사람 하수는 잘 던지지 않는다.
    - 1방문 JSON 결과에 주 모델의 루트 값이 함께 오므로 추가 비용은 거의 없다(DERIVED).
  - **봇이 기권하면 사용자 승**이다.
- **"?" 불확실 결과**: 창에서 빼거나 정밀 계가를 돌린다(§5.3.1).

#### 5.3.5 보여 주는 방식과 연출

- 화면에 창을 그대로 보여 준다(예: ●●○● "1승 더"). 목표에 가까울수록 빨라지는 효과를 노린다 [S38].
- **월반 — v1 규칙은 절대 발동하지 않는다.**
  - v1은 "같은 상대에게 5연승하면 두 칸"이었다.
  - 그런데 5판 3승이나 6판 4승이면 3번째나 4번째 승리에서 이미 승급한다.
  - **제안**: 1차 출시에서는 뺀다.
  - 넣는다면 이렇게 다시 정의한다: "**무패 승급**(5판 3승이면 3연승, 6판 4승이면 4연승)이면 다음 급 하나를 건너뛴다. 단계 안에서만." 부풀림에 주는 영향은 시뮬레이션하지 않았다.
- **단계 클리어** = 그 단계의 맨 윗급을 통과하는 것. 배지, 다음 단계 공개, 공유 카드를 준다.
- **1급 → 초단**은 가장 크게 연출한다("초단 승단" 앱 인증서).
  - **앱 기력임을 명시**하고, 한국기원 단증과 닮지 않게 만든다.
  - 초단 관문을 따로 어렵게 만들지는 않는다. 그러면 승급전 문제가 되살아난다.

#### 5.3.6 18급에서 9단까지 몇 판인가 (이상화)

- 모든 상대에게 승률 50%를 유지한다고 가정한 **이상화된 값**이다.
- 칸마다 승급 판수 중앙값(p=0.5)
  - 5판 3승: 5~6판. 분포가 경계에 걸려 있어서 난수 시드에 따라 5와 6을 오간다.
  - 6판 4승: 9판
  - 7판 5승: 14판
- v1의 배분으로 합하면: 9칸 × 6 + 9칸 × 9 + 6칸 × 9 + 3칸 × 14 = **약 231판**(5판으로 잡으면 222판).
- 13x13 한 판을 10~15분으로 **가정**하면 약 **40~60시간**이다(DERIVED).
- 부풀림을 막는 규칙을 쓰면 늘어난다. 예: 고정 블록 4/5면 칸당 19판, 합쳐 약 500판.

### 5.4 강등과 보호

- §5.3.3의 선택에 따른다.
- 기본안("현재 기력 + 최고 칭호")이면
  - **최고 칭호는 내리지 않는다.** GoQuest가 같은 방식이고, 혼자 배우는 사용자를 벌하지 않는다 [S36].
  - **현재 기력은 내려간다.** 칭호가 실력을 뜻하게 하려면 필요하다.
- 강등을 아예 두지 않기로 한다면, 칭호가 실력을 뜻한다고 주장하지 않는다. "도달한 기록"이라고만 부른다.
- 선택 사항: 숨은 "요즘 기세" 레이팅을 상대 추천에 쓴다.

### 5.5 첫 배치

- 기본은 18급 상대부터 시작한다.
- 경험자는 시작 단계를 고를 수 있게 하되 **초단까지만** 허용한다. 야호도 자가 등록을 3단까지로 막는다 [S33].
  - 스스로 고른 칭호는 첫 승급 전까지 "임시"로 표시한다.
- 선택 사항: "기력 측정" 3~5판.
  - ±3 → ±2 → ±1 순서로 이분 탐색하고, 져도 불이익이 없다.
  - 결과보다 한 급 아래에 배치해서 첫 승급이 빨리 오게 한다. 진행을 미리 조금 채워 주면 완주율이 오른다 [S38].
  - 숨은 Elo 게이트를 쓴다면, 배치 결과를 시작 레이팅으로 준다.

### 5.6 연패 보호

- 근거: EA 자료에서 3연패 뒤 7일 이탈률은 5.1%였다. 기준선은 2.6~2.7%다 [S38].
- 같은 상대에게 2연패하면 → 도움이 붙은 **연습 대국**을 제안한다(덤을 더 받거나 1점 접기).
  - 연습 대국은 승급 창에 들어가지 않는다. 체스닷컴의 왕관처럼 표식만 준다 [S37].
- 3연패하면 → 이전 급 상대와의 "몸풀기" 대국을 권하고, 진 판에서 큰 실수 1~3개를 보여 준다.
- 봇 사다리에는 진짜 벽이 생긴다. 대인전처럼 승률이 50% 근처로 맞춰지지 않기 때문이다. 막힌 사용자에게는 다른 목표(왕관, 무르기 없이 이기기)를 준다.
- 어떤 급의 승급 중앙값 판수가 이웃 급의 2배를 넘으면, 실력 벽이 아니라 **보정 문제**로 본다.
  - 단, 앱에 analytics가 없으므로 기기 안 기록으로만 알 수 있다(§6.2 M4).

### 5.7 치석·덤으로 미세 조정

- 승급전은 호선이다. 자기 급의 상대를 호선으로 이겨야 "그 급"이라는 뜻이 선다.
- 도움은 연습 대국에서만 준다.
  - 19x19: 1점 ≈ 1급이라 치석이 맞다.
  - 13x13: 1점이 한 단계 전체라서 **덤 단위**로 조정하는 게 맞다 [S34][S35].
  - ⚠️ 앱의 덤 선택지는 0.5/6.5/7.5뿐이다(`BoardModels.kt:11`). 연습용 덤 단계에는 새 값이 필요하다.
- 상대 쪽 손잡이
  - 프로필(주 손잡이)
  - 온도: 낮을수록 "다수결" 효과로 세진다 [S6]
  - 섞기 비율(단 리그 윗단)
  - 연습 치석 대국에서는 `rank_{흑}_{백}` 프로필(9급 차 이내에서만)
- **P0 선택 변형: 비대칭 프로필.**
  - 지금 사다리는 사용자가 봇과 정확히 같은 급이라고 가정한다.
  - 호선이면서 차이가 작은 경우에 `rank_{사용자}_{봇}`을 쓰면, 봇이 "상대가 조금 약하다/세다"를 아는 대국을 흉내 낸다. 9급 차 이내에서만 쓴다.
  - 사람다움과 세기가 나아지는지 P0에서 잰다.

### 5.8 판 크기

- 판 크기마다 사다리와 칭호를 **따로** 둔다.
  - KGS는 19x19만 레이팅에 반영한다 [S25].
  - Crazy Stone이 판 크기별로 레이팅을 따로 둔다는 말은 **App Store 리뷰어 글(2차 자료)**에서 나왔다. 제품 공식 문서가 아니다 [S36].
  - OGS는 판 크기별 레이팅을 따로 낸다(§3.5).
- **OGS 판 크기별 신호**(잡음이 크다)
  - 13x13에서 약한 쪽이 더 벌어진다 → 급 리그 아랫단은 13x13에서 오히려 잘 갈릴 수 있다.
  - 13x13에서 5k~5d가 뭉친다 → **단 리그가 13x13에서 갈리지 않을 위험**이 있다.
- **P0 가설**: 13x13에서 3급 차 단계끼리의 승률이 19x19와 같은 만큼 갈리는지는 **모른다.** 판 크기별로 잰다. v1의 "13x13은 운이 크게 좌우한다"는 추론은 치석 가치와 호선 승률을 섞은 잘못이라서 지웠다.
- 1차로 어떤 판을 열지는 **P0 결과로 정한다.**
  - 13x13
    - 장점: 앱 기본 판이고 모바일에 맞다. 급 아랫단이 잘 갈릴 신호가 있다.
    - 단점: 사람 모델 학습은 대부분 19x19다. 단 리그가 뭉칠 위험이 있다.
  - 19x19
    - 장점: 모델이 가장 충실하고, 급 척도가 원래 정의된 판이다.
    - 단점: 판이 길고 폰 화면에 빽빽하다. 1단계(18~16급)를 원시로 못 만든다.
- 9x9는 랭크에 쓰지 않는다(1점 ≈ 6급). 튜토리얼로는 쓸 수 있다.

### 5.9 5 캐릭터와의 관계

- 5 캐릭터는 지금 그대로 **자유 대국**으로 둔다.
- 리그는 별도 모드다. 계획된 "대국장" 진입 개념과도 맞는다(`FAST_BEGINNER_TIER_DESIGN.md:184`).
- 캐릭터에 급/단을 붙이는 것은 **보정한 뒤에만** 한다(예: "약 N급"). 이 숫자는 P0에서 처음 나온다.
- **5 캐릭터 회귀 확인** — 이것을 통과해야 "그대로 둔다"가 확정된다.
  1. 캐릭터는 GTP 경로를 쓴다. `-human-model`은 리그 분석 프로세스에만 붙이고, GTP에는 붙이지 않는다.
  2. **JSON 분석 기능도 확인한다.** 추천 수, 착수 평가, 대국 뒤 최적화가 여기에 든다.
     - 사용자가 리그를 나간 뒤에도 사람 모델을 올린 분석 프로세스가 살아 있으면, 캐릭터 대국의 이 기능들이 그 프로세스에서 돈다.
     - 대책 둘 중 하나:
       - 리그를 나갈 때 분석 프로세스를 `-human-model` 없이 다시 띄운다.
       - 사람 설정을 보내지 않은 요청의 결과가 같음을 검증한다. 사람 가중치가 0이면 탐색이 바뀌지 않는다는 가정은 **UNVERIFIED**다.
  3. GTP 프로세스에는 `humanSLChosenMoveProp`이나 프로필을 **절대 전역으로 걸지 않는다.** genmove 폴백까지 사람처럼 바뀐다.

### 5.10 보상·프리미엄 연결

**보상**
- 출석·광고 조각 경제와 **분리**한다. 승급 보상은 배지·인증서·공유 카드로 한다.
- 알려진 "유령 출석 보상" 잠복 결함을 되풀이하지 않는다(`docs/spec/FEATURE_ACCESS_PRINCIPLES.md` §8.4).
- 업적 시스템은 코드에 없다(출석 보상 화면뿐이다). 리그가 앱의 첫 진행·전적 기능이 된다.

**프리미엄**
- 구독이 캐릭터 로스터를 여는 곳은 `BotCollectionState.isAvailable` 하나뿐이다(:79-82).
- 1시간 광고 보상은 일부러 로스터를 열지 않는다(`shared/.../application/premium/state/PremiumState.kt:86`).
- `clampToOwnedBotCharacter`는 카탈로그 밖 레벨에 null을 돌려준다. 즉 **따로 설계하지 않고 붙이면 리그는 무료로 열린다.**
- 제안
  - **칭호는 팔지 않는다.** 승급을 돈으로 사면 맛이 없다.
  - 형세·추천 수·힌트·무르기는 승급전에서 끄거나, 쓰면 그 판을 비랭크로 돌린다.

**백업**
- 리그 진행은 로그인 백업(#170)에 넣을 유력한 항목이다. 그 전까지는 재설치나 기기 변경 때 돌아오지 않는다(§0.1).

### 5.11 표시 규칙 — 아직 정하지 않은 것

- **주 칭호**: 판 크기마다 칭호가 있으면 홈·기록·공유 카드에 어느 것을 보여 줄지.
  - 제안: 판 크기를 붙여 쓴다(예: "13줄 5급").
- **임시 칭호 표식**: 자가 배치나 배치 대국으로 받은 칭호에 붙인다(예: "5급(임시)").
- **"초단"과 "1단"**: 한국어에서 둘은 같은 뜻이다. 연출에는 "초단", 목록에는 "1단"을 쓸지 정한다.
- **다른 언어**: en "5 kyu / 1 dan", ja "5級 / 初段", zh "5级 / 1段"(初段).
- **끝**: 9단 이후나 9단계가 막혔을 때 보여 줄 화면. 졸업 화면이나 "이 기기에서 열린 최고 단계" 화면.

### 5.12 초기화와 사다리 버전

- **리그 초기화**: 사용자가 누르면 18급부터 다시 시작한다. 리셋 코디네이터 두 곳에 등록한다(함정 6·55).
- **사다리 버전**
  - 업데이트로 봇을 다시 맞추면, 이미 딴 칭호는 유지하고 **어느 사다리 버전에서 땄는지** 기록한다.
  - 칭호의 뜻을 몰래 바꾸지 않는다.
  - 새 버전에서는 현재 기력을 다시 확인한다(예: 창을 비우고 시작).

### 5.13 5 캐릭터에 나중에 사람 스타일을 입힌다면

- **기술적으로는 된다.** 티어마다 프로필을 하나씩 대응시키고, JSON 경로나 `kata-raw-human-nn`으로 보내면 된다.
- 하지만 걸리는 것이 넷 있다.
  - **고정 조건을 깬다.** 캐릭터의 세기와 엔진 경로가 바뀐다.
  - **모든 기기에 모델이 있어야 한다.** 설치 시 동봉이나 fast-follow로 약 +100MB를 받거나, 모델이 오기 전에는 다른 세기로 두는 폴백을 둬야 한다. 폴백이면 캐릭터의 세기가 다운로드 여부에 따라 달라진다.
  - **P0 배치 표가 먼저 있어야 한다.** 그 캐릭터가 지금 몇 급인지 알아야 같은 세기의 프로필을 고를 수 있다.
  - **`fast_beginner_$tier` ID는 그대로 둬야 한다**(세이브 스키마).
- **대안**: 원래 캐릭터는 그대로 두고, 옆에 **"사람 스타일" 변형을 선택형으로** 더한다.

## 7. 용량·배포

**Play 한도** — Google 도움말, 2026-09-28 재확인 [S39]
- ⚠️ **"기본 모듈 150MB"는 옛 전제다.**

**PAD 주문형의 요점** [S39]
- `getPackLocation()` → `assetsPath()`가 팩의 `assets` 폴더 경로를 준다. 네이티브 엔진이 그 자리에서 바로 읽는다(filesDir로 복사할 필요 없음).
- **팩 위치를 실행 사이에 캐시하지 말라**고 문서가 적는다. 앱은 실행할 때마다 팩이 있는지 확인해야 한다.
  - 팩은 앱 업데이트나 **앱 데이터 삭제**로 무효가 될 수 있다.
- 주문형 파일은 "사용자가 지우거나 PAD 라이브러리가 옮길 수 있다."
  - 저장 공간이 부족할 때 시스템이 지우는지는 **UNVERIFIED**다.
- **앱 업데이트 때의 순서**
  1. 패치를 받는다.
  2. 앱 바이너리를 업데이트한다.
  3. 받아 둔 팩을 무효로 한다.
  4. 패치를 적용한다.
  - 드물게, 앱이 열렸는데 팩 패치가 아직 끝나지 않은 순간이 있다.
- ⇒ 리그는 **들어갈 때마다 "모델 없음 → 다시 받기" 상태를 확인**해야 한다.
- 사이드로드로 설치한 앱은 `REQUIRES_USER_CONFIRMATION` 상태가 된다.
- 시험 방법: 로컬은 `bundletool build-apks --local-testing`, 실제에 가까운 시험은 내부 앱 공유.
- 팀의 adb 시드 개발 흐름(`Makefile:211-212`, `scripts/seed-katago-model-to-app.sh`)이 두 번째 모델을 알아야 한다.

**모델 수명 UX**
- 받기 진행률과 취소
- **먼저 빈 공간 확인**
- 팩이 지워졌을 때의 다시 받기 경로
- "받는 중"은 실패가 아니라 **정상 상태**로 보여 준다(`work/roadmap/260906-260911_RELEASE_AND_EARLY_FEEDBACK.md:694`)

**백로그 #57과의 관계 — 서로 다른 두 일이다**
- **#57**은 **주 모델(93MB)을 기본 모듈 밖으로 옮기는 일**이다.
  - 백로그 #57 카드에 "단독 브랜치·단독 인터널 검증", "다른 작업과 절대 병행하지 마라"가 적혀 있다.
  - 「사용자 결정 대기」 표의 #57 행 질문은 "109MB를 줄일 필요가 실제로 생겼는가(설치 이탈 관측 등)"이고, 기본값은 "안 한다"다(`work/roadmap/261001-_REFACTORING_BACKLOG.md`).
- **리그에 필요한 것**은 사람 모델을 담은 **주문형 팩 하나를 더하는 일**뿐이다. 주 모델의 설치 경로는 바뀌지 않는다.
- ⇒ **새 항목으로 만든다.**
  - 앱의 첫 PAD 통합이므로 #57의 격리 규칙(단독 브랜치, 단독 인터널 검증)은 빌려 온다.
  - 주 모델 이전과 **한 묶음으로 하지 않는다.**

**그 밖의 주의**
- 에셋 폴더 이름이 아직 `src/friend/assets`이고, `BundledEngineAssetContractTest`가 Makefile 변수로 이 이름을 고정하고 있다(`Makefile:34-40`).
- 모델을 나중에 `noBackupFilesDir`로 옮기면 자동 백업이 다시 켜진다(`docs/spec/PITFALLS.md` 37). 그러면 리그 진행도 백업되지만, 개인정보처리방침 문구와 부딪친다.
- 자체 서버에서 받게 하면 개인정보·데이터 보안 답변을 건드린다(함정 60) → 비권장.

**저사양 기기**
- ⚠️ **시동 벤치마크는 없다.** 기기 벤치마크는 사용자가 직접 실행하는 흐름이다. 저장된 값은 디버그 리포트에만 실리고, 그 값으로 분기하는 곳은 없다(`EngineBenchmarkController.kt:9-25`).
- 그래서 기기 게이트에는 **새 측정 코드**가 필요하다.
  - **제안**: 리그에 처음 들어갈 때 한 번 잰다. 잴 것: 로드 시간, 1방문 질의 몇 번, 메모리 여유.
  - 그 결과로 단계별로 막는다(예: 단 리그 윗단만 막기).
- "모델 받는 중/준비 중"은 정상 상태로 보여 준다.

**✖ 비권장: 주 모델을 작은 transformer로 바꿔 공간 벌기**
- 후보는 b10c384h6nbttflrs(38.2MB, KataGo 1.17 이상 필요)다.
- 하지만 5 캐릭터의 세기가 바뀌므로 **고정 조건 위반**이다.
- 16KB 정렬로 다시 빌드해야 하고(함정 33), Eigen에서 ARM transformer 성능은 UNVERIFIED다.

## 11. 1차 리서치(사용자 초안) 사실 확인

판정: ✅ 맞음 · △ 일부 맞음 · ✖ 틀림

| ID | 초안의 주장(요약) | 판정 | 고친 내용 |
| --- | --- | --- | --- |
| D1 | 온디바이스면 인프라 비용 0, 완전 오프라인, 패키지 50~150MB | △ | 인프라 비용 0은 맞다. **오프라인은 모델을 한 번 받은 뒤부터**다(첫 받기·다시 받기는 네트워크). 앱 기준 모델 약 98MB + 바이너리. Human SL을 더하면 +99MB. Play 한도는 기본 모듈 500MB, 에셋 팩 1.5GB [S39] |
| D2 | 약한 폰에서 발열·배터리·ANR 위험 | △ | ANR은 메인 스레드가 막힐 때만 생긴다. 이 앱의 엔진은 자식 프로세스 + IO 코루틴이라 버벅임은 있어도 ANR로 바로 이어지지 않는다 |
| D3 | 클라이언트-서버는 GPU 서버 비용, 하이브리드는 가벼운 모델 먼저 + 기기 사양으로 자동 조정 | △ | 의견으로는 타당하다. KataGo는 `benchmark`로 스레드 수를 맞추라고 권한다 [S8]. 앱에는 원격 어댑터와 MQ 프로토타입이 있다(이식은 승인 필요). 기기 사양 자동 조정에 쓸 시동 측정은 앱에 없다 |
| D4 | 최신 기기에서는 Vulkan이 가장 안정적 | ✖ | KataGo에는 **Vulkan 백엔드가 없다.** v1.18.2 기준 OpenCL·CUDA·TensorRT·ROCm·ONNX·Eigen·Metal뿐이다. Vulkan은 제3자 앱이 clvk(Vulkan 위의 OpenCL)를 거쳐 쓰는 경우만 있다 [S41] |
| D5 | OpenCL은 빠르지만 드라이버가 파편화돼 있다 | △ | 파편화는 맞다. OpenCL은 NDK 안정 API가 아니라서 API 31 이상에서는 `<uses-native-library>`를 선언해야 한다. Pixel 7a에서 튜닝 중 크래시(#977). "폰에서 빠르다"는 UNVERIFIED. KataGo는 Android를 공식 지원하지 않는다 [S40][S41] |
| D6 | GPU가 실패하면 CPU NEON 폴백이 필수 | △ | "NEON 백엔드"는 따로 없고, Eigen(CPU)이 NEON을 쓴다(얼마나 쓰는지는 UNVERIFIED). 이 앱에서는 Eigen이 폴백이 아니라 유일한 백엔드다 |
| D7 | iOS는 Metal/CoreML | △ | Metal 백엔드 문서는 macOS 기준이다. iOS 앱과 `ios-dev` 브랜치는 있다. 공식 iOS 빌드 경로는 UNVERIFIED [S41]. 이 저장소에는 iOS 앱이 없다 |
| D8 | 40/60블록은 폰에서 못 돌리니 b10c128이나 b18c384 | △ | "못 돌린다"는 과장이다(느릴 뿐). b10c128은 옛 g170 망이다. 새 transformer b10c384h6은 38.2MB지만 KataGo 1.17 이상이 필요하고, 성능 수치는 GPU 측정이며 폰 Eigen 속도는 UNVERIFIED. Human SL은 b18만 있다 [S12][S41] |
| D9 | kata_human_sl 가중치는 메모리 30MB 이하 | ✖ | 파일 이름은 `b18c384nbt-humanv0.bin.gz`이고 99,066,230 B다. 메모리에는 가중치만 약 107MB(FP32)에 캐시가 더해진다. 유일한 Human SL 모델이다 [S1][S14] |
| D10 | FP16/INT8 양자화로 속도 2배 | ✖(이 앱) | Eigen에는 FP16이 없다. KataGo 런타임은 INT8을 지원하지 않는다(PR #1231은 병합 없이 닫힘) [S41] |
| D11 | UI → 오케스트레이터 → JNI/파이프 → KataGo | △ | 공식 인터페이스는 stdin/stdout 위의 GTP와 JSON이다. 문서화된 C API는 찾지 못했다(UNVERIFIED). 앱은 이미 파이프 + 자식 프로세스 구조다 [S4][S12] |
| D12 | 서브프로세스는 크래시를 격리하지만 백그라운드에서 죽을 수 있다 | ✅ | API 29부터 W^X 때문에 nativeLibraryDir에서 실행해야 한다(앱은 준수, `app-android/build.gradle.kts:325`). Android 12+의 phantom process killer도 있다(일부만 확인) [S40] |
| D13 | pondering=false로 둔다 | ✅(키 이름은 틀림) | 키 이름은 `ponderingEnabled`이고 기본값이 false다. 앱에도 이미 설정돼 있다 |
| D14 | 백그라운드로 가면 엔진을 멈춘다 | △ | GTP `stop` 명령은 있다. 하지만 앱이 쓰는 취소 불가형 `kata-search_analyze`는 끊지 못한다 → `_cancellable` 변형이 필요하다. JSON 엔진에는 `terminate`가 있다 [S5] |
| D15 | 메모리 부족 경고 때 캐시를 비운다 | ✅ | `clear_cache`가 있다(항목당 약 1.5KB). 앱에는 onTrimMemory 훅이 없다 [S8]. 분석 cfg의 캐시는 2^20칸이다 |
| D16 | GTP 좌표는 I를 건너뛴다 | ✅ | 이미 구현돼 있고 골든 테스트도 있다 [S41] |
| D17 | 한국·일본 덤 6.5, 중국 7.5 | ✅ | 앱은 덤을 규칙과 따로 고른다 → 리그에서는 사다리마다 규칙과 덤을 고정한다 [S34] |
| D18 | KataGo는 기본적으로 중국룰에 최적화돼 있다 | ✖ | 자가대국에서 AREA/TERRITORY 계가 등 규칙을 무작위로 섞어 학습한다. 일본룰도 거의 모든 경우를 지원한다 [S12][S41] |
| D19 | 한국룰은 rules=japanese + 사석 보정 | △ | `korean` 단축어는 `japanese`와 똑같다. 앱은 이미 `final_status_list`와 로컬 계가를 쓴다 [S5] |
| D20 | SGF v4 트리를 로컬 DB에 둔다 | △ | SGF가 표준인 것은 맞지만, 앱은 SharedPreferences + JSON을 쓴다. 리그에 중요한 것은 전체 수순을 넘기는 일이다(`ignorePreRootHistory=false`) [S41] |
| D21 | Human SL 프로필로 기력 사다리를 만든다 | ✅ | `rank_20k`…`9d` 등. 18급~9단 모두 유효한 프로필 이름이다. 다만 이름이 곧 세기는 아니다(§3.5) [S4][S6] |
| D22 | 연승·연패에 따라 프로필을 올리고 내린다 | △ | 실행 중 전환은 된다(`kata-set-param` / overrideSettings). 다만 (a) 고단은 이름값을 못 하고 (b) 인접 급 차이가 작다(19x19 15k 이하) (c) 척도는 KGS다 (d) 사람 모델 단독이면 가치 출력이 왜곡된다 [S4][S18][S9] |
| D23 | 앱의 어느 경로가 사람 정책을 읽을 수 있나 | (앱 사실) | GTP 텍스트 출력에는 `humanPrior`가 없다 → JSON이나 `kata-raw-human-nn`이 필요하다 [S11] |
| D24 | resignThreshold로 자연스럽게 기권시킨다 | △ | genmove 전용이다. 앱은 `allowResignation=false`이고 분석 결과로 착수하므로 → 앱 자체의 기권 규칙이 필요하다(§5.3.4) [S6][S8] |
| D25 | 0.8~2.5초 가우시안 랜덤 지연 | △ | KataGo에 `delayMoveScale`/`delayMoveMax`가 이미 있다(감마 분포, 정책 확률에 반비례). 하지만 genmove 전용이라 앱에서 같은 공식을 구현해야 한다. "0.05초" 전제는 이 앱에 맞지 않는다(급 리그의 1회 평가도 수백 ms 이상) [S1][S11] |
| D26 | 복기: 승률 그래프, 급락한 수를 퀴즈로 | ✅(설계) | Human SL 가이드가 급을 기준으로 한 실수 지표를 제안한다. 앱에는 이미 ScoreTimeline이 있다 [S4] |
| D27 | "이중" 엔진 셋업 | ✅ | `-model` + `-human-model`은 공식 용도다. KaTrain 1.17.0이 선례다 [S12][S26] |
| D28 | 사람 정책보다 세게 하는 조정 | ✅ | λ, 온도, 점수 효용, 9d 예제. 5~9단은 실제 탐색이 필요해서 Eigen 1스레드로는 폰 지연을 넘길 수 있다 [S6][S7] |
| D29 | 업그레이드 경로 | ✅ | 1.17과 1.18 어디에도 Android GPU 지원은 없다. Human SL은 b18 그대로다 [S41] |

## 부록 A. 승급 규칙 시뮬레이션 (§5.3.3 재현용)

- 모델 조건은 §5.3.3에 적었다: 27칸, 급당 64 Elo, 실력 고정, 늘 지금 칸의 봇과 대국, 재도전 무제한.
- 반복 횟수: 한 칸짜리 표는 20,000회, 사다리 전체는 4,000회. 난수 시드는 7(v2), 5(추가 규칙), 3(Elo 게이트).
- 스크립트는 지금 임시 폴더에만 있다. P0를 시작할 때 저장소로 옮기는 것을 제안한다(예: scripts/league/ 아래 새 파일 — 아직 없다). 옮기려면 승인이 필요하다.
- 핵심 부분:

```python
ELO_PER_RANK = 64.0          # KaTrain CALIBRATED_RANK_ELO 기울기
RUNGS = 27                   # 18k..1k, 1d..9d

def p_win(rung, true_rung):  # 사용자가 칸 rung의 봇을 이길 확률
    return 1 / (1 + 10 ** ((rung - true_rung) * ELO_PER_RANK / 400))

def window(p, k, n, cap=400, min_games=0):   # 최근 n판 중 k승이면 승급
    hist = []
    for g in range(1, cap + 1):
        hist.append(random.random() < p)
        if len(hist) > n: hist.pop(0)
        if g >= min_games and sum(hist) >= k: return g
    return None

def ladder(k, n, true_rung, horizon, demote=None):  # 18k에서 시작, horizon판 뒤 (최고 − 실력, 현재 − 실력)
    rung = best = 0; hist = []
    for _ in range(horizon):
        hist.append(random.random() < p_win(rung, true_rung))
        if len(hist) > n: hist.pop(0)
        if sum(hist) >= k and rung < RUNGS - 1:
            rung += 1; best = max(best, rung); hist = []; continue
        if demote:                                   # (dmax, dn): 최근 dn판 중 dmax승 이하면 한 칸 아래
            dmax, dn = demote
            if len(hist) >= dn and sum(hist[-dn:]) <= dmax and rung > 0:
                rung -= 1; hist = []
    return best - true_rung, rung - true_rung
```

- 고정 블록(`block`), 별 규칙(`stars`), 숨은 Elo 게이트(K=24, 여유 32 Elo)도 같은 틀에 있다.
  - 블록: n판 안에 k승이면 승급하고, 못 하면 카운트를 비운다.
  - 별: 이기면 +1, 지면 −1(0 아래로는 안 감), 목표 개수에 닿으면 승급한다.
  - 게이트: 창 규칙에 더해, 숨은 레이팅이 다음 칸 봇 Elo − 32 이상일 때만 승급한다.
