# E5 — 폰에서 사람 모델을 올리면 한 수에 얼마가 드나

**배경**(백로그 #215 단계 ①): 캐릭터가 사람 모델로 두게 하려면 폰에 신경망이 하나 더 올라간다. 리서치의 시간·메모리 숫자는 전부
옛 폰(S22U) 9줄 표본 3개에서 끌어낸 것이라 **신뢰도 낮음**이었다 — 정하기 전에 폰에서 직접 잰다.
같은 측정으로 #218이 넘긴 물음(다시보기 분석을 JSON 단일 질의로 — 분석 프로세스를 하나 더 띄우는 값)과 I-3(분석을 얼마나 깊게 돌릴 수 있나)의 근거도 얻는다.

## 방법

앱이 깔린 폰에서 `adb run-as`로 **앱 안의 KataGo(같은 바이너리·같은 주 모델·같은 cfg)**를 띄워 설정을 바꿔 가며 잰다(`run.py`).

| 설정 | 무엇 |
| --- | --- |
| `main-t1` | **지금 앱의 GTP 프로세스** — 주 모델만, 탐색 스레드 1 |
| `human-t1` · `-t2` · `-t4` | 사람 모델을 같이 올린 GTP 프로세스, 스레드 1 · 2 · 4 |
| `human-t1-buf13` · `human-t4-buf13` | 위 + NN 버퍼를 13줄로(`maxBoardXSizeForNNBuffer`) — 13줄 판만 |
| `gobot-t1` · `gobot-t4` | go-bot 레시피의 한 수(`genmove`): 사람 정책에서 착수 + 주 모델 40방문 |
| `analysis-main` · `analysis-human` | 앱의 JSON 분석 프로세스(1 × 4스레드), 주 모델만 / 사람 모델 같이 |
| `analysis-main+gtp` · `analysis-human+gtp` | 위 + 대국용 GTP 프로세스를 **함께** 띄웠을 때의 메모리 |

- 평가 1회는 `kata-raw-nn`·`kata-raw-human-nn`의 대칭 번호를 돌려 캐시를 피한다. 탐색은 매번 `clear_cache`.
- 시간은 맥에서 `adb` 왕복을 포함해 잰다(왕복 약 2ms — 표에 같이 적는다). 메모리는 `/proc/<pid>/status`의 RSS.
- 사람 프로필은 `rank_5k` 하나로 잰다 — 프로필은 입력 한 줄이라 시간·메모리에 영향이 없다.

## 폰 준비

```sh
adb -s <시리얼> push ~/worksoc/katago/models/b18c384nbt-humanv0.bin.gz /data/local/tmp/human.bin.gz
adb -s <시리얼> shell chmod 644 /data/local/tmp/human.bin.gz
adb -s <시리얼> shell "run-as com.zenit9hub.ai.baduk cp /data/local/tmp/human.bin.gz files/katago/human-b18c384nbt.bin.gz"
adb -s <시리얼> shell rm /data/local/tmp/human.bin.gz
adb -s <시리얼> shell am force-stop com.zenit9hub.ai.baduk     # 앱의 엔진이 같이 돌면 숫자가 섞인다
```

⚠️ 디버그 빌드여야 `run-as`가 된다. 끝나면 `run-as … rm files/katago/human-b18c384nbt.bin.gz`로 지운다(앱은 아직 이 파일을 모른다).

## 실행

```sh

```

## 결론 — `runs/20261005-1942-…-s23`(Galaxy S23 · SM8550 · Android 15 · RAM 7.2GB)

**한 수에 드는 시간**(중앙값)

| 무엇 | 13줄 | 19줄 |
| --- | ---: | ---: |
| 평가 1회 — 주 모델 `kata-raw-nn` | 0.27초 | 0.49초 |
| 평가 1회 — **사람 모델** `kata-raw-human-nn` | **0.29초** | **0.50초** |
| 지금 캐릭터 경로: GTP 16방문(1스레드) | 4.3초 | 7.7초 |
| GTP 32 · 40방문(1스레드) | 8.8 · 11.2초 | 15.4 · 19.4초 |
| GTP 32 · 40방문(4스레드) | 6.3 · 8.2초 | 11.8 · 14.0초 |
| go-bot 레시피 한 수(`genmove`, 40방문) 1 · 4스레드 | 18.4 · 9.5초 | 32.0 · 17.1초 |
| JSON 분석 1방문 — 주 모델만 / 사람 정책까지 | 0.55 / 1.08초 | 0.84 / 1.73초 |
| JSON 분석(4스레드) 영역 포함 16 · 64 · 128방문 | 5.8 · 13.5 · 28.6초 | 9.6 · 19.6 · 42.1초 |

**메모리(RSS)와 뜨는 시간**

| 프로세스 | RSS | 뜨는 시간 |
| --- | ---: | ---: |
| GTP, 주 모델만(지금 앱) | 507~517MB | 1.4초 |
| GTP, 주 + 사람 모델 | **1,003~1,075MB** | 2.5초 |
| JSON 분석, 주 모델만 | 516~550MB | 2.2초 |
| JSON 분석, 주 + 사람 모델 | 1,021~1,068MB | 4.7초 |
| GTP(주) + JSON 분석(주)를 함께 | 508 + 549MB | – |
| GTP(주) + JSON 분석(주 + 사람)을 함께 | 508 + 1,068MB | – |

읽는 법

1. **사람 모델로 두면 한 수가 0.3초(13줄) · 0.5초(19줄)다** — 지금 16방문 4.3 · 7.7초의 1/15. 사람 모델 평가는 주 모델 평가와 값이 같다.
2. **그 대가는 메모리다 — 신경망 하나에 약 500MB.** 주 + 사람을 한 프로세스에 올리면 약 1.0GB. 설정으로는 못 줄인다:
   NN 캐시 2^14 · 배치 1 · 노드 테이블 2^10을 다 걸어도 507 → 482MB(−25MB)였다. NN 버퍼 13줄도 메모리를 줄이지 않는다.
3. **스레드를 늘리면 평가 1회는 오히려 느려진다**(13줄 0.29 → 2스레드 0.30 → 4스레드 0.37~0.40초). 탐색은 32방문부터만 덕을 본다(40방문 11.7 → 8.2초).
   16방문은 4스레드가 덕이 없다(4.9 → 4.6초). ⇒ 평가 1회로 두는 길에는 **1스레드가 맞다.**
4. **NN 버퍼를 13줄로 줄여도 이득이 없다** — 연달아 번갈아 잰 대조(`runs/…-s23-ab*`)에서 0.297 → 0.290초(2%). Eigen은 이미 실제 판 크기로 돈다
   (평가 1회가 13줄 0.27초 · 19줄 0.49초로 판 넓이를 따라간다 — 리서치의 「버퍼 크기로 돈다」는 추정은 틀렸다).
5. **32 · 40방문은 S23에서도 한 수 8~20초다** — 앱의 기본 최대 탐색 시간(5초)에 들지 않는다. go-bot 레시피를 그대로 쓰는 것(40방문 `genmove`)도 9.5~32초라 폰에서는 못 쓴다.
6. **사람 정책을 JSON 분석 프로세스로 받는 길은 두 배 느리고(1.08초) 프로세스가 하나 더 뜬다** ⇒ 대국 프로세스에서 `kata-raw-human-nn`으로 받는 길이 싸다.
7. **분석 프로세스를 하나 더 띄우면 +0.5GB다**(#218이 넘긴 물음). 16방문 + 영역 한 질의는 5.8초(13줄) — 지금 다시보기의 형세 보기(평가 1회 0.27초)보다 느리다.
8. 깊은 분석(I-3)의 값: 64방문 13~20초, 128방문 29~42초.

**RAM 2GB 에뮬레이터**(`runs/…-emu2g-*`): 주 + 사람 모델이 올라가기는 한다(뜬 직후 RSS 1,003MB). 그러나 뜨는 데 14.9초(주 모델만 8.3초), 일한 뒤 RSS가 375MB로 내려가 있고
(나머지는 스왑으로 밀렸다) 평가 1회가 1.19 → 1.61초로 느려졌으며, 그사이 시스템이 다른 앱을 줄줄이 내렸다(`lowmemorykiller`). 앱 화면 프로세스 없이 엔진만 띄운 값이다.

## 덧붙임(2026-10-05 밤) — 신경망을 갈아 올리는 값과 「첫 `boardsize` 1.2초」

구조가 「한 번에 하나만」으로 정해진 뒤(#215), 사람 모델만 올린 프로세스와 갈아 올리기를 같은 폰에서 손으로 쟀다(스크립트 밖 — 표본 3~4개).

- **사람 모델만 올린 프로세스**(`-model`에 사람 모델): 뜨는 데 1.49초 · RSS 510MB · 평가 1회 0.27초(13줄) · 프로필 바꾸기 1.4ms. 주 모델 하나와 같다.
- **갈아 올리기**(내리기 → 새로 뜨기 → 40수 맞추기 → 첫 평가): 내리기 0.06초 · 뜨기 1.35~1.41초 · **맞추기 1.3초** · 첫 평가 0.28초 = **약 3.0초.**
- 맞추기 1.3초의 정체는 수순이 아니었다 — **새 프로세스의 첫 `boardsize 13` 하나가 1.23초**다(그 뒤로는 `boardsize`·`komi`·`clear_board` 1~2ms, `play` 40수 합계 45~50ms).
  KataGo는 19줄로 뜨고, 다른 크기로 처음 바꿀 때 한 번 다시 준비한다(19줄 판은 2ms, 9줄 판은 1.29초).
- **띄울 때 `defaultBoardSize`를 판 크기로 주면 그 값이 사라진다**: 첫 평가까지 13줄 2.98 → **1.64초**, 9줄 2.82 → 1.53초. 틀린 크기를 주면 도로 1.29초를 낸다.
  ⇒ 앱은 판 크기를 알면 그 크기로 띄운다(`buildGtpCommand`의 `defaultBoardSize`). 갈아 올리기만이 아니라 **새 대국마다**(프로세스를 새로 띄운다) 13줄·9줄에서 약 1.2초가 준다.

## 한계

- 폰 한 대(S23, 플래그십). 4GB급 실기가 없다 — 2GB 에뮬레이터는 메모리 압박의 모양만 보여 준다(속도는 맥 CPU라 참고 불가).
- **오래 돌리면 느려진다**: 본 측정 후반(4스레드 탐색 직후)에는 같은 1스레드 평가가 0.29 → 0.41초(약 1.4배)였다. 표의 값은 설정마다 8초 쉬며 잰 것이고, 탐색 표본은 2개씩이다.
- 평가 1회는 캐시를 피하려 대칭 번호를 돌렸다 — 실제 대국의 한 수는 대칭을 무작위로 하나 쓴다(값은 같다).
- 시간에는 `adb` 왕복(1~2ms)이 들어 있다.
