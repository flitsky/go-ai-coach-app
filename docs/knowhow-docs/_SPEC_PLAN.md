# 1. 스펙 문서 운영 원칙 및 각주 작성 규칙

스펙 문서는 처음 작성된 기획으로 끝나지 않고 개발 과정에서 지속적으로 진화하는 살아있는 문서(Living Document)입니다.

### 핵심 운영 원칙

1. **절 번호의 안정성**: 백로그가 `참고: 스펙 3.2절` 형태로 가리키므로, 대규모 구조 변경이 아니면 기본 절 번호 체계를 유지합니다.
2. **단방향 지식 역류**: AI 스레드가 코드를 작성하며 내린 아키텍처 판단과 버린 대안은 백로그가 아니라 **반드시 스펙 문서의 해당 절 아래 각주로 역류**시킵니다.
3. **각주는 append-only, 본문은 필요하면 개정한다**: 이미 작성된 각주는 수정하거나 지우지 않고 시간 순으로 덧붙입니다 — 그게 "그때 왜 그렇게 판단했는가"의 히스토리이기 때문입니다. 다만 이건 스펙 **본문**(요구사항, 정책표 등)까지 절대 수정하지 말라는 뜻은 아닙니다 — 요구사항 자체가 바뀌면 본문은 새 내용으로 갱신하되, 옛 각주는 지우지 않고 "본문이 재확정됐다"는 새 각주를 덧붙여 왜 바뀌었는지를 남깁니다.

---

### 📌 구현 결정 각주(Footnote) 작성 공식

각주는 단순한 작업 일지가 아닙니다. "다음 AI 스레드가 똑같은 비효율적 대안을 다시 검토하지 못하게 막는 방어벽"입니다.

```markdown
> 구현 결정(백로그 #N, YYYY-MM-DD):
> 1. [선택한 방식]: 실제로 채택한 인터페이스/로직/설계
> 2. [버린 대안과 이유]: 검토했으나 배제한 방식과 그 기술적/도메인적 사유 (★ 가장 중요)
> 3. [영향 및 후속 주의점]: 다음 일감(#M)이나 타 모듈이 주의해야 할 부수효과
```

이 3항목은 **고정된 서식이 아니라 점검 체크리스트**입니다 — 매번 정확히 세 줄을 채우라는 뜻이 아니라, 좋은 각주라면 이 세 가지를 놓치지 않는다는 뜻입니다. 배제한 대안이 여러 개면 항목을 늘리고, 후속 영향이 없으면 3번은 생략해도 됩니다.

#### 실제 각주 작성 예시

> **구현 결정 (백로그 #12, 2026-08-24)**:
> 1. **선택**: 소모품 차감 우선순위 판정을 `decideConsumableSpend` 순수 함수로 분리했다.
> 2. **버린 대안과 이유**: 기존 `FeatureAccessPolicy.resolve()` 내부에 차감 로직을 합치는 안을 검토했으나 기각했다 — `resolve()`는 부수효과 없는 조회 함수라 화면 렌더링 중에도 호출되는데, 여기에 자원 소모를 넣으면 "확인만 했는데 재고가 닳는" 구조가 된다.
> 3. **영향**: "이미 쓸 수 있는가" 판정은 기존 `resolve()`에 위임해, 프리미엄·영구 클레임 정책이 두 군데로 갈라지지 않게 했다.

각주에는 **실제로 존재하는(또는 이번에 실제로 만든) 함수/클래스 이름만** 씁니다. 아직 만들지 않은 클래스를 그럴듯하게 지어내 예시로 넣으면, 다음 스레드가 그게 실재한다고 믿고 코드를 찾다가 시간을 씁니다.

# 3. SPEC_PLAN과 SPEC_BACKLOG의 유기적 상호작용 요약

두 문서는 아래와 같이 완벽히 결합되어 동작합니다:

```
[SPEC_PLAN.md]                                [SPEC_BACKLOG.md]
4.1절 (상세 스펙) ◄────────── 포인터 참조 ────────  #13 일감 ("참고: 스펙 4.1절")
│                                                  │
│                                             [AI 스레드 작업]
│                                                  │
4.1절 각주 역류 ◄────── 버린 대안 및 결정 기록 ────────────┘
("> 구현 결정(#13): ...")
```

1. **백로그(BACKLOG)**는 스펙의 내용을 복제하지 않고 오직 **절 번호(`참고: 스펙 4.1절`)**만 가리킵니다.
2. **AI 스레드**는 해당 절을 읽고 작업을 수행합니다.
3. 작업 중 발생한 의사결정과 버린 대안은 **스펙(PLAN)의 해당 절 밑에 각주**로 남겨져 영구적인 설계 히스토리가 됩니다.
4. 백로그의 일감에는 **"스펙 4.1절 각주 참고"**라는 한 줄 포인터만 남겨 문서를 슬림하게 유지합니다.
