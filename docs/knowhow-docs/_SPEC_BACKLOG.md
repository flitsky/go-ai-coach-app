# 단일 문서 백로그 방법론 — AI 스레드 실행 및 보고 정합성 표준 가이드

작성일: 2026-08-24

---

## 1. 개요 및 핵심 가치

새로 열린 AI 대화 스레드는 직전 스레드의 설계 결정과 맥락을 알지 못합니다(Cold Start). 사람이 매번 맥락을 구두로 설명하면 편차가 생기고, 특히 "왜 그렇게 구현하지 않았는가(버린 대안)"가 유실되어 같은 헛발질을 반복합니다.

이 방법론은 **컨텍스트 유지를 사람이 아닌 문서(Markdown)가 흡수**하도록 설계된 개인 작업 실행 표준입니다.

```
[조직 레벨 : 매크로 관리]   이슈 트래커 (Jira / Linear / GitHub Issues, 있다면)
                                         │  ▲
              할당된 Task / Story 단위 수신 │  │ 보고 데이터 동기화 (6장)
                                         ▼  │
[개인 레벨 : 마이크로 실행]   _SPEC_PLAN.md (스펙)  +  _SPEC_BACKLOG.md (실행)
                                         │  ▲
                     고정 프롬프트 1줄 주입 │  │ [완료] 상태, 산출물, 결정 각주 반환
                                         ▼  │
[AI 스레드 : 순차 실행]     AI 코딩 에이전트 (Claude / Cursor / Windsurf 등)
```

### 핵심 가치

1. **팀 트래커 하위의 개인 실행 엔진**: 팀 이슈트래커가 있다면 그 배분·조율은 그대로 거기서 하고, 이 방법론은 그 아래 — 한 사람이 할당받은 일감을 AI 스레드로 실행하는 과정 — 을 맡습니다.
2. **다중 프로젝트 컨텍스트 보존**: 프로젝트마다 문서 쌍을 두면, 다른 프로젝트를 오가도 백로그를 여는 즉시 작업 지점이 복구됩니다. 문서 하나가 자기 완결적이라는 설계에서 따라 나오는 결과입니다.
3. **보고 데이터 재사용**: 백로그의 완료 메타데이터(산출물, 커밋 해시, 결정 근거)를 그대로 복사해 일일/주간 보고 원본으로 쓸 수 있습니다.

### 적용 경계

- **맞는 경우**: AI 스레드가 주 실행 주체 · 한 사람(스레드)이 순차 진행 · 항목 간 판단이 서로 전제가 되는 작업 · 다중 프로젝트 컨텍스트 전환.
- **안 맞는 경우**: 여러 사람이 동시에 같은 백로그의 다른 항목을 진행(그 조율은 상위 트래커의 몫) · 항목이 서로 독립적인 작업 · 실시간 대시보드가 필요한 보고.

## 2. 문서 아키텍처 및 네이밍 규칙

동일 디렉터리 내에 접두사를 일치시킨 두 개의 세트 문서(Twin Documents)로 관리합니다.

| 파일명 규칙 | 역할 | 수명 및 성격 | 핵심 규칙 |
| --- | --- | --- | --- |
| **`[기능명]_SPEC_PLAN.md`** | **Why / What**<br><br>(설계 원본, 아키텍처) | 영구 보존<br><br>(Living Document) | • 설계 변경 및 버린 대안은 이 문서에 **각주(Footnote)**로 역류시켜 영구 자산화한다. |
| **`[기능명]_SPEC_BACKLOG.md`** | **Who / When / Status**<br><br>(순차 일감, 실행 상태) | 트랙 단위<br><br>(Ephemeral) | • **스펙을 다시 쓰지 않는다.** 스펙 문서의 절 번호(예: `4.2절 참고`)만 참조 포인터로 둔다. |

## 3. Git 라이프사이클: 격리 커밋과 무결성 푸시

작업 단위의 변경 사항이 뒤섞이는 것을 방지하고 원격 브랜치의 무결성을 보장하기 위해, 커밋 단위가 항목 단위와 겹치는 게 자연스러운 상황에서는 커밋과 푸시 주기를 분리합니다.

```
[단위 일감 승인] ──► [로컬 커밋 (즉시)] ──► [리뷰 / 로컬 테스트] ──► [원격 푸시 (마일스톤)]
                           │                            │
                           └─ (필요시 amend 보완) ───────┘
```

1. **단위 일감 완료 즉시 로컬 커밋**: 백로그 1개 항목이 완료 승인되면 즉시 커밋합니다 (`feat(scope): ... (backlog #N)`). 다른 일감과 변경점이 섞이는 것을 차단합니다.
2. **원격 푸시는 검증 후 일괄 수행**: 푸시는 일감마다 하지 않고, 유의미한 기능 단위가 묶이고 로컬 전체 테스트가 통과된 시점에 수행합니다.
3. **푸시 전 완결성 보완**: 푸시 전 로컬 리뷰 과정에서 발견된 사소한 누락은 `git commit --amend` 등을 활용해 보완함으로써 원격 저장소에는 결함 없는 커밋만 반영합니다. **아직 푸시하지 않은 로컬 커밋에만** 씁니다 — 이미 푸시된 커밋을 amend하지 않습니다.

⚠️ 항목 여러 개가 같은 파일을 함께 건드리면 이 리듬대로 항목마다 쪼개 커밋하기 어렵습니다 — 그럴 땐 억지로 분리하지 말고 관련 항목들을 하나의 커밋으로 묶으세요. 이 리듬은 항목들이 서로 다른 파일에서 독립적으로 완결될 때 가장 잘 맞습니다.

## 4. 실전 운영 핵심 규칙

1. **번호(#N)는 불변 식별자, 실행 순서는 목록의 줄 위치**
* 번호는 커밋 및 스펙 각주와 연결되므로 절대 재부여하지 않습니다. 우선순위가 바뀌면 `예정사항` 목록 내에서 항목의 줄 위치만 위아래로 이동합니다. AI는 항상 최상단 1개만 집습니다. 번호는 섹션마다 새로 시작하지 않고 문서 전체를 통틀어 하나의 연속된 시퀀스입니다.

2. **완료 항목 불변 원칙**
* 이미 완료된 일감의 방향이 바뀌더라도 기존 완료 기록을 고치지 않고 새 일감(예: `#16. #8 로직 개편`)을 발행합니다.

3. **버린 대안은 스펙 각주로 역류**
* "A 대신 B를 선택한 이유", "검토 후 기각한 방식"은 백로그가 아닌 스펙 문서에 `> 구현 결정(#N):` 형식의 각주로 남깁니다. 다음 AI 스레드가 동일한 비효율적 대안을 제시하는 것을 방어합니다.

4. **엄격한 스코프 통제**
* AI 특유의 "이왕 하는 김에 리팩토링"을 금지합니다. 지정된 스펙 절의 요구사항만 정확히 구현합니다.

5. **비정상 중단 복구 프로토콜**
* 새 스레드 시작 시 백로그에 `[진행중]` 항목이 남아있다면, 직전 스레드가 중단된 상태입니다. 코드를 이어 작성하기 전에 `git status` 및 `git diff`로 워킹 트리를 먼저 진단합니다.

6. **완료는 사람 승인 후에만**
* AI 스레드는 스스로 일감을 완료로 표시하지 않습니다. 산출물을 검증하고 사용자가 승인한 뒤에만 [완료 사항]으로 옮깁니다. 이 게이트가 없으면 문서가 "다 됐다"고 스스로 주장하는 상태로 흘러갑니다.

7. **착수 전 확인 필드로 제품 결정을 가둔다**
* 가격, 콘텐츠, 정책처럼 AI가 대신 정하면 안 되는 것은 항목의 `착수 전 확인(사용자):` 필드에 미리 적어 둡니다. 스레드는 그 시점에 반드시 사용자에게 확인한 뒤에만 진행합니다.

8. **노력정도 예상 → 실제를 기록한다**
* 완료 시 `노력정도: 중간 → 실제: 높음`처럼 실제 소요를 덧붙입니다. 이 기록이 쌓이면 다음 일감을 쪼갤 때의 분할 감각이 좋아집니다.

## 5. 이식용 표준 템플릿: `[기능명]_SPEC_BACKLOG.md`

새 프로젝트나 트랙을 시작할 때 아래 템플릿을 복사하여 사용합니다. 고정 프롬프트가 상단에 내장되어 있어 복사 후 즉시 실행이 가능합니다.

```markdown
# [기능/트랙명] 개발 일감 백로그

- 참조 스펙: [기능명]_SPEC_PLAN.md
- [선택] 매크로 이슈 키: <조직 트래커를 쓴다면 그 키>
- 검증 명령: ./gradlew test (또는 npm test) — 환경 함정이 있으면 여기 반드시 적는다.

---

## 1. 신규 스레드 착수 프로토콜

> **[고정 프롬프트] 매 스레드 시작 시 아래 한 줄을 복사하여 주입하세요:**
> 이번 스레드에서는 `[경로]/[기능명]_SPEC_BACKLOG.md` 파일의 '예정사항' 최상단(첫 번째) 항목을 파악하여 수행하세요. 항목과 연계된 스펙 절을 숙지한 뒤 작업을 진행하고, 결과물 검증 후 사용자가 승인하면 백로그 문서를 완료 상태로 갱신하고 스레드를 종료하세요.

### 스레드 실행 순서
1. **읽기**: 백로그와 연계 스펙의 해당 절 번호를 확인한다.
2. **진행 상태 점검**: `진행 중`이 `(없음)`인지 확인한다. 기존 항목이 남아있다면 `git status`/`git diff`로 워킹 트리를 먼저 점검한다 — 직전 스레드가 중단됐다는 신호일 수 있다.
3. **작업 및 질의**: 지정된 스펙 범위만 작업한다. `착수 전 확인:` 질문이 있다면 사용자에게 확인 후 진행한다.
4. **결정 역류**: 중요한 아키텍처 판단 및 버린 대안은 스펙 문서에 `> 구현 결정(#N):` 각주로 기록한다.
5. **완료 갱신**: 사용자 승인 후에만 일감을 [완료 사항]으로 옮기고 산출물과 커밋 메시지를 기입한다.
6. **다음 안내**: 다음 예정 항목 번호만 간략히 브리핑하고 마친다.
```

## 6. 조직 보고(Daily / Weekly) 연계 가이드

백로그의 구조화된 `완료 사항` 필드는 별도의 회상이나 가공 없이 조직 보고 텍스트로 옮길 수 있습니다.

```
[백로그 완료 메타데이터]              [보고 텍스트 매핑]
- 연계 이슈                       ──►  이슈 번호 매핑
- 산출물 / 비고                   ──►  주요 개발 실적 및 특이사항
- 구현 결정                       ──►  아키텍처 의사결정 요약
- 커밋                           ──►  PR 및 Git 변경 증빙
```

* **일일 스크럼/보고**: 최근 완료된 항목 1~2개의 `산출물`과 `비고`를 복사하여 진행 상태로 공유합니다.
* **주간/월간 보고**: 한 주간 축적된 완료 항목들을 취합하여 완료 태스크 목록 및 스펙 각주의 `구현 결정`을 아키텍처 성과로 제출합니다.
* **데이터 아카이빙**: 보고서나 이슈트래커에 동기화가 완료된 오래된 완료 항목은 백로그에서 압축하거나 삭제해도 무방합니다(Git 히스토리 및 트래커가 영구 보관).

## 7. 향후 개선 과제

1. **완료 항목 압축 임계값 설정**: 백로그 라인 수가 늘어날 때 오래된 완료 항목을 압축하는 구체적 기준(예: N개 초과 시 압축, 상세는 git 히스토리에 위임)이 아직 없습니다.
2. **노력정도 추정 보정**: 규칙 8의 `예상 → 실제` 기록이 쌓이면, 그 데이터로 다음 일감을 쪼갤 때의 최적 분할 단위를 다시 정리합니다.
3. **조직 보고 연계(6장)의 실전 검증**: 구조화된 필드가 보고 원본이 된다는 메커니즘은 서 있지만, 실제 트래커에 몇 주 연계해 본 뒤 문구·주기를 다시 다듬어야 합니다.
