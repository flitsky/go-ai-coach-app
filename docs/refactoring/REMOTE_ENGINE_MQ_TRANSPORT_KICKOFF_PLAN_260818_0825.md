# 원격 엔진 MQ 전환 + 피어 신뢰 모델 킥오프 계획서

작성 시각: 2026-08-18 08:25 (KST)

상태: **결정 문서. 아직 착수하지 않았다.** 사용자가 명시적으로 "당장 착수하기보다는 방향을 결정한 뒤 문서화"를 요청했다 — 이 문서는 그 결정과 근거를 기록한다. 실제 구현은 별도 승인 후 진행한다.

이 문서는 `LAYERED_ARCHITECTURE_REFACTORING_PLAN_260803_1500.md` Stage F(물리적 분산·DePIN)의 전용 킥오프 문서다 — 그 계획서 F-2가 "연산 마켓플레이스는 부정사용 방지·정산 문제를 동반하니 착수 시점에 전용 킥오프 문서를 새로 쓰라"고 미리 정해뒀고, 오늘 사용자가 제시한 설계(가장 빠른 응답자에게 보상 점수 지급)가 정확히 그 지점에 해당한다.

## 1. 오늘 보고된 버그 — 근본 원인

에뮬레이터에서 대국 시작 시 "엔진 응답 지연" 팝업이 바로 떴다. 원인은 단순하다: 어제 Stage E-3 검증 때 `local.properties`의 `debug.remoteEngineUrl`을 켜둔 채로 세션을 마쳤고, 검증에 쓴 맥북 참조 서버(`scripts/run-katago-remote-analysis-server.py`)는 이미 꺼져 있었다. 지금 배선(`MainActivity.kt`)은 **엔진 클라이언트를 앱 시작 시점에 한 번만** 원격/로컬 중 선택한다 — 서버가 있는지 없는지는 그 시점에 확인하지 않고, 있다고 가정하고 원격으로 고정한다. 이후 모든 엔진 호출(`genMove`/`analyze`/`estimateScore`)이 죽은 서버로 나가 `connectTimeoutMillis=3000`/`readTimeoutMillis=30000`(최대 33초) 뒤에야 실패하고, 그 실패가 "느린 로컬 엔진"과 구분 없이 같은 지연 팝업으로 보인다.

**즉시 조치**: `local.properties`의 `debug.remoteEngineUrl`을 주석 처리해 껐다(이 파일은 개인 로컬 설정이라 git에 안 잡힌다 — 다시 테스트하려면 주석만 풀면 된다). 근본 해결은 "턴 단위로 원격 실패를 감지해 그 즉시 로컬로 병행/전환"하는 것인데, 이게 정확히 오늘 사용자가 요청한 재설계(4절)와 같은 작업이라 이번 킥오프에 포함해 같이 설계한다 — HTTP 버전에만 임시로 패치하고 MQ 버전에서 다시 만드는 이중 작업을 피한다.

## 2. 오늘 요청 정리

1. **버그**: 원격 우선 상태에서 서버가 꺼져 있으면 지연 팝업이 뜬다 — 런타임에 감지해서 우회해야 한다.
2. **전송 계층**: HTTP 대신 MQ로 전환 — 컴퓨터↔실물폰뿐 아니라 **실물폰↔실물폰**도 지원해야 한다.
3. **개발자 토글(중요, 필수)**: 앱에 "개발자 테스트" 모드를 만들고 그 안에 **"원격 엔진 연결 우선"** 토글을 넣어, 빌드 없이 런타임으로 켜고 끌 수 있어야 한다(지금의 `BuildConfig`/`local.properties` 방식은 컴파일 타임 고정이라 이 요구를 못 채운다).
4. **개발 순서 최종 판단**: 맥북에서 파이썬으로 최대한 고도화한 뒤 앱으로 이식하는 방향을 고려하라는 강한 힌트 + "앱 개발자 기능으로 개발할지 / 맥북 테스트 서버로 먼저 구축할지" 결정 요청.
5. **초안 설계**(당장 착수 대상 아님, 방향성 입력):
   - 게임 세션 ID로 전용 토픽을 만들어 그 토픽으로 요청/응답을 주고받는다.
   - 첫 3수는 로컬 엔진으로도 분석해 원격 응답과 무결성(정합성) 체크를 한다.
   - 엔진레이어↔앱레이어 통신은 "와이어링"으로 추상화해, MQ 외 다른 전송 수단이 추가돼도 무리 없게 한다.
   - 응답이 여러 개 오면(여러 원격 후보가 동시에 답한 경우) 서로 정합성을 체크한다.
   - "최대 탐색 시간 제한"(Off면 30초) 안에 원격 응답이 없으면 원격을 "연결 불가"로 전환하되, 로컬 분석은 계속하고 원격 요청 발행도 계속 병행한다.
   - 세션 ID 단일 토픽은 요청/응답 메시지에 타임스탬프가 자연히 남는다 — 나중에 가장 빠른 응답자 3명에게 순위별 보상 점수(5/3/2/1점)를 줄 때 이 이력을 그대로 쓴다.
   - 보드 화면에 원격/로컬 엔진 구동 상태를 색으로 구분해 표시(원격 응답 수신 시 연한 강조색 "원격 엔진 구동중", 평소엔 진한 회색 "로컬 엔진 구동중").

## 3. 기존 아키텍처 확인 — "와이어링 추상화" 요구는 이미 충족돼 있다

3번 요구(엔진레이어↔앱레이어 통신을 와이어링으로 추상화)는 좋은 소식이 있다 — **이미 그렇게 돼 있다.** `shared/RemotePositionAnalysisTransport.kt`/`RemoteEngineOperationTransport`는 처음부터 "요청을 어떻게 실어 나르는지"를 트랜스포트 인터페이스로 분리해뒀고, 지금 있는 `HttpRemoteEngineOperationTransport`는 그 인터페이스의 구현체 "중 하나"일 뿐이다. MQ로 옮기는 작업은 원칙적으로 **같은 인터페이스의 새 구현체(`MqttRemoteEngineOperationTransport`, `FirestoreRemoteEngineOperationTransport` 등)를 하나 더 만드는 일**이지, 계층 구조 자체를 바꾸는 일이 아니다. `EngineCoreApiFactory`에 선택지를 하나 추가하면 된다.

단, 4절의 "여러 응답 정합성 체크"·"타임아웃 시 로컬+원격 병행"은 **지금 인터페이스로는 안 된다** — `RemoteEngineOperationTransport.execute()`는 정확히 응답 1개를 돌려주는 단발 요청-응답 계약이라, "여러 응답을 모아서 비교"하거나 "로컬과 원격을 동시에 돌리다가 먼저 끝나는 쪽을 쓰기"는 새 계약이 필요하다. 이건 여기서 확정하지 않고 5절 실험으로 넘긴다.

## 4. 전송 수단 비교 — MQTT vs Firestore vs 기타

사용자는 "MQ"라고 표현했지만, 실제 요구사항(세션 스코프 토픽, 메시지 이력이 곧 감사로그, 컴퓨터/폰 어디서나 접속)을 만족하는 후보는 전통적 메시지 브로커만이 아니다. 넷을 검토했다.

| 후보 | 컴퓨터↔폰 | 폰↔폰 | 메시지 이력(보상 감사로그) | 기존 인프라 | 운영 부담 |
| --- | --- | --- | --- | --- | --- |
| **MQTT**(Mosquitto 자체 호스팅 또는 HiveMQ Cloud/EMQX Cloud 무료 티어) | 좋음 — 모바일/IoT 표준 프로토콜, QoS로 전달 보장, 배터리 효율적 | 좋음 — 브로커를 매개해서 통신하므로 두 폰이 직접 연결 안 해도 됨(NAT/방화벽 문제 없음) | **기본 없음** — pub/sub은 휘발성이라 이력을 보려면 브로커 로그나 별도 DB에 직접 적재해야 함 | 새 인프라(브로커 계정/호스팅) 필요 | 관리형 서비스면 낮음, 자체 호스팅이면 있음 |
| **Firebase Firestore**(실시간 리스너) | 좋음 | 좋음 — 리스너 기반이라 역시 NAT 문제 없음 | **기본 제공** — 문서 자체가 타임스탬프 있는 로그. 추가 설계 없이 요구사항 5번(보상 감사로그)을 그대로 만족 | **이미 있음** — 이 앱은 이미 Firebase Auth(Google/Email)를 쓰고 있어 SDK/설정이 이미 연결돼 있다 | 낮음(이미 쓰는 서비스, 별도 브로커 운영 불필요) |
| RabbitMQ(AMQP) | 가능하지만 모바일 클라이언트 라이브러리가 무겁고 흔치 않음 | 가능 | durable queue로 가능하지만 설계 필요 | 새 인프라 필요 | 높음(직접 운영 시) |
| Redis Pub/Sub | 가능 | 가능 | 없음(Pub/Sub이 아니라 Streams를 따로 써야 이력이 남음) | 새 인프라 필요 | 중간 |
| Kafka | 과함 | 과함 | 있음 | 매우 무거움, "세션마다 새 토픽"이라는 모델과 안 맞음(파티션 설계가 정반대 용도) | 매우 높음 |

**1차 판단**: Firestore가 의외로 강력한 후보다 — "MQ" 자체가 목적이 아니라 "세션 스코프 pub/sub + 메시지 이력이 곧 감사로그"가 진짜 목적이라면, Firestore 실시간 리스너가 그 요구사항을 이미 있는 인프라로 정확히 만족시킨다(문서 = 메시지이자 로그, 컬렉션 = 토픽). MQTT는 "진짜 pub/sub 프로토콜"이라는 점에서 더 표준적이지만, 이력을 보상 근거로 쓰려면 별도로 어딘가에 적재하는 설계를 얹어야 한다 — 그 "별도 적재"가 결국 Firestore 같은 문서 DB가 될 가능성이 높다. 즉 MQTT를 택해도 감사로그용으로 Firestore(또는 유사 DB)를 결국 같이 쓰게 될 공산이 크다.

**이번 문서에서 최종 확정하지는 않는다** — 이건 정확히 "먼저 파이썬으로 두 방식을 다 흉내내보고 비교해야 하는" 종류의 결정이라 5절로 넘긴다. 다만 후보를 이 둘로 좁히는 것까지는 이번에 결정한다: RabbitMQ/Redis/Kafka는 이 앱 규모와 요구사항(1인 개발, 세션당 짧은 토픽 다수, 모바일 클라이언트, 이미 있는 이력 요구)에 비해 과하거나 이력 요구를 못 채워서 제외한다.

## 5. 최종 판단: "앱 개발자 기능" vs "맥북 파이썬 서버 먼저" — **맥북 파이썬 먼저**

**결정**: 사용자가 강하게 시사한 대로, **맥북에서 파이썬으로 먼저 고도화하고 검증한 뒤 앱으로 이식한다.** 근거:

1. **오늘 비교(4절) 자체가 아직 실험이 필요한 열린 질문이다.** MQTT vs Firestore 중 뭐가 세션 토픽 수명 관리·재연결·정합성 체크에 실제로 더 잘 맞는지는 코드를 짜보기 전엔 모른다. 두 후보 다 Python SDK가 있다(`paho-mqtt`, `google-cloud-firestore`) — 맥북에서 3개 프로세스(컴퓨터 역할 1개 + 폰 역할 흉내 2개)를 띄워 실제로 세션 토픽을 만들고, 메시지를 주고받고, 정합성 체크 로직을 돌려보는 게 Android 빌드+에뮬레이터 사이클보다 압도적으로 빠르다 — 오늘 오전 `run-katago-remote-analysis-server.py`를 만들 때도 이 방식이 효과적이었다.
2. **"여러 응답 정합성 체크"·"로컬+원격 병행 폴백" 로직 자체가 새 설계라 버그가 나기 쉽다.** 이런 동시성/타임아웃 로직은 Kotlin coroutine + Android 생명주기 안에서 처음부터 디버깅하는 것보다, 순수 Python으로 로직만 먼저 검증하고 나서 이식하는 편이 훨씬 안전하다.
3. **오늘 버그(1절)가 정확히 "검증 없이 앱에 먼저 배선했을 때의 위험"을 보여준다.** HTTP 스파이크도 결국 똑같이 "일단 앱에 배선"부터 했고, 그 결과가 오늘의 팝업이다. 같은 실수를 MQ에서 반복하지 않는다.
4. 5점/3점/2점/1점 같은 **보상 점수·정산 로직은 특히 되돌리기 어렵다** — 실제 사용자 데이터가 아니라 맥북에서 시뮬레이션한 세션들로 먼저 "5명이 동시에 답했을 때 순위가 실제로 타임스탬프대로 매겨지는가" 같은 걸 확인하는 게 안전하다.

**따라서 앱 쪽(개발자 토글 UI, `EngineCoreApiFactory`에 새 transport 추가 등)은 이번 킥오프에서 착수하지 않는다.** 6절의 파이썬 프로토타입이 어느 정도 안정된 뒤, 별도 승인을 받고 이식 단계로 넘어간다. 단, "원격 엔진 연결 우선" 개발자 토글 자체는 이식 단계의 **필수 요구사항으로 이 문서에 못박아 둔다** — HTTP 스파이크처럼 컴파일 타임 고정 방식으로 다시 만들지 않는다.

## 6. 다음 단계 (승인 시 착수할 파이썬 프로토타입)

1. **세션 토픽 흉내내기**: `scripts/`에 3개 역할(요청자 1, 원격 후보 1~2)을 흉내내는 소형 파이썬 스크립트를 MQTT와 Firestore 두 방식으로 각각 만들어, "세션 ID로 토픽/컬렉션 생성 → 요청 발행 → 응답 수신 → 타임스탬프 기록"이 실제로 되는지 확인.
2. **정합성 체크 로직 실험**: 오늘 이미 만든 `run-katago-candidate-refine-experiment.py`/`run-katago-remote-analysis-server.py`의 KataGo 호출 코드를 재사용해, "로컬 3수 분석 결과"와 "원격 응답"을 비교하는 로직을 프로토타입 — KataGo는 같은 국면이라도 nondeterminism(스레드 경쟁, 배치 처리 순서)으로 완전히 같은 수치가 안 나올 수 있어, **정확히 같음이 아니라 허용 오차 기반 비교**가 맞는지부터 검증해야 한다.
3. **타임아웃+병행 폴백 시뮬레이션**: 원격 후보를 일부러 늦게/응답 안 하게 만든 시나리오에서, "로컬 계속 진행 + 원격 요청 계속 발행"이 실제로 매끄러운지(예: 원격이 뒤늦게 응답했을 때 이미 로컬로 착수된 수와 충돌하지 않는지) 확인.
4. **세션 토픽 정리(TTL) 정책 결정** — 오늘 초안에 없던 항목: 대국마다 새 토픽/컬렉션이 쌓이므로, 대국 종료 후 언제까지 보관할지(보상 정산에 필요한 기간만큼?) 정해야 한다.
5. 위가 안정되면 → **개발자 토글 UI + MQ/Firestore transport 이식**을 별도 승인받아 진행.
