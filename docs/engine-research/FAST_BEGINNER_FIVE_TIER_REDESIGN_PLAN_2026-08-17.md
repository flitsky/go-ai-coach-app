# 빠른 초급 5단계 재정립 계획

작성일: 2026-08-17
갱신: 2026-08-18 — 사용자 승인 + 추가 요구사항 반영 후 구현 착수. 11절에 확정된 최종 설계(원래 5/7절이 제안했던 "누적 상태 추적 방식"보다 더 단순하고 안전한 무상태 방식으로 교체)와 오늘 함께 확정된 결정사항을 기록한다. 5/7절은 검토 과정 기록으로 그대로 남기고 지우지 않는다.

상태: **구현 완료(2026-08-18), 빌드/테스트 검증 중.** 11절부터 읽는 것을 권장한다 — 5~7절은 검토 당시 두 가지 설계안을 비교한 과정이고, 실제 구현은 11절의 최종안을 따랐다.

## 배경

`빠른 초급`(GTP fast, B16)의 현재 1~3단계를, 후보수 분류 기반의 5단계(`초보`~`초고수`, 친근하고 직관적인 표현)로 확장 재정립해달라는 요청. 요청에 포함된 구체 기준:

1. 후보수를 최적수/중급수/최하수 3개 버킷으로 분류하는 규칙(초안 제시됨)
2. 5단계 각각의 버킷별 착수 비율(초안 제시됨) — 분류명은 방향성만 따르고 더 나은 인덱스로 정리
3. 대국 전체에 걸쳐 최하수를 먼저 채우고 중급수/최적수를 후반에 채우는 배치 전략 — 스타일(초반 실수·후반 정리) + 실무(후보 부족으로 비율을 못 맞추는 문제 완화) 두 가지 목적

## 1. 더블체크 — 현재 빠른 초급 1~3단계는 정확히 어떻게 동작하는가

질문하신 두 가지 모두 **맞다.** `shared/PlayLevel.kt:72-76`의 `PlayLevelGroup.FastBeginner.selectionPolicy()`:

```kotlin
FastBeginner -> when (safeLevel) {
    1 -> MoveSelectionPolicy.PercentileRange(70, 100, "탐색 후보 최하위 30%")
    2 -> MoveSelectionPolicy.PercentileRange(40, 70, "탐색 후보 중위 40~70%")
    else -> MoveSelectionPolicy.BestOnly
}
```

- **1단계**: 엔진이 반환한 scored 후보를 order(0=최상위)로 정렬한 뒤, 하위 30%(70~100 percentile) 구간에서 균등 랜덤 선택. `AiMoveSelectionPolicy.select()`(`shared/match/AiMoveSelectionPolicy.kt:70-79`)가 `candidateIndexRange()`로 구한 range를 `slice()`한 뒤 `random.nextInt()`로 뽑는다. 말씀하신 "하위수를 비율로 착수" 그대로다.
- **2단계**: 중위 40~70% 구간. 역시 "일부러 저하"가 맞다 — 다만 1단계보다는 약간 나은 구간이다.
- **3단계**: `BestOnly`. `candidateIndexRange()`가 항상 `0..0`을 반환해 최상위 후보 1개만 선택 범위가 된다. 그리고 이보다 한 단계 더 앞에서, `AiMoveSelectionPolicy.analysisLimitFor()`(`shared/match/AiMoveSelectionPolicy.kt:24-37`)가 `selectionPolicy is BestOnly`이면 **엔진에 요청하는 candidateCount 자체를 8이 아니라 1로 줄인다.** 즉 3단계는 "8개 중 1등만 고른다"가 아니라 "애초에 1개만 탐색해서 그걸 둔다"— 말씀하신 그대로다. (같은 내용을 오늘 앞서 만든 `ENGINE_CANDIDATE_EXPANSION_REVIEW_2026-08-17.md` 1-2절에서도 확인했다.)

## 2. 후보 분류 규칙 — 최적수/중급수/최하수

제시하신 규칙을 정식화한다. `N`을 그 턴에 실제로 scored(= `pointLoss`가 있는) 후보 개수, 인덱스는 KataGo `order` 기준 0(최상위)부터 `N-1`(최하위)까지라 하면:

| N | 최적수 (best) | 중급수 (mid) | 최하수 (worst) |
| ---: | --- | --- | --- |
| 1 | `{0}` | `{}` | `{}` |
| 2 | `{0}` | `{1}` | `{}` |
| 3 | `{0}` | `{1}` | `{2}` |
| 4 | `{0}` | `{1,2}` | `{3}` |
| N ≥ 3 (일반형) | `{0}` | `{1 .. N-2}`(N-2개) | `{N-1}` |

즉 최적수는 항상 정확히 1개(존재하면), 최하수는 N≥3부터 정확히 1개, 중급수는 N-2개로 계속 늘어난다 — 제시하신 규칙과 정확히 일치한다. 이 규칙은 `MoveSelectionPolicy.candidateIndexRange()`가 이미 쓰는 "인덱스 range" 개념과 호환되므로, 버킷 하나하나는 기존 코드 패턴 그대로(연속 구간) 표현할 수 있다.

## 3. 5단계 이름 — 원안 유지 + 충돌 리스크 한 가지 플래그

`초보 → 하수 → 중수 → 고수 → 초고수` 원안을 그대로 채택한다. 이유: 이미 한국 게임/바둑 커뮤니티에서 가장 널리 쓰이는 실력 사다리 어휘이고, 순서(약→강)도 직관적으로 맞다. 억지로 다른 은유(성장/식물/동물 등)로 바꾸면 오히려 "방향성만 이해하라"는 요청과 어긋난다고 판단했다.

**다만 한 가지 실제 리스크를 짚고 간다**: `중수`/`고수`는 기존 상위 그룹명 `중급`/`고급`과 첫 글자가 같고 끝 글자(수/급)만 달라 빠르게 훑을 때 헷갈릴 수 있다(`중급`(B64, 완전히 다른 그룹)과 `빠른 초급의 중수`(여전히 B16)는 강도 차이가 크다). 이름을 바꾸는 대신 **UI 표시 규칙으로 완화**하는 것을 제안한다 — 항상 상위 그룹명과 함께 표기(예: `빠른 초급 · 중수`, 지금의 `displayLabel = "${group.label} ${level}단계"` 패턴과 동일한 방식으로 `"${group.label} · ${tierName}"`), 절대 `중수` 단독으로 노출하지 않는다. 이 규칙이면 원안 이름을 그대로 쓰면서 충돌 리스크를 실질적으로 없앨 수 있다고 판단한다.

## 4. 단계별 버킷 비율 (원안 채택)

| 단계 | 최하수 | 중급수 | 최적수 | 비고 |
| --- | ---: | ---: | ---: | --- |
| 초보 | 100% | 0% | 0% | |
| 하수 | 60% | 40% | 0% | |
| 중수 | 20% | 60% | 20% | |
| 고수 | 10% | 30% | 60% | |
| 초고수 | — | — | — | 버킷 분류 자체를 안 쓴다. 오늘날의 3단계(`BestOnly`, 후보 1개만 탐색)를 그대로 승계 |

`초고수`는 나머지 4단계와 성격이 다르다 — 후보를 여러 개 받아서 그중 하나를 고르는 게 아니라, 애초에 엔진에 후보 1개만 요청한다(2절 참고). 그래서 이 단계는 아래 5절의 배치 알고리즘이 아예 필요 없다 — 오늘의 3단계 구현을 이름만 바꿔 그대로 쓰면 된다.

## 5. 대국 전체 배치 알고리즘 — "최하수 먼저" 를 만족시키는 방식

### 왜 단순 "매 턴 비율대로 뽑기"가 아닌가

매 턴 독립적으로(예: 고수는 매 턴 10% 확률로 최하수) 뽑으면 말씀하신 문제가 그대로 재현된다 — 어느 턴에 최하수를 뽑아야 하는데 그 턴의 scored 후보가 1~2개뿐이면(최하수 버킷은 N≥3부터 존재) 채울 수가 없다. 오늘 실측(`ENGINE_CANDIDATE_EXPANSION_REVIEW_2026-08-17.md` 4절)에서도 후보수가 국면마다 크게 출렁이는 걸 직접 확인했다(빈 보드 5개 → 초반 8수 2개 → 중반 20수 3개, 항상 늘어나지 않는다). 그래서 "언제 최하수를 시도할지"를 게임 진행에 따라 동적으로 조정하는 장치가 필요하다.

### 검토한 두 방식과 최종 선택

**방식 A — 고정 초반 구간(예: 첫 8수)에 최하수를 몰아넣기.** 구현은 가장 단순하지만 심각한 단점이 있다: 단계가 정의하는 비율(예: 하수 60%)이 "게임 전체 비율"이 아니라 "초반 구간 안에서의 비율"이 되어버린다. 40수짜리 대국이면 첫 8수에 최하수 5개를 다 쓰고 나머지 32수는 전부 중급수/최적수 — 실제 게임 전체 최하수 비율은 60%가 아니라 12.5%로 희석된다. 또 보드 크기가 달라지면 "8수"라는 상수도 다시 튜닝해야 한다.

**방식 B — 누적 비율 기반 자기 교정(추천).** 매 턴마다 "지금까지 뒀어야 할 만큼 최하수를 실제로 뒀는가"를 확인하고, 못 채웠으면 최하수부터 우선 시도한다. 의사코드:

```
# 이 AI 진영이 이번 판에서 지금까지 둔 수: ownMoveCount
# 지금까지 각 버킷으로 착수한 횟수: worstCount, midCount, bestCount

순서 [최하수, 중급수, 최적수] 각각에 대해:
    target = ceil(그 버킷의 목표비율 * (ownMoveCount + 1))
    만약 그 버킷의 누적착수수 < target 이고, 이번 턴 후보 중 그 버킷이 비어있지 않다면:
        이번 턴은 이 버킷에서 뽑는다. (여기서 종료)

# 셋 다 "밀린 것 없음"이면 (평상시) 세 버킷을 원래 비율대로 가중 랜덤 추첨
```

이 방식의 성질:

- **최하수부터 검사**하므로, 최하수와 다른 버킷이 동시에 밀려 있으면 항상 최하수가 우선 채워진다 — 요청하신 "최하수 먼저"를 문자 그대로 만족한다.
- `target`이 `ceil(비율 * 1)`이라 **비율이 0%보다 큰 모든 단계는 이 진영의 첫 수부터 무조건 최하수를 시도한다.** 예: `고수`(최하수 10%)도 1수부터 `ceil(0.10×1)=1`이라 첫 수는 최하수. 이후엔 비율 유지를 위해 필요할 때만(계산하면 약 10수마다 한 번꼴) 다시 최하수를 시도한다 — "초반에 강하게, 이후엔 드물게"가 자연히 나온다.
- **게임이 길어져도 목표 비율이 희석되지 않는다** — 매 턴 "지금까지 비율"을 기준으로 재계산하므로 장기적으로 정확히 원안의 비율(초보100/하수60/중수20/고수10 등)에 수렴한다. 방식 A의 핵심 단점을 해결한다.
- 보드 크기별 상수 튜닝이 필요 없다 — "몇 수"가 아니라 "지금까지 비율"이 기준이라 9x9/13x13/19x19 어디서든 같은 공식이 그대로 성립한다.
- 후보가 부족해 해당 버킷이 비어있으면(예: 최하수 목표인데 이번 턴 N<3) 우선순위상 다음 버킷(중급수 → 최적수)으로 넘어간다 — 최적수는 N≥1이면 항상 존재하므로 이 폴백은 절대 막다른 골목에 다다르지 않는다.

**결론: 방식 B를 최종안으로 제안한다.** 방식 A보다 구현 복잡도는 약간 높지만(4절에서 설명할 상태 추적 필요), "요청하신 두 가지 장점"(초반에 실수를 몰아주는 체감 + 비율을 실제로 맞추는 신뢰성) 중 후자를 방식 A는 사실상 달성하지 못한다. 두 방식의 차이를 인지하시고 확정해주시면 좋겠다 — 만약 "체감상 확실하게 초반에만 몰리는" 쪽을 더 우선하신다면 방식 A(또는 두 방식의 절충)도 가능은 하다.

### 예시 — `고수` 단계 15수 시뮬레이션

| 순번 | 계산되는 최하수 target | 최하수 누적 | 이번 수 선택 |
| ---: | ---: | ---: | --- |
| 1 | ceil(0.1×1)=1 | 0 → 부족 | **최하수** |
| 2 | ceil(0.1×2)=1 | 1 → 충분 | 중급/최적 가중 추첨 |
| 3~10 | 1 | 1 → 충분 | 중급/최적 가중 추첨 |
| 11 | ceil(0.1×11)=2 | 1 → 부족 | **최하수** |
| 12~15 | 2 | 2 → 충분 | 중급/최적 가중 추첨 |

첫 수는 항상 최하수로 시작하고, 이후로는 비율을 유지하는 선에서만 드문드문 최하수가 다시 등장한다 — "초반에 실수 확보 + 이후엔 안정적으로 정리"가 자연히 나타난다.

## 6. 엔진 요청 측면 — 추가 비용은 사실상 없다

`초보~고수` 4단계 모두 오늘 코드가 이미 하고 있는 요청을 그대로 재사용한다. `PlayLevelGroup.FastBeginner`의 `candidateCount=8`, `visits=16`, `GtpStatefulFast`는 바뀌지 않는다 — 오늘 1~2단계가 이미 이 요청을 쓰고 있다(2절). 즉 **이 재설계는 엔진에 새로운 부하를 전혀 추가하지 않는다.** 바뀌는 건 순수하게 "받은 후보를 어떻게 버킷으로 나누고 어떤 버킷에서 뽑을지"라는 선택 로직뿐이다. `초고수`도 오늘의 3단계(candidateCount=1 요청)를 그대로 쓴다.

## 7. 필요한 새 상태 — 이번 제안의 가장 큰 구조적 변화

지금 `MoveSelectionPolicy`(`shared/PlayLevel.kt:139-195`)의 모든 variant(`BestOnly`, `PercentileRange`, `ExcludeBestPercentileRange`)는 **순수 함수**다 — `candidateIndexRange(count: Int): IntRange?` 하나로 그 턴의 후보 개수만 보고 즉시 답을 낸다. 과거 기록도 없고 상태도 없다.

방식 B(5절)는 구조적으로 다르다 — "지금까지 이 진영이 이번 판에서 최하수/중급수/최적수를 각각 몇 번 뒀는가"라는 **판 전체에 걸친 누적 상태**가 반드시 필요하다. 이건 오늘 이 코드베이스에 없는 종류의 상태라 새로 설계해야 한다.

제안하는 모양:

```kotlin
data class TierProgressState(
    val ownMoveCount: Int = 0,
    val worstCount: Int = 0,
    val midCount: Int = 0,
    val bestCount: Int = 0,
)
```

- 이 state는 진영(흑/백)별로 독립이어야 한다 — AI vs AI 자동대국에서 두 AI가 각자 다른 5단계를 쓸 수 있으므로.
- `AiMoveSelectionPolicy.select()`가 지금은 `(state 없이) 후보 → 선택된 수`만 반환하는데, 새 경로는 `(이전 TierProgressState, 후보) → (선택된 수, 갱신된 TierProgressState)`로 바뀌어야 한다.
- 이 state를 어디에 보관할지가 이번 제안에서 가장 중요한 미정 사항이다. 오늘 조사한 범위에서는 `MatchPolicy.kt`가 `selectAiMoveFromAnalysis()`를 갖고 있고 이게 진영별 AI 응수 흐름을 소유하는 지점으로 보이지만, 실제로 게임 세션 상태(`GameSessionCoreState` 계열)의 어디에 진영별로 이 카운터를 얹을지는 구현 착수 시 해당 파일들을 직접 열어 확정해야 한다 — 오늘은 설계 문서라 추측성 파일 경로를 확정 짓지 않는다.
- 새 게임 시작/무르기(undo) 시 이 state를 리셋해야 하는지도 결정이 필요하다 — 상식적으로는 "새 게임 시작 = 리셋", "무르기 = 되돌린 수만큼 카운터도 되돌림"이 맞다고 보이지만, 이것도 구현 시 기존 undo 아키텍처와 맞춰 확정한다.

이 부분이 "바로 착수" 여부를 판단할 때 가장 중요하게 볼 지점이다 — 후보 분류(2절)와 버킷 비율(4절)은 순수 계산이라 리스크가 작지만, 이 상태 추적은 게임 세션 생명주기(새 게임/무르기/AI vs AI 진영 분리)와 맞물리는 실제 설계 작업이다.

## 8. 레벨 번호 재해석 — 마이그레이션 리스크

`PlayLevelGroup.FastBeginner.maxLevel`이 3에서 5로 바뀌고, 선택 정책 자체가 전부 교체된다. 문제는 **레벨 번호는 그대로 저장되는데 의미가 바뀐다**는 점이다 — 예를 들어 사용자가 지금 저장해 둔 "빠른 초급 3단계"는 오늘은 `BestOnly`(최강)를 의미하지만, 재설계 후 "3단계"는 `중수`(최하수20/중급60/최적20, 훨씬 약함)를 의미하게 된다. `PlayLevelSetting`이 앱 설정에 영속 저장되는지는(예: `preferences-autosave-pattern`류 자동저장 대상인지) 오늘 문서 범위에서 확인하지 않았다 — 구현 착수 전에 반드시 확인이 필요한 항목이다.

만약 영속 저장된다면 권장 완화책: 값 자체를 1:1로 옮기지 말고, **기존 3단계(BestOnly) 사용자는 새 5단계(`초고수`)로, 기존 1/2단계 사용자는 새 2단계(`하수`)로 매핑**하는 간단한 마이그레이션을 한 번 태운다 — "저장돼 있던 난이도가 갑자기 훨씬 약해지는" 체감 저하를 피하기 위해서다(1/2단계는 원래도 "일부러 약하게 만든" 의도였으니 새 체계에서도 약한 쪽에 두는 게 자연스럽다).

## 9. 검증 계획 — 코드 반영 전에 터미널에서 먼저 확인할 것

오늘 만든 `scripts/run-katago-candidate-refine-experiment.py`와 같은 방향으로, Kotlin을 건드리기 전에 순수 Python 시뮬레이션으로 5절 알고리즘을 먼저 검증하는 걸 제안한다:

1. 2절의 버킷 분류 규칙과 5절의 방식 B 알고리즘을 Python으로 그대로 구현.
2. 실제 KataGo 응답(오늘 스크립트가 이미 만드는 `moveInfos` 목록)에 대입해 N수 시뮬레이션 대국을 여러 판 돌리고, 판마다 실제 최하수/중급수/최적수 사용 비율이 원안 비율(예: 고수 10/30/60)에 얼마나 수렴하는지 확인.
3. "최하수가 필요한 턴에 후보가 부족해서 폴백이 발동한 비율"을 별도로 집계 — 이게 낮아야 방식 B가 실제로 문제(전반 요청의 배경 문제 2번)를 해결한다는 근거가 된다.
4. 문제 없으면 그때 Kotlin 구현(`MoveSelectionPolicy` 확장, `TierProgressState`, 7절의 상태 보관 위치 확정)에 들어간다.

이 순서면 "설계가 실제로 의도한 비율을 만드는지"를 앱 빌드 없이 먼저 확인할 수 있다.

## 10. 다음 단계 제안

**결론부터: 이 설계는 착수할 가치가 있다고 판단한다.** 6절에서 확인했듯 엔진 부하 증가가 없고, 2/4/5절의 핵심 알고리즘은 순수 계산이라 리스크가 낮다. 다만 7절(새 상태 추적)과 8절(마이그레이션)은 실제 설계 판단이 더 필요한 지점이라, 다음 순서를 제안한다.

1. **이름/비율/알고리즘 확정** — 3절의 이름(그대로 채택 제안), 5절의 방식 A vs B(방식 B 채택 제안) 두 가지만 확인 부탁드린다. 나머지는 원안 그대로다.
2. **9절 Python 시뮬레이션** — 확정된 설계를 코드 없이 먼저 검증. 하루 이내로 가능한 작업.
3. **7절 상태 보관 위치 조사 + 8절 마이그레이션 여부 확인** — 실제 코드(`MatchPolicy.kt`, `GameSessionCoreState` 계열, 설정 저장소)를 열어 확정.
4. **Kotlin 구현** — `MoveSelectionPolicy`에 새 variant 추가, `AiMoveSelectionPolicy`/`MatchPolicy` 경로에 상태 threading, `PlayLevel.kt`의 `FastBeginner` 재정의.
5. **에뮬레이터/실기기 확인** — 5단계 각각 몇 판씩 자동대국으로 돌려 체감 난이도 순서(초보<하수<중수<고수<초고수)가 실제로 지켜지는지 확인.

1~2번은 사용자 확인만 있으면 바로 시작할 수 있는 가벼운 작업이라, **1번 확인을 주시면 2번(시뮬레이션)부터 바로 착수하는 것을 제안한다.** 3번 이후(실제 Kotlin 변경)는 여전히 별도 승인을 받고 진행하겠다.

## 11. 확정 사항 및 구현 결과 (2026-08-18)

사용자가 3절 이름/5절 방식을 승인하면서 두 가지를 추가로 요청했다: (a) AI 선택을 그룹→단계 2뎁스에서 5단계 1뎁스로 간소화(초급/중급/고급 그룹은 완전히 숨김), (b) 신규 대국 기본값(AI=초보, 덤 6.5, 13x13, 접바둑 최대). 이 절은 그 확정 내용과, 구현 과정에서 5/7절보다 더 나은 방식을 찾아 대체한 내용을 기록한다.

### 11-1. AI 선택 UI: 그룹 선택 완전히 숨김 (승인됨)

`PlayerSetupPanel.kt`의 그룹 드롭다운(`PlayLevelGroup.entries`)을 제거하고, 5단계(초보~초고수) 단일 드롭다운만 남겼다. `PlayLevelGroup.Beginner/Intermediate/Advanced` 열거형과 그 관련 코드(`EngineAnalysisPolicy.kt`의 JSON 경로, `playLevelGroupLabel()` 등)는 **삭제하지 않고 그대로 둔다** — 코드는 살아있지만 이 화면에서는 선택할 방법이 없다.

**향후 로드맵(사용자 확정, 미구현)**: 나중에 "대국장" 개념을 도입해, 어느 대국장에 입장하는지가 곧 중분류(초급/중급/고급) 선택이 되도록 만들 예정이다. 즉 지금 숨긴 그룹 선택 UI는 "제거"가 아니라 "다른 진입 경로로 대체 예정"이다 — `PlayLevelGroup.entries`/`playLevelGroupLabel()`을 나중에 대국장 목록 UI가 그대로 재사용할 가능성이 높으므로, 이번 구현에서 이 코드들을 정리하지 않았다.

### 11-2. 신규 대국 기본값 (일부는 이미 충족되어 있었다)

코드 조사 결과, 4개 요청 중 3개는 이미 현재 기본값과 일치했다.

| 항목 | 요청값 | 조사 결과 | 조치 |
| --- | --- | --- | --- |
| AI 레벨 | 초보 | `PlayLevelSetting()` 기본값이 `(FastBeginner, level=1)` — 11-3절 재정의로 레벨 1의 의미 자체가 "초보"가 되므로 **추가 코드 변경 없이 자동으로 충족** | 변경 없음 |
| 덤 | 6.5점 | `DefaultKomi = 6.5`(`BoardModels.kt`)로 이미 기본값 | 변경 없음 |
| 바둑판 | 13x13 | `UserPreferencesSnapshot.boardSize`가 이미 `BoardSize.Thirteen` | 변경 없음 |
| 접바둑 | 최대값 | `UserPreferencesSnapshot.handicapCount`가 기존엔 `0`(맞바둑) | **`0` → `BoardSize.Thirteen.maxHandicapCount`(=5)로 변경** |

`집계가`는 "계가(scoring rule) + 덤" 요청으로 해석했다 — 계가 방식(`Ruleset.Japanese`, 영역+사석 계가)도 이미 기본값이라 별도 변경은 하지 않았다. 이 해석이 틀렸다면 정정 부탁드린다.

기본 좌석 배정은 흑=사람/백=AI(`MatchPolicy.kt`)이므로, 접바둑을 최대로 두면 **사람이 접바둑을 받는 유리한 쪽**이 된다 — 최약체 AI(초보) + 최대 접바둑이 합쳐져 첫 대국을 확실히 이기기 쉽게 만드는 조합이다. 이건 우연이 아니라 "초심자 진입 난이도를 낮춘다"는 목적에 정확히 부합하는 설계로 판단해 그대로 반영했다.

### 11-3. 최종 배치 알고리즘 — 5/7절의 "누적 상태" 방식을 무상태 방식으로 대체

구현에 들어가기 전 실제 코드(`AiMoveSelectionPolicy.select()`, `MatchTurnOrchestration.kt`)를 확인해보니, 7절이 우려했던 "판 전체에 걸친 누적 상태"가 지나가는 모든 계층(`GameSessionCoreState`/`AutoAiTurnDisplayPlan`/undo/영속화)에 새 필드를 심어야 하는 구조였다 — 리스크가 컸다. 다시 계산해보니 **상태를 전혀 저장하지 않고도 5절과 수학적으로 동일한 성질을 얻는 공식**을 찾아 이걸로 대체했다.

**핵심 아이디어**: `AiMoveSelectionPolicy.select()`는 이미 `currentState: GameState`를 받는다. `GameState.moves`에 전체 수순이 있으므로, "이 진영이 이번 판에서 지금까지 몇 수를 뒀는가"(`ownMoveIndex`)는 **저장할 필요 없이 그때그때 세면 된다** — 무르기(undo)를 해도 `moves`가 줄어들면서 자동으로 올바르게 "되돌아간다".

남은 건 "최하수를 몇 번 뒀는가"였는데, 이것도 상태로 안 쌓고 아래 공식으로 대체했다(5절의 `ceil` 누적 목표 공식을 살짝 바꾼 것):

```
target(k) = ceil(worstPercent / 100 * k)   # k = 이 진영의 몇 번째 수인지(1부터)

이번 수(k번째)에서 최하수를 목표로 한다  ⇔  target(k) > target(k-1)
```

이건 "지난 수들이 전부 목표대로 성공했다"고 가정하고 5절 공식을 telescoping(망원경식 상쇄)한 것과 수학적으로 동일하다 — 그래서 상태 추적 없이 `k`(=`ownMoveIndex`)만 알면 계산된다. 성질은 5절 worked example과 완전히 같다:

- `worstPercent > 0`인 모든 단계는 **이 진영의 1수째는 항상 최하수를 목표로 한다**(`target(1) = ceil(r) ≥ 1 = target(0) + 1`, 어떤 `r>0`이든 성립).
- 장기적으로 실제 최하수 비율은 원안 퍼센트에 최대 1회 오차로 수렴한다(`shared/PlayLevelSettingTest.kt`의 `targetBucketConvergesToNominalWorstRatioOverManyMoves`가 500수 시뮬레이션으로 검증).
- 최하수 목표인데 그 턴 후보가 부족하면(N<3) 중급수→최적수 순으로 폴백한다(5절과 동일).

`PlayLevel.kt`에 `CandidateBucket` enum, `candidateBucketRange()`(2절 분류 규칙의 순수 함수 버전), `BucketedTierSelection.targetBucket()`/`.resolveIndexRange()`(위 공식)로 구현했다. `AiMoveSelectionPolicy.select()`는 `selectionPolicy`가 `BucketedTierSelection`이면 이 경로로, 아니면 기존 `candidateIndexRange()` 경로로 분기한다.

**이 대체가 바꾼 것**: 7절이 가장 큰 리스크로 지목했던 "새 세션 상태·undo 리셋·직렬화 마이그레이션"이 전부 필요 없어졌다. 8절의 레벨 번호 재해석 문제만 남는다(아래 11-4).

### 11-4. 마이그레이션: 하지 않기로 결정

8절이 제안했던 "구 3단계→신 5단계, 구 1/2단계→신 2단계" 매핑은 구현하지 않았다. 이유:

1. `PlayerSetupJsonCodec`을 확인해보니 `PlayLevelSetting`에는 스키마 버전 필드가 없다(시간 제한 설정에만 있음). 버전 구분자 없이는 "이 저장값이 구 스킴 3단계인지, 신 스킴에서 사용자가 실제로 고른 3단계(중수)인지" 구분할 방법이 없다 — 구분 없이 리매핑하면 신규 사용자가 중수를 골라도 계속 초고수로 밀어올리는 별도 버그가 생긴다.
2. 이 앱은 아직 Google Play에 발행되지 않았다(`launch-plan/README.md` 기준 초도 발행 준비 단계) — 실제로 구 스킴을 저장한 사용자가 사실상 없다.
3. `PlayerSetupJsonCodec.decodePlayLevel()`은 이미 안전하게 저하한다 — 그룹 이름이 안 맞으면 `FastBeginner`로, 레벨은 그대로 두고 `normalized()`로 범위만 clamp한다. 크래시나 데이터 손실 없이 "저장된 레벨 번호가 새 의미로 재해석되는" 정도의 조용한 동작 변화만 있다.

결론: 지금 마이그레이션 코드를 추가하는 비용이 실제 위험보다 크다고 판단해 생략한다. 나중에 실제 사용자가 생긴 뒤 이 문제가 다시 불거지면, 그때는 스키마 버전 필드를 `PlayerSetupJsonCodec`에 추가하는 선행 작업부터 해야 한다.

### 11-5. 이름 표시 방식도 재확인 필요 없어졌다

3절은 "중수/고수가 중급/고급과 헷갈릴 수 있으니 항상 `빠른초급 · 중수`처럼 그룹명과 같이 표기하자"고 제안했었다. 그런데 11-1절 결정(그룹 선택 UI 자체를 완전히 숨김)으로 이 우려의 전제가 사라졌다 — 화면에 `중급`/`고급`이 아예 안 보이니 헷갈릴 대상이 없다. 그래서 AI 선택 드롭다운에는 그룹명 없이 순수 티어명(`초보`/`하수`/`중수`/`고수`/`초고수`)만 표시하도록 구현했다. 다만 진단 로그/Copy Log용 `PlayLevelSetting.displayLabel`은 여전히 `"빠른 초급 · 중수"` 형식을 유지한다 — 로그에는 어떤 탐색 모드(B16/GTP)에서 나온 레벨인지가 명확한 게 낫기 때문이다.
