## 1. 무엇을 푸는 방법인가

**문제: AI 스레드는 매번 콜드 스타트한다.**

새 스레드는 지난주에 무엇을 왜 그렇게 정했는지 모릅니다. 사람이 매번 말로 설명하면 설명이 조금씩 달라지고, 그 편차가 그대로 구현 편차가 됩니다. 특히 **"왜 그렇게 안 했는가"**(검토했지만 버린 선택지)는 코드에 남지 않아 다음 스레드가 같은 논의를 처음부터 반복합니다.

**해법: 컨텍스트를 사람이 아니라 문서가 흡수한다.**

사람은 한 문장짜리 고정 프롬프트만 붙여 넣고, 나머지는 문서가 스레드에게 알려 줍니다. 스레드가 끝날 때 그 스레드가 알아낸 것을 다시 문서에 돌려놓습니다.

```
사람: 고정 프롬프트 한 줄 복붙
  ↓
스레드: 문서를 읽고 → 자기 일감을 집고 → 작업하고 → 문서에 결과를 돌려놓음
  ↓
사람: 승인
  ↓
(다음 스레드는 갱신된 문서에서 시작)
```

이 방식의 값어치는 **스레드가 끝나도 지식이 남는다**는 것입니다. 대화창은 사라져도 문서는 남습니다.

## 2. 포지셔닝과 핵심 가치

이 방법론은 팀의 이슈 트래커(Jira·Linear·GitHub Issues)를 대체하지 않습니다. 그 아래 자리를 잡습니다:

```
[팀/조직 레벨 — 매크로 관리]     이슈 트래커 (있다면)
                                        │  ▲
                할당된 일감을 개인이 수신 │  │ 완료 요약을 반영 (7장)
                                        ▼  │
[개인 레벨 — 마이크로 실행]      단일 문서 백로그 + 스펙 문서
                                        │  ▲
                  고정 프롬프트 1줄 주입 │  │ [완료] 상태·산출물을 되돌려줌
                                        ▼  │
[AI 스레드 — 순차 실행]         Claude 등 AI 작업 스레드
```

핵심 가치는 두 가지입니다.

**① 팀 트래커 아래의 개인 실행 계층.** 트래커가 있다면 팀 단위 배분·조율은 그대로 거기서 합니다. 이 방법론은 그 아래 — 한 사람이 할당받은 일감을 AI 스레드로 실행하는 과정 — 을 맡습니다. 완료되면 7장의 방식으로 트래커·보고에 되돌립니다.

**② 다중 프로젝트 컨텍스트 보존.** 팀 여부와 무관하게, 프로젝트마다 이 문서 쌍(스펙+백로그) 하나씩을 두면 다른 프로젝트로 옮겼다 돌아와도 그 파일 하나를 여는 것으로 재진입이 끝납니다. 문서 하나가 자기 완결적이라는 설계에서 논리적으로 따라 나오는 결과이지, 측정된 성능 수치는 아닙니다.

실제로 검증된 것은 이 저장소 단일 트랙에서의 운영 규칙(5장)이고, 위 두 가치는 같은 설계 원칙(자기 완결적 문서)이 일반화되는 방향입니다.

### 적용 경계

- **맞는 경우**: AI 스레드가 주 실행 주체 · 한 사람(스레드)이 순차 진행 · 항목 간 판단이 서로 전제가 되는 작업 · 몇 주 단위 트랙 · 다중 프로젝트 컨텍스트 전환.
- **안 맞는 경우**: 여러 사람이 동시에 다른 항목을 진행(트래커로 조율) · 항목이 서로 독립적인 작업 · 실시간 대시보드가 필요한 보고.

## 3. 전체 그림 — 문서 2개 + 프롬프트 1개

프로젝트 트랙마다 아래 두 문서가 한 쌍으로 존재합니다.

| 구성 | 역할 | 성격 |
| --- | --- | --- |
| **스펙 문서** (`[기능명]_SPEC_PLAN.md`) | **왜 / 무엇을** 만드는가. 절 번호로 참조되는 원본 | 오래 산다. 결정이 append됨 |
| **백로그 문서** (`[기능명]_SPEC_BACKLOG.md`) | **누가 언제 무엇을** 하는가. 스레드 단위 일감과 상태 | 자주 바뀐다. 스레드마다 갱신 |
| **고정 프롬프트** | 새 스레드에 복붙하는 한 문장 | 거의 안 바뀐다 |

### 가장 중요한 규칙 하나

> **백로그는 스펙을 다시 쓰지 않는다. 절 번호만 가리킨다.**

이걸 어기면 같은 사실이 두 군데에 남고, 한쪽만 고쳐져 어긋납니다. 백로그 항목은 "참고: 4.2절"처럼 포인터만 두고, 설계 근거는 스펙에서 읽게 합니다.

같은 원리를 코드에도 적용합니다. 이번 트랙의 실제 사례 — 캐릭터의 출석 지급 일차는 **카탈로그 코드**(`BotUnlockSource.Attendance(tier)`)에만 적고, 보상 정책표는 그걸 읽어 갑니다. 정책표에도 적었다면 캐릭터 획득 경로가 바뀔 때마다 두 군데를 고쳐야 했을 것입니다.

### 고정 프롬프트 (그대로 쓰면 됩니다)

> 이번 스레드에서는 `<경로>/<백로그 파일명>.md` 이 파일의 내용을 파악하여 '예정사항'의 첫번째 항목을 파악하여 수행 담당해야합니다. 먼저 항목을 이해하셨다면 진행중으로 변경하고 작업 착수하시고, 결과물을 사용자와 논의 후 사용자가 완료 승인을 하면 문서에 완료 업데이트하고 당신의 스레드 업무가 종료되었다고 명시해주시면 됩니다.

짧지만 네 가지를 지시합니다 — **어떤 문서를 읽을지 / 어떤 항목을 집을지 / 상태를 언제 바꿀지 / 무엇으로 끝내는지.** 경로를 포함시키면 스레드가 파일을 찾는 탐색 한 단계를 아낍니다.

## 4. 백로그 문서 해부 — 5개 구성요소

실제 문서에서 그대로 뽑은 샘플입니다. 완료 항목은 아래처럼 서술형으로 쌓여 있고 완료 사항이 맨 앞에 옵니다 — 이건 실제 운영된 원본을 그대로 보여주는 것이 목적이라 고치지 않았습니다. **새로 시작하는 트랙은 9장 템플릿의 순서(진행중 → 예정사항 → 완료 사항)를 권장합니다** — 완료 항목이 쌓여도 실행 가능한 부분이 먼저 보이도록.

### ① 신규 스레드 착수 프로토콜

```
1. 읽기      — 백로그 전체 + 스펙의 공통 전제 절(2·3장) + 이번 항목이 가리키는 절.
2. 상태 전환 — 예정사항의 첫 번째 항목을 진행 중으로 옮기고 [진행중]을 붙인다.
              단, 문서에 이미 [진행중] 항목이 있다면 먼저 규칙 8(복구 확인)을 따른다.
3. 작업      — 해당 절의 스펙대로 구현한다. 범위 확장이나 다음 항목 선착수는 하지 않는다.
4. 막히면    — 스펙에 없는 정보는 먼저 코드를 직접 확인해 스스로 판단한다.
              그래도 답이 안 나오는 제품/설계 결정만 사용자에게 확인한다.
5. 완료 처리 — 사용자 승인 후에만. 완료 사항으로 옮기고 "산출물:" 한 줄을 추가한다.
6. 다음 안내 — 다음 항목 번호만 짧게 언급하고 마친다. 서두의 파생 정보가
              여전히 맞는지 함께 확인한다.
```

### ② 서두 정리 — 매 스레드가 알아야 할 공통 전제

스코프, 항목 간 의존관계, 아직 미확정인 것. **"스레드가 대신 정하지 말 것"**을 여기에 명시합니다.

> "의존관계"·"미확정 목록"은 항목 본문의 `선행 조건`·`착수 전 확인` 필드와 내용이 겹쳐 가장 빨리 낡습니다(8장 ①). "스코프"처럼 항목 단위로 쪼갤 수 없는 것만 최소로 남기는 것을 권장합니다.

### ③ 완료 사항 — 무엇이 남았는지가 아니라 **무엇을 알아냈는지**

```
6. 대국 히스토리 저장소 구현 — GameHistoryStorePort/GameHistoryEntry
   + 대국 종료 시 append 배선 (AI 모델: Sonnet, 노력정도: 중간) [완료]
   - 참고: 6장.
   - 산출물(shared): GameHistoryEntry.kt / GameHistoryPorts.kt / ...
     산출물(app-android): persistence/GameHistoryStore.kt + GameHistoryCodec ...
     구현 결정은 킥오프 플랜 6장 각주 참고 — 조사 중 발견한
     SidePlayerSetup.aiCharacterProfile()은 #8에 참고로 남김.
   - 전체 테스트·컴파일 통과, 사용자 승인 완료(2026-08-24).
```

값어치가 큰 것은 제목이 아니라 **"산출물:" 줄과 그 뒤에 붙는 발견**입니다. 위 예의 "`aiCharacterProfile()`은 #8에 참고로 남김" 한 줄이, 3일 뒤 #8 스레드가 같은 혼동을 겪지 않게 막아 줬습니다.

### ④ 진행 중 — 항상 0개 또는 1개

```
### 진행 중

(없음)
```

동시에 여러 스레드를 붙이지 않는 것이 전제입니다. `(없음)`이 아니라 항목이 들어 있는 채로 새 스레드가 시작되면, 지난 스레드가 중간에 끊겼다는 신호입니다 — 곧바로 이어받지 말고 규칙 8을 먼저 따르세요.

### ⑤ 예정 사항 — 다음 스레드가 집을 것

```
17. 소모품 인벤토리 상시 표시 — '형세보기: 30' / '추천 수: 30' / '광고 스킵권: 5'
    (AI 모델: Sonnet, 노력정도: 중간)
    - 참고: 4.5절. #15에서 확정했던 "잔량은 팝업 안에만"을 대체하는 항목이다.
    - 가장 중요한 요구사항은 "잔여 개수가 확연히 보이면서 차감되는 것이 보이는 것".
    - #16 완료 후 착수(지급량이 바뀌므로).
```

반드시 들어가야 할 것: **참조 절 / 선행 조건 / 착수 전 확인이 필요한 것.**

### 항목 포맷

```
N. 제목 — 한 줄 요약 (AI 모델: <모델>, 노력정도: <낮음|중간|높음|최대>) [상태]
```

`AI 모델`은 사람이 스레드를 어떤 모델로 띄울지 참고하는 값입니다(스레드가 스스로 바꾸지 않습니다). 완료 후 노력정도에는 `중간 → 실제 높음`처럼 실제 소요를 덧붙입니다(규칙 3).

체크박스(`- [ ]`/`- [x]`)는 쓰지 않습니다. 예정/진행중/완료는 **어느 섹션에 있는가 자체가 상태**인 3단 구조인데, 체크박스는 2단뿐이라 "진행중"을 표현할 자리가 없습니다.

## 5. 운영 규칙 8가지

### 1. 번호는 식별자, 실행 순서는 목록에 적힌 물리적 위치

번호를 다시 매기지 않습니다 — 완료 항목과 스펙 각주가 그 번호를 참조하기 때문입니다. 실행 순서는 **별도로 적지 않습니다.** 예정사항 목록에서 항목이 놓인 줄 순서 자체가 실행 순서입니다. 우선순위가 바뀌면 항목을 위아래로 옮기기만 하면 되고, "지금 실행 순서는 이렇다"는 문장을 따로 적어 둘 필요가 없습니다 — 적어 두면 그 문장 자체가 낡습니다(실제로 이 트랙이 겪은 문제, 8장 ①).

### 2. 완료 항목은 불변이며, 산출물을 반드시 남긴다

완료 기록은 "그때 무엇을 왜 그렇게 했는가"의 히스토리입니다. 나중에 방향이 바뀌었다고 고치면 히스토리가 사라집니다 — 되돌리는 대신 **새 일감을 세웁니다.**

> **실제 사례**: 보상 구조가 재확정되면서 완료 항목 #8·#9·#12·#13·#15의 산출물을 고쳐야 했지만, 되돌리는 대신 **새 일감 #16**을 세웠습니다. "왜 처음엔 5종을 전부 잠갔다가 되돌렸는가"가 그대로 남아 있습니다.

그리고 완료 시에는 **실제로 바뀐 파일**을 "산출물:" 한 줄로 반드시 적습니다. 이게 없으면 몇 주 뒤 "그 기능 어디 있죠?"를 코드 검색으로 찾아야 합니다.

### 3. 노력정도 추정 오차를 기록한다 (`예상 → 실제`)

이 트랙에서 두 번 빗나갔습니다 — 새 요구사항이 붙어 "높음"이 더 커진 경우, "중간"이 "높음"으로 올라간 경우. 기록이 쌓이면 다음 일감을 쪼갤 때의 감각이 좋아집니다(다만 규칙을 만든다고 추정이 바로 정확해지지는 않습니다 — 기록이 쌓이는 것만 보장합니다).

### 4. 구현 결정은 스펙 문서에 각주로 역류시킨다

작업 중 판단은 백로그가 아니라 **스펙 쪽에 각주**로 붙입니다. 실제 각주(2026-08-24):

```
> 구현 결정(백로그 #12, 2026-08-24):
> 4. FeatureAccessPolicy를 고쳐 소모품을 네 번째 허용 경로로 넣지 않았다.
>    그 함수는 부수효과 없는 조회(resolve)인데 소모품은 보는 순간 줄어드는
>    자원이라, 합치면 "확인만 했는데 재고가 닳는" 구조가 된다. 대신 우선순위
>    규칙을 별도 순수 함수 decideConsumableSpend에 담고, "이미 쓸 수 있는가"
>    판정은 기존 resolve에 위임해 정책이 두 군데로 갈라지지 않게 했다.
```

백로그는 자주 갈아엎히지만 스펙은 오래 삽니다. **버린 선택지와 그 이유**를 여기 남기는 것이 가장 값어치가 큰 습관입니다 — 코드 주석은 "무엇을 했는지"를, 이 각주는 "무엇을 안 했는지"를 말합니다. 각주를 어떻게 쓰면 좋은지의 구체적 형식(작성 공식 + 체크리스트)은 `docs/knowhow-docs/_SPEC_PLAN.md` 1장에 있습니다.

### 5. "착수 전 확인(사용자)"을 항목에 미리 박아 둔다

AI가 대신 정하면 안 되는 것(제품 결정, 가격, 콘텐츠)을 항목에 미리 표기합니다:

```
- 착수 전 확인(사용자): '광고 스킵권' 1회의 범위(대국 1판인지 광고 1회인지)와
  스킵 대상 광고 노출 지점. 이게 정해져야 차감 단위가 결정된다.
```

### 6. 스코프와 완료는 AI가 스스로 넘지 않는다

두 가지를 함께 지킵니다 — **범위 확장 금지**: AI는 "이왕 하는 김에"에 취약하므로 프로토콜 3단계에 명시적으로 금지어를 둡니다. **완료는 사람 승인 후에만**: 스레드가 스스로 완료 처리하지 않습니다. 이 게이트가 없으면 문서가 "다 됐다고 주장하는" 상태로 흘러갑니다.

### 7. 커밋 시점은 사람이 정하고, 검증 명령은 문서에 적어 둔다

스레드가 임의로 커밋하지 않습니다. 커밋 메시지 형식(`feat(scope): ... (backlog #N)`)을 정해 두면 `git log --grep "backlog #"`로 트랙 전체를 훑을 수 있습니다. 구체적인 커밋 리듬 패턴은 6장 참고.

새 스레드는 빌드 환경도 모릅니다 — 환경 함정이 있으면 반드시 적습니다:

```
- 검증 명령: 이 저장소는 JDK 17이 필요하다 — 시스템 기본 JDK로 돌리면
  Gradle이 `25` 한 줄만 뱉고 즉시 실패해 원인을 찾기 어렵다.
```

### 8. `[진행중]` 항목을 발견하면 먼저 `git status`로 확인한다

스레드는 착수 즉시 `[진행중]`을 파일에 씁니다 — 다음 스레드가 즉시 알 수 있게. 다만 그 스레드가 중간에 끊기면 표시만 남고 작업은 반쯤 걸쳐 있을 수 있습니다. 새 스레드가 `(없음)` 대신 `[진행중]` 항목을 발견하면, 곧바로 이어받지 말고 **`git status`/`git diff`로 워킹 트리를 먼저 확인**합니다. 변경이 있으면 미완성 작업이니 이어갈지 되돌릴지 판단하고, 없으면 예정사항으로 되돌려 다시 시작해도 안전합니다.

## 6. 선택적 커밋 리듬 — 격리 커밋 플레이북

규칙 7("커밋 시점은 사람이 정한다")을 실제로 어떤 리듬으로 할지는 프로젝트마다 다릅니다. 팀 리뷰가 있거나 커밋 단위 추적성이 중요하다면 아래 패턴이 유용합니다.

```
[단위 일감 승인] → [로컬 커밋(즉시)] → [로컬 테스트/리뷰] → [원격 푸시(마일스톤 단위)]
                          │                        │
                          └─ (필요시 amend로 정리) ──┘
```

1. 항목이 완료 승인되면 즉시 로컬에 커밋합니다 — 다른 항목의 변경과 섞이지 않게.
2. 푸시는 항목마다 하지 않고, 의미 있는 단위가 모이고 전체 테스트가 통과한 시점에 합니다.
3. 푸시 전 발견된 사소한 누락은 `git commit --amend`로 정리합니다 — **아직 푸시하지 않은 로컬 커밋에만** 씁니다. 이미 푸시된 커밋을 amend하면 안 됩니다.

⚠️ **이건 규칙이 아니라 선택 가능한 패턴입니다.** 이 저장소에는 반대 사례가 있습니다 — 항목 5개(#9·#12·#13·#14·#15)가 여러 공유 파일에 걸쳐 있어 항목별로 깔끔하게 분리되지 않았고, 사용자 지시로 **한 커밋에 묶었습니다.** 항목이 서로 다른 파일을 건드리면 이 플레이북을, 같은 파일을 여러 항목이 함께 건드리면 묶어서 커밋하는 쪽을 고르세요.

## 7. 팀 트래커·보고 주기와 연계하기

2장에서 말한 상위 계층과 만나는 지점입니다 — 팀에 이슈 트래커가 있다면, 완료 항목을 정기적으로 그 트래커·보고에 반영하는 방법입니다.

**메커니즘**: 완료 항목을 9장 템플릿처럼 구조화된 필드(산출물 / 커밋 / 승인일 / 비고)로 적어 두면, 그대로 복사해 보고 텍스트로 옮길 수 있습니다.

```
[완료 항목 필드]                    [보고 텍스트로 그대로 옮김]
- 산출물: AppDatabase.kt 외 2건  →  "산출물: AppDatabase.kt 외 2건"
- 비고: 레거시 마이그레이션 스킵  →  "특이사항: 레거시 마이그레이션 스킵"
- 커밋: feat(history): ... #13   →  (PR/커밋 링크로 그대로 첨부)
```

구체적인 보고 문구·주기(일일/주간/월간 정형 포맷)는 이 저장소에서 실제 사이클로 돌려본 적은 없습니다 — 팀 관행에 맞춰 조정하세요. "구조화된 필드가 곧 보고 원본이 된다"는 핵심 메커니즘 자체는 이미 쓰고 있는 것입니다.

**긴장 하나**: 완료 항목을 보고 원본으로 계속 쓰려면 영구 보관해야 할 것 같지만, 이건 8장 ④("완료 항목이 쌓여 문서가 길어진다")와 부딪힙니다. 해법은 역할 분리입니다 — **보고서·트래커에 옮겨 적은 시점부터는 그쪽이 영구 기록**이고, 백로그 쪽 항목은 압축해도 됩니다. 이 저장소의 문서 보존 정책(`docs/DOCS_INDEX.md`: "결론이 흡수되면 삭제한다, git이 아카이브다")과 같은 원리입니다.

트래커 연계를 쓴다면, 항목 헤더에 `연계 이슈: <트래커 키>` 필드만 9장 템플릿에 추가하면 됩니다.

## 8. 실제로 겪은 마찰과 대응

### ① 파생 정보가 빨리 낡는다 — 가장 자주 생기는 문제

서두의 "의존관계 / 미확정 목록"은 항목에서 계산할 수 있는 정보를 복제한 것이라 빨리 낡습니다. 이 트랙에서 이틀 새 두 번 갱신했고, 한 번은 실행 순서 문장이 낡은 채로 남아 **새 스레드가 이미 끝난 항목을 집을 뻔했습니다.**

> **대응**: 실행 순서 자체는 규칙 1로 해소됐습니다(문장이 아니라 목록 위치). 남은 "의존관계/미확정" 요약은 최소화하는 것이 근본 대응입니다.

### ② 노력정도 추정이 빗나간다

규칙 3으로 승격됐습니다 — 다만 규칙을 만든다고 추정이 바로 정확해지진 않습니다. 기록이 몇 건뿐이라 이 트랙에서는 아직 검증되지 않았습니다.

### ③ 사용자 답변이 새 요구사항이 될 때

"1회권의 소비 단위가 무엇인가?"라고 물었더니 "토글은 유지하고 1회권은 단발성으로"라는 새 설계가 돌아온 적이 있습니다.

> **대응**: 별도 일감으로 뗄지 여기서 할지 판단하고 근거를 밝혀야 합니다. 이 사례는 "단발성 모드는 1회권 말고 진입점이 없어 떼면 실행할 수 없는 일감이 된다"는 이유로 같은 항목에서 처리했습니다. 규칙으로 자동화할 수 없는 부분입니다.

### ④ 완료 항목이 쌓여 문서가 길어진다

지금 백로그 180줄 중 절반 이상이 완료 항목입니다.

> **대응**: 트랙이 끝나면 완료 항목을 한 문단으로 압축하고 상세는 git 히스토리에 맡기세요. 조직 보고로 이미 옮겨 적은 항목이라면 더 적극적으로 압축해도 됩니다(7장). "몇 개부터 압축할지" 구체적 임계값은 아직 없습니다(11장).
