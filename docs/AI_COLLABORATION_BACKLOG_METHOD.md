## 1. 무엇을 푸는 방법인가

**문제: AI 스레드는 매번 콜드 스타트한다.**

새 스레드는 지난주에 무엇을 왜 그렇게 정했는지 모릅니다. 사람이 매번 말로 설명하면 설명이 조금씩 달라지고, 그 편차가 그대로 구현 편차가 됩니다. 특히 **"왜 그렇게 안 했는가"**(검토했지만 버린 선택지)는 코드에 남지 않아 다음 스레드가 같은 논의를 처음부터 반복합니다.

**해법: 컨텍스트를 사람이 아니라 문서가 흡수한다.**

사람은 한 문장짜리 고정 프롬프트만 붙여 넣고, 나머지는 문서가 스레드에게 알려 줍니다. 스레드가 끝날 때 그 스레드가 알아낸 것을 다시 문서에 돌려놓습니다. 이 순환이 방법론의 전부입니다.

```
사람: 고정 프롬프트 한 줄 복붙
  ↓
스레드: 문서를 읽고 → 자기 일감을 집고 → 작업하고 → 문서에 결과를 돌려놓음
  ↓
사람: 승인
  ↓
(다음 스레드는 갱신된 문서에서 시작)
```

이 방식의 값어치는 **스레드가 끝나도 지식이 남는다**는 것입니다. 대화창은 사라져도 문서는 남습니다.

## 2. 포지셔닝 — 이 방법론이 아닌 것

**팀의 이슈 트래커(Jira·Linear·GitHub Issues)를 대체하는 도구가 아닙니다.** 이 방법론이 있는 이유는 오직 하나 — **AI 스레드가 콜드 스타트한다는 제약** — 뿐입니다. 그 제약이 없는 팀(사람만 일하는 팀)이라면 트래커가 대체로 낫습니다. 자세한 비교는 9장.

대신 이렇게 자리를 잡습니다 — 조직 트래커가 있다면 그 아래, AI 스레드보다는 위에:

```
[조직 레벨: 매크로 관리]      이슈 트래커 (Jira / Linear / GitHub Issues 등 — 있다면, 선택)
                                        │  ▲
                할당된 작업 단위를 수신  │  │ 완료 요약을 필요할 때 복사 (선택 — 6장)
                                        ▼  │
[개인/트랙 레벨: 마이크로 실행]  백로그 문서 + 스펙 문서 (이 방법론의 본체)
                                        │  ▲
                  고정 프롬프트 1줄 주입 │  │ [완료] 상태·산출물·발견점을 되돌려줌
                                        ▼  │
[AI 스레드: 순차 실행]         Claude 등 AI 작업 스레드
```

맨 위 계층은 **선택**입니다. 이 저장소 자체는 지금 그런 조직 트래커를 쓰고 있다는 근거가 없어서, 백로그 문서 하나만으로 이 트랙을 끝까지 운영했습니다. 트래커가 있는 사람은 6장을 보되, 6장은 아직 이 저장소에서 실측하지 않은 **설계 제안**이라는 점을 유의하세요.

### 이 방법론이 실제로 줄이는 것 (검증된 것만)

- **콜드 스타트 설명 비용**: 새 대화창마다 배경을 말로 다시 설명할 필요가 없습니다 — 문서가 대신 설명합니다.
- **"버린 선택지"의 재논의**: 4장 규칙 4(각주 역류)가 이걸 막습니다. 실측: 이 트랙에서 같은 논의가 스레드 간에 반복된 사례가 없습니다.
- **여러 트랙/기능을 오갈 때의 재파악 시간**: 백로그를 열면 그 트랙의 상태를 처음부터 다시 훑을 필요 없이 "완료/진행중/예정"만 보면 됩니다. ("0초"까지는 아닙니다 — 문서를 읽는 시간 자체는 듭니다.)

## 3. 전체 그림 — 문서 2개 + 프롬프트 1개

| 구성 | 역할 | 성격 |
| --- | --- | --- |
| **스펙 문서** (예: `..._KICKOFF_PLAN_....md`) | **왜 / 무엇을** 만드는가. 절 번호로 참조되는 원본 | 오래 산다. 결정이 append됨 |
| **백로그 문서** (예: `..._BACKLOG_....md`) | **누가 언제 무엇을** 하는가. 스레드 단위 일감과 상태 | 자주 바뀐다. 스레드마다 갱신 |
| **고정 프롬프트** | 새 스레드에 복붙하는 한 문장 | 거의 안 바뀐다 |

### 가장 중요한 규칙 하나

> **백로그는 스펙을 다시 쓰지 않는다. 절 번호만 가리킨다.**

이걸 어기면 같은 사실이 두 군데에 남고, 한쪽만 고쳐져 어긋납니다. 백로그 항목은 "참고: 4.2절"처럼 포인터만 두고, 설계 근거는 스펙에서 읽게 합니다.

같은 원리를 코드에도 적용합니다. 이번 트랙의 실제 사례 — 캐릭터의 출석 지급 일차는 **카탈로그 코드**(`BotUnlockSource.Attendance(tier)`)에만 적고, 보상 정책표는 그걸 읽어 갑니다. 정책표에도 적었다면 캐릭터 획득 경로가 바뀔 때마다 두 군데를 고쳐야 했을 것입니다.

### 고정 프롬프트 (그대로 쓰면 됩니다)

> 이번 스레드에서는 `<경로>/<백로그 파일명>.md` 이 파일의 내용을 파악하여 '예정사항'의 첫번째 항목을 파악하여 수행 담당해야합니다. 먼저 항목을 이해하셨다면 진행중으로 변경하고 작업 착수하시고, 결과물을 사용자와 논의 후 사용자가 완료 승인을 하면 문서에 완료 업데이트하고 당신의 스레드 업무가 종료되었다고 명시해주시면 됩니다.

짧지만 네 가지를 지시합니다 — **어떤 문서를 읽을지 / 어떤 항목을 집을지 / 상태를 언제 바꿀지 / 무엇으로 끝내는지.** 경로를 포함시키면 스레드가 파일을 찾는 탐색 한 단계를 아낍니다.

## 4. 백로그 문서 해부 — 5개 구성요소

실제 문서에서 그대로 뽑은 샘플입니다. 완료 항목은 아래 예시처럼 서술형으로 쌓여 있습니다 — **지금부터 새로 시작하는 트랙은 8장의 구조화 포맷을 권장**하지만, 이 절은 실제로 운영된 원본 그대로를 보여주는 것이 목적이라 고치지 않았습니다.

### ① 신규 스레드 착수 프로토콜

문서 맨 앞에 **스레드가 따라야 할 순서**를 둡니다. 이게 있으면 프롬프트가 짧아도 됩니다.

```
1. 읽기      — 백로그 전체 + 스펙의 공통 전제 절(2·3장) + 이번 항목이 가리키는 절.
              이 셋을 읽지 않고 바로 코드부터 작성하지 않는다.
2. 상태 전환 — 예정사항의 첫 번째 항목을 진행 중으로 옮기고 [진행중]을 붙인다.
              단, 문서에 이미 [진행중] 항목이 있다면 먼저 규칙 10(복구 확인)을 따른다.
3. 작업      — 해당 절의 스펙대로 구현한다. 범위 확장이나 다음 항목 선착수는 하지 않는다.
4. 막히면    — 스펙에 없는 정보는 먼저 코드를 직접 확인해 스스로 판단한다.
              그래도 답이 안 나오는 제품/설계 결정만 사용자에게 확인한다.
5. 완료 처리 — 사용자 승인 후에만. 완료 사항으로 옮기고 "산출물:" 한 줄을 추가한다.
6. 다음 안내 — 다음 항목 번호만 짧게 언급하고 마친다. 이때 서두의 파생 정보가
              여전히 맞는지 함께 확인한다.
```

### ② 서두 정리 — 매 스레드가 알아야 할 공통 전제

스코프, 항목 간 의존관계, 아직 미확정인 것. **"스레드가 대신 정하지 말 것"**을 여기에 명시합니다.

> 여기 적는 것 중 "의존관계"·"미확정 목록"은 항목 본문의 `선행 조건`·`착수 전 확인` 필드와 **내용이 겹칩니다** — 그래서 가장 빨리 낡습니다(7장 ① 참고). "스코프"(다루는 것/안 다루는 것)처럼 항목 단위로 쪼갤 수 없는 것만 최소로 남기는 것을 권장합니다.

### ③ 완료 사항 — 무엇이 남았는지가 아니라 **무엇을 알아냈는지**

```
6. 대국 히스토리 저장소 구현 — GameHistoryStorePort/GameHistoryEntry
   + 대국 종료 시 append 배선 (AI 모델: Sonnet, 노력정도: 중간) [완료]
   - 참고: 6장.
   - 산출물(shared): GameHistoryEntry.kt / GameHistoryPorts.kt / ...
     산출물(app-android): persistence/GameHistoryStore.kt + GameHistoryCodec ...
     구현 결정은 킥오프 플랜 6장 각주 참고 — 조사 중 발견한
     SidePlayerSetup.aiCharacterProfile()은 #8에 참고로 남김.
   - 전체 테스트·컴파일 통과, 사용자 승인 완료(2026-08-24).
```

완료 항목에서 값어치가 큰 것은 제목이 아니라 **"산출물:" 줄과 그 뒤에 붙는 발견**입니다. 위 예에서 "조사 중 발견한 `aiCharacterProfile()`은 #8에 참고로 남김" 한 줄이, 3일 뒤 #8 스레드가 같은 혼동을 겪지 않게 막아 줬습니다.

### ④ 진행 중 — 항상 0개 또는 1개

```
### 진행 중

(없음)
```

동시에 여러 스레드를 붙이지 않는 것이 전제입니다. 두 스레드가 같은 문서를 갱신하면 충돌하고, 무엇보다 앞 항목의 결정이 뒤 항목의 전제가 되는 구조라 병렬이 의미가 없습니다.

`(없음)`이 아니라 항목이 들어 있는 채로 새 스레드가 시작되면, 그건 **지난 스레드가 중간에 끊겼다는 신호**입니다 — 곧바로 이어받지 말고 규칙 10을 먼저 따르세요.

### ⑤ 예정 사항 — 다음 스레드가 집을 것

```
17. 소모품 인벤토리 상시 표시 — '형세보기: 30' / '추천 수: 30' / '광고 스킵권: 5'
    (AI 모델: Sonnet, 노력정도: 중간)
    - 참고: 4.5절. #15에서 확정했던 "잔량은 팝업 안에만"을 대체하는 항목이다 —
      팝업 안 표시는 그대로 두고, 상시 보이는 인벤토리를 추가한다.
    - 가장 중요한 요구사항은 "사용처 팝업이 뜰 때 잔여 개수가 확연히 보이면서
      차감되는 것이 보이는 것" — 숫자만 조용히 바뀌지 않게 할 것.
    - #16 완료 후 착수(지급량이 바뀌므로).
```

예정 항목에 반드시 들어가야 할 것: **참조 절 / 선행 조건 / 착수 전 확인이 필요한 것.**

### 항목 포맷

```
N. 제목 — 한 줄 요약 (AI 모델: <모델>, 노력정도: <낮음|중간|높음|최대>) [상태]
```

- **AI 모델**: 사람이 스레드를 어떤 모델로 띄울지 참고하는 값입니다. 스레드가 스스로 모델을 바꾸는 동작이 아닙니다.
- **노력정도**: 스레드를 나눌 단위를 가늠하는 값입니다. "최대"가 붙으면 그 항목 하나로 스레드를 통째로 씁니다. 완료 후에는 `중간 → 실제 높음`처럼 실제 소요를 덧붙입니다(규칙 4).

체크박스(`- [ ]`/`- [x]`) 문법은 쓰지 않습니다. 예정/진행중/완료는 **어느 섹션에 있는가 자체가 상태**인 3단 구조인데, 체크박스는 2단(했다/안 했다)뿐이라 "진행중"을 표현할 자리가 없습니다.

## 5. 운영 규칙 10가지

각 규칙 뒤에 **왜 그런지**를 적었습니다. 이유를 모르면 상황이 바뀔 때 잘못 응용하게 됩니다.

### 1. 번호는 식별자, 실행 순서는 목록에 적힌 물리적 위치

번호를 다시 매기지 않습니다. 완료 항목과 스펙 각주가 그 번호를 참조하고 있어서, 재번호는 그 참조를 전부 깨뜨립니다. 실제로 이 트랙은 `9 → 12 → 13 → 14 → 15 → 10 → 11` 순서로 실행됐습니다.

**실행 순서는 별도로 적지 않습니다 — 예정사항 목록에서 항목이 놓인 줄 순서 자체가 실행 순서입니다.** 우선순위가 바뀌면 항목을 목록 안에서 위아래로 옮기기만 하면 되고, "지금 실행 순서는 이렇다"는 문장을 어딘가에 따로 적어 둘 필요가 없습니다 — 적어 두면 그 문장 자체가 낡는 대상이 됩니다(7장 ①에서 실제로 겪은 문제).

### 2. 완료 항목은 불변 — 바뀌면 되돌리지 말고 새 일감을 세운다

완료 기록은 "그때 무엇을 왜 그렇게 했는가"의 히스토리입니다. 나중에 방향이 바뀌었다고 그 기록을 고치면 히스토리가 사라집니다.

> **실제 사례**: 2026-08-24에 보상 구조가 전면 재확정되면서 완료 항목 #8·#9·#12·#13·#15의 산출물을 고쳐야 하게 됐습니다. 그 항목들을 되돌리는 대신 **새 일감 #16**을 세웠습니다. 덕분에 "왜 처음엔 5종을 전부 잠갔다가 되돌렸는가"가 그대로 남아 있습니다.

### 3. 완료 시 "산출물:" 한 줄은 필수

실제로 바뀐 파일을 적습니다. 이게 없으면 몇 주 뒤 "그 기능 어디 있죠?"를 코드 검색으로 찾아야 합니다.

### 4. 노력정도 추정 오차를 기록한다 (`예상 → 실제`)

완료 항목에 `노력정도: 중간 → 실제: 높음`처럼 실제 소요를 덧붙입니다. 이 트랙에서 두 번 빗나갔습니다 — #15는 "높음"으로 잡았는데 사용자 답변이 새 요구사항을 낳아 더 커졌고, #11은 "중간"에서 "높음"으로 올라갔습니다. 이런 기록이 쌓이면 다음 일감을 쪼갤 때의 감각이 좋아집니다. (다만 이 규칙 자체가 추정을 잘하게 만들어주는 건 아닙니다 — "기록이 쌓이는 것"만 보장합니다. 실제로 감이 좋아지는지는 더 지나 봐야 압니다.)

### 5. 구현 결정은 스펙 문서에 각주로 역류시킨다

작업 중에 내린 판단은 백로그가 아니라 **스펙 쪽에 각주**로 붙입니다. 이 저장소의 실제 각주(2026-08-24, 소모품 소비 배선 항목):

```
> 구현 결정(백로그 #12, 2026-08-24):
> 4. FeatureAccessPolicy를 고쳐 소모품을 네 번째 허용 경로로 넣지 않았다.
>    그 함수는 부수효과 없는 조회(resolve)인데 소모품은 보는 순간 줄어드는
>    자원이라, 합치면 "확인만 했는데 재고가 닳는" 구조가 된다. 대신 우선순위
>    규칙을 별도 순수 함수 decideConsumableSpend에 담고, "이미 쓸 수 있는가"
>    판정은 기존 resolve에 위임해 정책이 두 군데로 갈라지지 않게 했다.
```

백로그는 자주 갈아엎히지만 스펙은 오래 삽니다. **버린 선택지와 그 이유**를 여기 남기는 것이 이 방법론에서 가장 값어치가 큰 습관입니다 — 코드 주석은 "무엇을 했는지"를 말하지만, 이 각주는 "무엇을 안 했는지"를 말합니다.

### 6. "착수 전 확인(사용자)"을 항목에 미리 박아 둔다

AI가 대신 정하면 안 되는 것(제품 결정, 가격, 콘텐츠)을 **항목에 미리 표기**합니다. 스레드는 그걸 보고 그 시점에 사람에게 묻습니다.

```
- 착수 전 확인(사용자): '광고 스킵권' 1회의 범위(대국 1판인지 광고 1회인지)와
  스킵 대상 광고 노출 지점. 이게 정해져야 차감 단위가 결정된다.
```

### 7. 범위 확장 금지 / 다음 항목 선착수 금지

AI는 "이왕 하는 김에"에 취약합니다. 프로토콜 3단계에 명시적으로 금지어를 둡니다.

### 8. 완료는 사람 승인 후에만

스레드가 스스로 완료 처리하지 않습니다. 승인 게이트가 없으면 문서가 "다 됐다고 주장하는" 상태로 흘러갑니다.

### 9. 커밋 시점은 사람이 정하고, 검증 명령은 문서에 적어 둔다

스레드가 임의로 커밋하지 않습니다. 커밋 메시지 형식(`feat(scope): ... (backlog #N)`)을 정해 두면 나중에 `git log --grep "backlog #"`로 트랙 전체를 훑을 수 있습니다.

새 스레드는 빌드 환경도 모릅니다. **환경 함정이 있으면 반드시 적습니다.**

```
- 검증 명령: 이 저장소는 JDK 17이 필요하다 — 시스템 기본 JDK로 돌리면
  Gradle이 `25` 한 줄만 뱉고 즉시 실패해 원인을 찾기 어렵다.
```

이 한 줄이 없으면 모든 새 스레드가 같은 함정에 한 번씩 빠집니다.

### 10. `[진행중]` 항목을 발견하면 먼저 `git status`로 확인한다

스레드는 착수 즉시(작업을 끝내기 전에) 백로그 파일에 `[진행중]`을 씁니다 — 그래야 문서를 여는 사람이나 다음 스레드가 "지금 뭔가 진행 중이다"를 즉시 알 수 있습니다. 다만 그 스레드가 중간에 끊기면(에러, 세션 종료 등) 파일에는 `[진행중]` 표시만 남고 실제 작업은 반쯤 걸쳐 있을 수 있습니다.

그래서 새 스레드가 `### 진행 중`에 `(없음)`이 아니라 항목이 있는 걸 발견하면, 곧바로 이어서 작업하지 말고 **`git status`/`git diff`로 워킹 트리에 실제 무엇이 바뀌어 있는지 먼저 확인**합니다. 커밋 안 된 변경이 있으면 그게 그 항목의 미완성 작업입니다 — 이어갈지 되돌릴지 판단합니다. 아무 변경도 없으면 상태 표시만 남은 것이므로 예정사항으로 되돌리고 처음부터 다시 시작해도 안전합니다.

## 6. 조직 트래커·보고 주기에 연계하고 싶다면 (선택)

⚠️ **이 절은 이 저장소에서 실측한 게 아니라 설계 제안입니다.** 조직 트래커나 정기 보고가 없다면 건너뛰어도 방법론의 나머지는 전부 그대로 작동합니다 — 지금까지 이 트랙도 이 절 없이 14개 항목을 끝냈습니다.

**아이디어**: 완료 항목을 8장 템플릿처럼 구조화된 필드(산출물 / 커밋 / 승인일 / 비고)로 적어 두면, 그 필드를 그대로 복사해 보고 텍스트로 옮길 수 있습니다. 별도로 "이번 주에 뭘 했지"를 회상하거나 git 로그를 뒤질 필요가 없습니다.

```
[완료 항목 필드]                    [보고 텍스트로 그대로 옮김]
- 산출물: AppDatabase.kt 외 2건  →  "산출물: AppDatabase.kt 외 2건"
- 비고: 레거시 마이그레이션 스킵  →  "특이사항: 레거시 마이그레이션 스킵"
- 커밋: feat(history): ... #13   →  (PR/커밋 링크로 그대로 첨부)
```

### 반드시 정하고 넘어가야 할 긴장 하나

완료 항목을 보고 원본으로 계속 쓰려면 **영구 보관**해야 할 것 같지만, 이건 7장 ④의 "완료 항목이 쌓여 문서가 길어진다"는 문제와 정면으로 부딪힙니다. 해법은 **역할을 분리**하는 것입니다 — 완료 항목을 보고서나 트래커에 옮겨 적은 **그 시점부터는, 그 보고서·트래커가 영구 기록**이고, 백로그 쪽 항목은 압축해도 됩니다. 백로그는 애초에 "AI 스레드의 컨텍스트용"이 본업이지 "조직의 감사 기록 보관소"가 아닙니다 — 이 저장소의 문서 보존 정책(`docs/DOCS_INDEX.md`: "결론이 상위 문서에 흡수되면 삭제한다, git이 아카이브다")과 같은 원리입니다.

트래커 연계를 쓰기로 했다면, 항목 헤더에 `연계 이슈: <트래커 키>` 필드를 추가하는 것 정도만 8장 템플릿에 더하면 됩니다 — 그 이상(일일/주간/월간 각각의 정형화된 문구, "정합성 100%" 같은 보장)은 이 저장소에서 검증되지 않았으므로 이 문서가 대신 약속하지 않습니다.

## 7. 실제로 겪은 마찰과 대응

정직하게 적습니다. 이 방법론에도 비용이 있습니다.

### ① 파생 정보가 빨리 낡는다 — 가장 자주 생기는 문제

서두의 "의존관계 / 미확정 목록"은 **항목에서 계산할 수 있는 정보를 복제**한 것입니다. 편하지만 그만큼 빨리 낡습니다. 이 트랙에서만 이틀 새 두 번 갱신했고, 한 번은 실행 순서를 적어 둔 문장이 낡은 채로 남아 **새 스레드가 이미 끝난 항목을 집을 뻔했습니다.**

> **대응**: 실행 순서 자체는 규칙 1로 해소됐습니다(문장으로 안 적고 목록 위치로 표현). 남은 것은 "의존관계/미확정" 같이 여전히 프로즈로 요약되는 정보인데, 이건 애초에 항목 본문(`선행 조건`/`착수 전 확인`)에서 계산 가능하므로 **최소화하는 것**이 근본 대응입니다(4장 ② 참고). 그래도 서두 요약을 쓴다면, 스레드 종료 6단계에 "여전히 맞는지 확인"을 넣으세요.

### ② 노력정도 추정이 빗나간다

이제 규칙 4로 승격됐습니다(위 5장 참고) — 다만 규칙을 만든다고 추정이 바로 정확해지는 건 아닙니다. "예상 → 실제" 기록이 쌓여야 다음 분할 감각이 좋아지는데, 아직 데이터가 몇 건뿐이라 이 트랙에서는 검증되지 않았습니다.

### ③ 사용자 답변이 새 요구사항이 될 때

"1회권의 소비 단위가 무엇인가?"라고 물었더니 **"토글은 유지하고 1회권은 단발성으로"**라는 새 설계가 돌아왔습니다. 확인 질문이 스코프를 키운 경우입니다.

> **대응**: 이럴 때 스레드는 **별도 일감으로 뗄지 여기서 할지 판단하고 근거를 밝혀야** 합니다. 이 사례는 "단발성 모드는 1회권 말고 진입점이 없어서 떼면 실행할 수 없는 일감이 된다"는 이유로 같은 항목에서 처리했고, 그 판단 근거를 스펙 각주에 남겼습니다. 이건 규칙으로 자동화할 수 없는 부분입니다 — 매번 판단하고 매번 근거를 남기는 수밖에 없습니다.

### ④ 완료 항목이 쌓여 문서가 길어진다

지금 백로그 180줄 중 절반 이상이 완료 항목입니다. 아직 감당 가능하지만 계속 자랍니다.

> **대응**: 트랙이 끝나면 완료 항목을 한 문단으로 압축하고 상세는 git 히스토리에 맡기세요. 조직 보고로 이미 옮겨 적은 항목이라면 더 적극적으로 압축해도 됩니다(6장). 다만 "몇 개부터 압축할지" 같은 구체적인 임계값은 아직 이 방법론에 없습니다 — 10장 참고.

## 8. 이식용 템플릿

새 트랙을 시작할 때 이 골격을 복사해 채우면 됩니다.

```markdown
# <트랙 이름> 개발 일감 백로그

작성일: YYYY-MM-DD

이 문서는 `<스펙 문서 파일명>`(설계/스펙)을 **새 스레드 단위로 순차 착수 가능한 일감**으로
쪼갠 진행 관리 문서입니다. 설계 근거나 상세 규칙은 다시 쓰지 않고 스펙의 절 번호만 가리킵니다.

**갱신 규칙**: "완료 사항 / 진행 중 / 예정사항" 3단 구조와 각 항목의

그 항목을 해당 섹션으로 옮기며 갱신합니다. 번호는 전체를 통틀어 하나의 연속된 시퀀스입니다.

## 신규 스레드 착수 프로토콜

**매번 새 스레드에 넣는 고정 프롬프트** (그대로 복사해서 사용):

> 이번 스레드에서는 `<경로>/<이 파일명>` 이 파일의 내용을 파악하여 '예정사항'의 첫번째
> 항목을 파악하여 수행 담당해야합니다. 먼저 항목을 이해하셨다면 진행중으로 변경하고 작업
> 착수하시고, 결과물을 사용자와 논의 후 사용자가 완료 승인을 하면 문서에 완료 업데이트하고
> 당신의 스레드 업무가 종료되었다고 명시해주시면 됩니다.

이 프롬프트를 받은 스레드가 따라야 할 순서:

1. **읽기** — 이 백로그 전체 + 스펙의 공통 전제 절(<절 번호>) + 이번 항목이 가리키는 절.
2. **상태 전환** — `### 진행 중`이 `(없음)`인지 먼저 확인한다. 항목이 이미 있다면 이어받기
   전에 `git status`/`git diff`로 실제 무엇이 바뀌어 있는지 확인한다(운영 규칙 10).
   `(없음)`이면 예정사항의 첫 번째 항목을 진행 중으로 옮기고 `[진행중]`을 붙인다.
3. **작업** — 스펙대로 구현한다. 범위 확장이나 다음 항목 선착수는 하지 않는다.
4. **막히면** — 코드를 먼저 확인해 스스로 판단하고, 제품/설계 결정만 사용자에게 확인한다.
5. **완료 처리** — 사용자 승인 후에만. 아래 필드를 채운다.
6. **다음 안내** — 다음 항목 번호만 짧게 언급하고 마친다. 이때 서두의 파생 정보가
   여전히 맞는지 함께 확인한다.

**참고사항**
- `AI 모델` 표기는 사람이 참고하는 값이다 — 스레드가 스스로 모델을 바꾸는 동작이 아니다.
- 동시에 여러 스레드를 이 백로그에 붙이지 않는다 — 순차 실행을 전제로 설계됐다.
- **검증 명령**: <빌드/테스트 명령, 환경 함정이 있으면 반드시 명시>
- **커밋 시점은 사용자가 정한다** — 지시가 있을 때 커밋하며, 메시지는 `<형식> (backlog #N)`.
- **(선택) 조직 트래커 연계**: 쓰는 경우에만 각 항목에 `연계 이슈: <트래커 키>`를 추가한다.
```

## 9. 이 방식이 맞는 팀 / 아닌 팀

### 이슈 트래커(Jira·Linear·GitHub Issues)와 무엇이 다른가

| | 단일 문서 백로그 | 이슈 트래커 |
| --- | --- | --- |
| **AI에게 통째로 먹이기** | 파일 하나 = 전체 맥락. **결정적 장점** | 이슈를 하나씩 조회해야 하고 맥락이 흩어짐 |
| 검색·필터·대시보드 | 없음(파일 검색뿐) | 강함 |
| 여러 사람 동시 작업 | 약함(충돌) | 강함 |
| 결정 근거 보존 | 스펙 각주로 강하게 남음 | 코멘트에 묻히기 쉬움 |
| 변경 이력 | git diff로 정확히 추적 | 트래커 자체 이력 |
| 도입 비용 | 파일 하나 | 계정·워크플로 설정 |

**결론: 트래커를 대체하는 방법이 아닙니다.** 이 방식의 존재 이유는 **AI 스레드가 콜드 스타트한다는 제약** 하나입니다. 그 제약이 없는 팀이라면 트래커가 대체로 낫습니다.

### 맞는 경우

- **AI 스레드를 주 실행 주체로 쓰는 작업.** 이게 핵심 조건입니다.
- 한 사람(또는 한 스레드)이 순차로 진행하는 트랙.
- 항목 간 결정이 서로 전제가 되는 작업 — 앞 항목의 판단이 뒤 항목의 입력이 되는 구조.
- 기간이 몇 주 단위인 트랙. 몇 달을 넘어가면 완료 항목이 문서를 압도합니다.

### 맞지 않는 경우

- 여러 사람이 **동시에** 다른 항목을 진행 → 문서 충돌. 트래커를 쓰세요.
- 항목이 서로 독립적이고 순서가 상관없는 작업 → 문서 한 줄로 묶을 이유가 없습니다.
- 경영진·이해관계자가 **실시간 대시보드**를 봐야 하는 경우 → 6장은 텍스트 스냅샷을 손으로 옮기는 것이지 실시간 연동이 아닙니다.

### 절충안

트래커를 쓰되 **각 에픽마다 이 백로그 문서 하나를 저장소에 두는** 방식이 실용적입니다. 트래커는 사람의 조율용, 문서는 AI 스레드의 컨텍스트용으로 역할을 나눕니다. 6장은 그 둘을 잇는 다리입니다.

## 10. 더 나아가려면 — 이 방법론의 다음 개선안

아직 도입/검증하지 않은 것들입니다.

1. **완료 항목 압축 임계를 정한다.** "완료 항목이 N개를 넘으면 오래된 것부터 한 문단으로 압축한다" 같은 구체적 규칙이 아직 없습니다. 상세는 git 히스토리가 보관합니다.
2. **6장(조직 보고 연계)을 실전에서 검증한다.** 지금은 설계 제안일 뿐입니다 — 실제로 트래커에 연계해 몇 주 돌려본 뒤, 어떤 필드가 실제로 쓸모 있고 어떤 건 군더더기인지 다시 정리해야 합니다.
3. **서두 파생 정보를 더 줄인다.** 실행 순서는 규칙 1로 해소됐지만, "의존관계/미확정" 요약은 여전히 항목 본문과 겹칩니다. 아예 없애고 항목만 신뢰하는 쪽으로 갈지, 최소 요약을 남길지는 아직 정하지 않았습니다.
