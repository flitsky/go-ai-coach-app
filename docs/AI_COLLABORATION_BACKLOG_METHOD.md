## 1. 무엇을 푸는 방법인가

**문제: AI 스레드는 매번 콜드 스타트한다.**

새 스레드는 지난주에 무엇을 왜 그렇게 정했는지 모릅니다. 사람이 매번 말로 설명하면 설명이 조금씩 달라지고, 그 편차가 그대로 구현 편차가 됩니다. 특히 **"왜 그렇게 안 했는가"**(검토했지만 버린 선택지)는 코드에 남지 않아 다음 스레드가 같은 논의를 처음부터 반복합니다.

**해법: 컨텍스트를 사람이 아니라 문서가 흡수한다.**

사람은 한 문장짜리 고정 프롬프트만 붙여 넣고, 나머지는 문서가 스레드에게 알려 줍니다. 스레드가 끝날 때 그 스레드가 알아낸 것을 다시 문서에 돌려놓습니다. 이 순환이 방법론의 전부입니다.

```
사람: 고정 프롬프트 한 줄 복붙
  ↓
스레드: 문서를 읽고 → 자기 일감을 집고 → 작업하고 → 문서에 결과를 돌려놓음
  ↓
사람: 승인
  ↓
(다음 스레드는 갱신된 문서에서 시작)
```

이 방식의 값어치는 **스레드가 끝나도 지식이 남는다**는 것입니다. 대화창은 사라져도 문서는 남습니다.

## 2. 전체 그림 — 문서 2개 + 프롬프트 1개

| 구성 | 역할 | 성격 |
| --- | --- | --- |
| **스펙 문서** (예: `..._KICKOFF_PLAN_....md`) | **왜 / 무엇을** 만드는가. 절 번호로 참조되는 원본 | 오래 산다. 결정이 append됨 |
| **백로그 문서** (예: `..._BACKLOG_....md`) | **누가 언제 무엇을** 하는가. 스레드 단위 일감과 상태 | 자주 바뀐다. 스레드마다 갱신 |
| **고정 프롬프트** | 새 스레드에 복붙하는 한 문장 | 거의 안 바뀐다 |

### 가장 중요한 규칙 하나

> **백로그는 스펙을 다시 쓰지 않는다. 절 번호만 가리킨다.**

이걸 어기면 같은 사실이 두 군데에 남고, 한쪽만 고쳐져 어긋납니다. 백로그 항목은 "참고: 4.2절"처럼 포인터만 두고, 설계 근거는 스펙에서 읽게 합니다.

같은 원리를 코드에도 적용합니다. 이번 트랙의 실제 사례 — 캐릭터의 출석 지급 일차는 **카탈로그 코드**(`BotUnlockSource.Attendance(tier)`)에만 적고, 보상 정책표는 그걸 읽어 갑니다. 정책표에도 적었다면 캐릭터 획득 경로가 바뀔 때마다 두 군데를 고쳐야 했을 것입니다.

### 고정 프롬프트 (그대로 쓰면 됩니다)

> 이번 스레드에서는 `<경로>/<백로그 파일명>.md` 이 파일의 내용을 파악하여 '예정사항'의 첫번째 항목을 파악하여 수행 담당해야합니다. 먼저 항목을 이해하셨다면 진행중으로 변경하고 작업 착수하시고, 결과물을 사용자와 논의 후 사용자가 완료 승인을 하면 문서에 완료 업데이트하고 당신의 스레드 업무가 종료되었다고 명시해주시면 됩니다.

짧지만 네 가지를 지시합니다 — **어떤 문서를 읽을지 / 어떤 항목을 집을지 / 상태를 언제 바꿀지 / 무엇으로 끝내는지.** 경로를 포함시키면 스레드가 파일을 찾는 탐색 한 단계를 아낍니다.

## 3. 백로그 문서 해부 — 5개 구성요소

실제 문서에서 그대로 뽑은 샘플입니다.

### ① 신규 스레드 착수 프로토콜

문서 맨 앞에 **스레드가 따라야 할 순서**를 둡니다. 이게 있으면 프롬프트가 짧아도 됩니다.

```
1. 읽기      — 백로그 전체 + 스펙의 공통 전제 절(2·3장) + 이번 항목이 가리키는 절.
              이 셋을 읽지 않고 바로 코드부터 작성하지 않는다.
2. 상태 전환 — 예정사항의 첫 번째 항목을 진행 중으로 옮기고 [진행중]을 붙인다.
3. 작업      — 해당 절의 스펙대로 구현한다. 범위 확장이나 다음 항목 선착수는 하지 않는다.
4. 막히면    — 스펙에 없는 정보는 먼저 코드를 직접 확인해 스스로 판단한다.
              그래도 답이 안 나오는 제품/설계 결정만 사용자에게 확인한다.
5. 완료 처리 — 사용자 승인 후에만. 완료 사항으로 옮기고 "산출물:" 한 줄을 추가한다.
6. 다음 안내 — 다음 항목 번호만 짧게 언급하고 마친다.
```

### ② 서두 정리 — 매 스레드가 알아야 할 공통 전제

스코프, 항목 간 의존관계, 아직 미확정인 것. **"스레드가 대신 정하지 말 것"**을 여기에 명시합니다.

### ③ 완료 사항 — 무엇이 남았는지가 아니라 **무엇을 알아냈는지**

```
6. 대국 히스토리 저장소 구현 — GameHistoryStorePort/GameHistoryEntry
   + 대국 종료 시 append 배선 (AI 모델: Sonnet, 노력정도: 중간) [완료]
   - 참고: 6장.
   - 산출물(shared): GameHistoryEntry.kt / GameHistoryPorts.kt / ...
     산출물(app-android): persistence/GameHistoryStore.kt + GameHistoryCodec ...
     구현 결정은 킥오프 플랜 6장 각주 참고 — 조사 중 발견한
     SidePlayerSetup.aiCharacterProfile()은 #8에 참고로 남김.
   - 전체 테스트·컴파일 통과, 사용자 승인 완료(2026-08-24).
```

완료 항목에서 값어치가 큰 것은 제목이 아니라 **"산출물:" 줄과 그 뒤에 붙는 발견**입니다. 위 예에서 "조사 중 발견한 `aiCharacterProfile()`은 #8에 참고로 남김" 한 줄이, 3일 뒤 #8 스레드가 같은 혼동을 겪지 않게 막아 줬습니다.

### ④ 진행 중 — 항상 0개 또는 1개

```
### 진행 중

(없음)
```

동시에 여러 스레드를 붙이지 않는 것이 전제입니다. 두 스레드가 같은 문서를 갱신하면 충돌하고, 무엇보다 앞 항목의 결정이 뒤 항목의 전제가 되는 구조라 병렬이 의미가 없습니다.

### ⑤ 예정 사항 — 다음 스레드가 집을 것

```
17. 소모품 인벤토리 상시 표시 — '형세보기: 30' / '추천 수: 30' / '광고 스킵권: 5'
    (AI 모델: Sonnet, 노력정도: 중간)
    - 참고: 4.5절. #15에서 확정했던 "잔량은 팝업 안에만"을 대체하는 항목이다 —
      팝업 안 표시는 그대로 두고, 상시 보이는 인벤토리를 추가한다.
    - 가장 중요한 요구사항은 "사용처 팝업이 뜰 때 잔여 개수가 확연히 보이면서
      차감되는 것이 보이는 것" — 숫자만 조용히 바뀌지 않게 할 것.
    - #16 완료 후 착수(지급량이 바뀌므로).
```

예정 항목에 반드시 들어가야 할 것: **참조 절 / 선행 조건 / 착수 전 확인이 필요한 것.**

### 항목 포맷

```
N. 제목 — 한 줄 요약 (AI 모델: <모델>, 노력정도: <낮음|중간|높음|최대>) [상태]
```

- **AI 모델**: 사람이 스레드를 어떤 모델로 띄울지 참고하는 값입니다. 스레드가 스스로 모델을 바꾸는 동작이 아닙니다.
- **노력정도**: 스레드를 나눌 단위를 가늠하는 값입니다. "최대"가 붙으면 그 항목 하나로 스레드를 통째로 씁니다.

## 4. 운영 규칙 9가지

각 규칙 뒤에 **왜 그런지**를 적었습니다. 이유를 모르면 상황이 바뀔 때 잘못 응용하게 됩니다.

### 1. 번호는 식별자, 실행 순서는 목록에 적힌 순서

번호를 다시 매기지 않습니다. 완료 항목과 스펙 각주가 그 번호를 참조하고 있어서, 재번호는 그 참조를 전부 깨뜨립니다. 실제로 이 트랙은 `9 → 12 → 13 → 14 → 15 → 10 → 11` 순서로 실행됐습니다.

> **주의**: 순서가 번호와 어긋나면 그 사실을 예정사항 머리말에 크게 적어야 합니다. 안 적으면 새 스레드가 번호 순으로 집습니다.

### 2. 완료 항목은 불변 — 바뀌면 되돌리지 말고 새 일감을 세운다

완료 기록은 "그때 무엇을 왜 그렇게 했는가"의 히스토리입니다. 나중에 방향이 바뀌었다고 그 기록을 고치면 히스토리가 사라집니다.

> **실제 사례**: 2026-08-24에 보상 구조가 전면 재확정되면서 완료 항목 #8·#9·#12·#13·#15의 산출물을 고쳐야 하게 됐습니다. 그 항목들을 되돌리는 대신 **새 일감 #16**을 세웠습니다. 덕분에 "왜 처음엔 5종을 전부 잠갔다가 되돌렸는가"가 그대로 남아 있습니다.

### 3. 완료 시 "산출물:" 한 줄은 필수

실제로 바뀐 파일을 적습니다. 이게 없으면 몇 주 뒤 "그 기능 어디 있죠?"를 코드 검색으로 찾아야 합니다.

### 4. 구현 결정은 스펙 문서에 각주로 역류시킨다

작업 중에 내린 판단은 백로그가 아니라 **스펙 쪽에 각주**로 붙입니다.

```
> 구현 결정(백로그 #12, 2026-08-24):
> 4. FeatureAccessPolicy를 고쳐 소모품을 네 번째 허용 경로로 넣지 않았다.
>    그 함수는 부수효과 없는 조회(resolve)인데 소모품은 보는 순간 줄어드는 자원이라,
>    같은 함수에 합치면 "확인만 했는데 재고가 닳는" 구조가 된다.
```

백로그는 자주 갈아엎히지만 스펙은 오래 삽니다. **버린 선택지와 그 이유**를 여기 남기는 것이 이 방법론에서 가장 값어치가 큰 습관입니다 — 코드 주석은 "무엇을 했는지"를 말하지만, 이 각주는 "무엇을 안 했는지"를 말합니다.

### 5. "착수 전 확인(사용자)"을 항목에 미리 박아 둔다

AI가 대신 정하면 안 되는 것(제품 결정, 가격, 콘텐츠)을 **항목에 미리 표기**합니다. 스레드는 그걸 보고 그 시점에 사람에게 묻습니다.

```
- 착수 전 확인(사용자): '광고 스킵권' 1회의 범위(대국 1판인지 광고 1회인지)와
  스킵 대상 광고 노출 지점. 이게 정해져야 차감 단위가 결정된다.
```

### 6. 범위 확장 금지 / 다음 항목 선착수 금지

AI는 "이왕 하는 김에"에 취약합니다. 프로토콜 3단계에 명시적으로 금지어를 둡니다.

### 7. 완료는 사람 승인 후에만

스레드가 스스로 완료 처리하지 않습니다. 승인 게이트가 없으면 문서가 "다 됐다고 주장하는" 상태로 흘러갑니다.

### 8. 커밋 시점은 사람이 정한다

스레드가 임의로 커밋하지 않습니다. 커밋 메시지 형식(`feat(scope): ... (backlog #N)`)을 정해 두면 나중에 `git log --grep "backlog #"`로 트랙 전체를 훑을 수 있습니다.

### 9. 검증 명령을 문서에 적어 둔다

새 스레드는 빌드 환경을 모릅니다. **환경 함정이 있으면 반드시 적습니다.**

```
- 검증 명령: 이 저장소는 JDK 17이 필요하다 — 시스템 기본 JDK로 돌리면
  Gradle이 `25` 한 줄만 뱉고 즉시 실패해 원인을 찾기 어렵다.
```

이 한 줄이 없으면 모든 새 스레드가 같은 함정에 한 번씩 빠집니다.

## 5. 실제로 겪은 마찰과 대응

정직하게 적습니다. 이 방법론에도 비용이 있습니다.

### ① 파생 정보가 빨리 낡는다 — 가장 자주 생기는 문제

서두의 "의존관계 / 미확정 목록"은 **항목에서 계산할 수 있는 정보를 복제**한 것입니다. 편하지만 그만큼 빨리 낡습니다. 이 트랙에서만 이틀 새 두 번 갱신했고, 한 번은 실행 순서가 낡은 채로 남아 **새 스레드가 이미 끝난 항목을 집을 뻔했습니다.**

> **대응**: 스레드 종료 시 6단계에 "서두의 파생 정보(순서·의존관계·미확정)가 여전히 맞는지 확인한다"를 넣으세요. 또는 파생 정보를 아예 줄이고 항목 본문만 신뢰하게 하세요.

### ② 노력정도 추정이 빗나간다

이 트랙에서 두 번 빗나갔습니다 — #15는 "높음"으로 잡았는데 사용자 답변이 새 요구사항(단발성 동작)을 낳아 훨씬 커졌고, #11은 "중간"에서 "높음"으로 올라갔습니다.

> **대응**: 완료 항목에 **실제 소요를 함께 적으세요**(예: `노력정도: 중간 → 실제 높음`). 몇 개 쌓이면 추정이 눈에 띄게 정확해집니다. 이 트랙은 아직 안 하고 있는데, 도입할 만한 개선입니다.

### ③ 사용자 답변이 새 요구사항이 될 때

"1회권의 소비 단위가 무엇인가?"라고 물었더니 **"토글은 유지하고 1회권은 단발성으로"**라는 새 설계가 돌아왔습니다. 확인 질문이 스코프를 키운 경우입니다.

> **대응**: 이럴 때 스레드는 **별도 일감으로 뗄지 여기서 할지 판단하고 근거를 밝혀야** 합니다. 이 사례는 "단발성 모드는 1회권 말고 진입점이 없어서 떼면 실행할 수 없는 일감이 된다"는 이유로 같은 항목에서 처리했고, 그 판단 근거를 스펙 각주에 남겼습니다.

### ④ 완료 항목이 쌓여 문서가 길어진다

지금 백로그 180줄 중 절반 이상이 완료 항목입니다. 아직 감당 가능하지만 계속 자랍니다.

> **대응**: 트랙이 끝나면 완료 항목을 한 문단으로 압축하고 상세는 git 히스토리에 맡기세요. 이 저장소의 문서 보존 정책(`docs/DOCS_INDEX.md`)이 이미 같은 원리입니다 — "결론이 상위 문서에 흡수되면 삭제한다, git이 아카이브다".

## 신규 스레드 착수 프로토콜

**매번 새 스레드에 넣는 고정 프롬프트** (그대로 복사해서 사용):

> 이번 스레드에서는 `<경로>/<이 파일명>` 이 파일의 내용을 파악하여 '예정사항'의 첫번째
> 항목을 파악하여 수행 담당해야합니다. 먼저 항목을 이해하셨다면 진행중으로 변경하고 작업
> 착수하시고, 결과물을 사용자와 논의 후 사용자가 완료 승인을 하면 문서에 완료 업데이트하고
> 당신의 스레드 업무가 종료되었다고 명시해주시면 됩니다.

이 프롬프트를 받은 스레드가 따라야 할 순서:

1. **읽기** — 이 백로그 전체 + 스펙의 공통 전제 절(<절 번호>) + 이번 항목이 가리키는 절.
2. **상태 전환** — 예정사항의 첫 번째 항목을 진행 중으로 옮기고 `[진행중]`을 붙인다.
3. **작업** — 스펙대로 구현한다. 범위 확장이나 다음 항목 선착수는 하지 않는다.
4. **막히면** — 코드를 먼저 확인해 스스로 판단하고, 제품/설계 결정만 사용자에게 확인한다.
5. **완료 처리** — 사용자 승인 후에만. "산출물:" 한 줄을 남긴다.
6. **다음 안내** — 다음 항목 번호만 짧게 언급하고 마친다. 이때 서두의 파생 정보
   (실행 순서·의존관계·미확정 목록)가 여전히 맞는지 함께 확인한다.

**참고사항**
- `AI 모델` 표기는 사람이 참고하는 값이다 — 스레드가 스스로 모델을 바꾸는 동작이 아니다.
- 동시에 여러 스레드를 이 백로그에 붙이지 않는다 — 순차 실행을 전제로 설계됐다.
- **검증 명령**: <빌드/테스트 명령, 환경 함정이 있으면 반드시 명시>
- **커밋 시점은 사용자가 정한다** — 지시가 있을 때 커밋하며, 메시지는 `<형식> (backlog #N)`.

## 7. 이 방식이 맞는 팀 / 아닌 팀

### 이슈 트래커(Jira·Linear·GitHub Issues)와 무엇이 다른가

| | 단일 문서 백로그 | 이슈 트래커 |
| --- | --- | --- |
| **AI에게 통째로 먹이기** | 파일 하나 = 전체 맥락. **결정적 장점** | 이슈를 하나씩 조회해야 하고 맥락이 흩어짐 |
| 검색·필터·대시보드 | 없음(파일 검색뿐) | 강함 |
| 여러 사람 동시 작업 | 약함(충돌) | 강함 |
| 결정 근거 보존 | 스펙 각주로 강하게 남음 | 코멘트에 묻히기 쉬움 |
| 변경 이력 | git diff로 정확히 추적 | 트래커 자체 이력 |
| 도입 비용 | 파일 하나 | 계정·워크플로 설정 |

**결론: 트래커를 대체하는 방법이 아닙니다.** 이 방식의 존재 이유는 **AI 스레드가 콜드 스타트한다는 제약** 하나입니다. 그 제약이 없는 팀(사람만 일하는 팀)이라면 트래커가 대체로 낫습니다.

### 맞는 경우

- **AI 스레드를 주 실행 주체로 쓰는 작업.** 이게 핵심 조건입니다.
- 한 사람(또는 한 스레드)이 순차로 진행하는 트랙.
- 항목 간 결정이 서로 전제가 되는 작업 — 앞 항목의 판단이 뒤 항목의 입력이 되는 구조.
- 기간이 몇 주 단위인 트랙. 몇 달을 넘어가면 완료 항목이 문서를 압도합니다.

### 맞지 않는 경우

- 여러 사람이 **동시에** 다른 항목을 진행 → 문서 충돌. 트래커를 쓰세요.
- 항목이 서로 독립적이고 순서가 상관없는 작업 → 문서 한 줄로 묶을 이유가 없습니다.
- 외부 이해관계자에게 진행 상황을 보고해야 하는 경우 → 대시보드가 필요합니다.

### 절충안

트래커를 쓰되 **각 에픽마다 이 백로그 문서 하나를 저장소에 두는** 방식이 실용적입니다. 트래커는 사람의 조율용, 문서는 AI 스레드의 컨텍스트용으로 역할을 나눕니다.
