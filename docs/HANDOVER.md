## 0. 30초 요약 — 지금 당장 뭘 하면 되는가

**파일 하나만 열면 됩니다.**

```
engagement-growth/OFFLINE_ENGAGEMENT_FEATURES_BACKLOG_260823_2059.md
```

AI 에이전트(Claude Code 등)에 **새 대화창**을 열고 아래 한 줄을 그대로 붙여넣으면 작업이 시작됩니다:

> 이번 스레드에서는 `engagement-growth/OFFLINE_ENGAGEMENT_FEATURES_BACKLOG_260823_2059.md` 이 파일의 내용을 파악하여 '예정사항'의 첫번째 항목을 파악하여 수행 담당해야합니다. 먼저 항목을 이해하셨다면 진행중으로 변경하고 작업 착수하시고, 결과물을 사용자와 논의 후 사용자가 완료 승인을 하면 문서에 완료 업데이트하고 당신의 스레드 업무가 종료되었다고 명시해주시면 됩니다.

그게 전부입니다. 에이전트가 알아서 그 파일을 읽고, 연계된 스펙 절을 읽고, 맨 위 일감 하나를 집어 진행합니다.
아래 1~3장은 **"왜 이렇게 하는가"**와 **"이 트랙이 다 끝나면 뭘 하는가"**입니다.

## 1. 핵심 원리 — 맥락을 사람이 아니라 문서가 들고 있다

AI 대화 스레드는 매번 백지에서 시작합니다(cold start). 사람이 매번 구두로 배경을 설명하면
설명할 때마다 내용이 조금씩 달라지고, 특히 **"왜 그 방식으로는 안 했는가(버린 대안)"**가 유실돼
다음 스레드가 같은 헛발질을 반복합니다.

그래서 맥락 보존을 사람 기억이 아니라 **마크다운 문서 두 개**에 맡깁니다.

| 문서 | 담는 것 | 수명 |
| --- | --- | --- |
| **스펙** `*_KICKOFF_PLAN_*.md` / `*_SPEC_PLAN.md` | 왜(Why) · 무엇을(What) · 어떤 제약 하에 | **영구.** 각주는 지우지 않고 시간순으로 쌓는다 |
| **백로그** `*_BACKLOG_*.md` | 누가(어느 스레드) · 언제 · 어디까지 했나 | 트랙 단위. 끝나면 역할 종료 |

두 문서가 맞물리는 방식이 이 방법론의 전부입니다:

```
[스펙 4.2절]  ◄──── "참고: 4.2절" 포인터만 ────  [백로그 #13 일감]
     │                                                │
     │                                          [AI 스레드가 작업]
     │                                                │
[4.2절 아래 각주] ◄──── 선택한 방식 + 버린 대안 ────────┘
 "> 구현 결정(#13, 날짜): ..."
```

- **백로그는 스펙 내용을 복제하지 않습니다** — 절 번호만 가리킵니다. 그래야 스펙이 바뀌어도 두 벌로 갈라지지 않습니다.
- **AI가 내린 설계 판단과 기각한 대안은 스펙 각주로 역류시킵니다** — 이게 다음 스레드를 막아주는 방어벽입니다.

위 원칙은 **지금 이 저장소에서 그대로 돌아가고 있는 것**입니다. 같은 원칙을 코드베이스와 무관하게
일반화하고 빈 템플릿까지 붙여 둔 문서가 [`knowhow-docs/`](./knowhow-docs/)입니다 —
[`_SPEC_BACKLOG.md`](./knowhow-docs/_SPEC_BACKLOG.md)(방법론 가이드 + 백로그 템플릿) ·
[`_SPEC_PLAN.md`](./knowhow-docs/_SPEC_PLAN.md)(스펙 템플릿 + 각주 작성 공식).
**신규 프로덕트를 시작한다면 그쪽이 출발점**이고, 이 저장소를 이어받는 중이라면 이 문서가 출발점입니다.

## 2. 일감 하나가 도는 사이클

```
새 스레드 ──► 백로그 맨 위 1개 집기 ──► [진행중] 표시 ──► 스펙 해당 절대로 구현
                                                              │
   백로그 [완료] + 산출물 기록  ◄── 사람이 승인 ◄── 결과물 보고 ─┘
                │
                └──► 스펙에 "구현 결정" 각주 역류 ──► 커밋 (`feat(scope): ... (backlog #N)`)
```

**어겨서는 안 되는 3가지** — 나머지는 문서에 다 적혀 있습니다.

1. **AI는 예정사항 맨 위 1개만 집는다.** 번호(#N)는 커밋·각주와 엮인 불변 식별자라 재부여하지 않습니다.
   우선순위가 바뀌면 번호가 아니라 **줄 위치**를 옮깁니다 — 그래서 지금 순서는 `16 → 19 → 17 → 10 → 11 → 18`처럼 번호순이 아닙니다.
2. **완료는 사람이 승인한 뒤에만.** AI가 스스로 완료로 표시하지 않습니다. 이 게이트가 없으면
   문서가 "다 됐다"고 자기 주장하는 상태로 흘러갑니다.
3. **지정된 스펙 절 범위만.** AI 특유의 "이왕 하는 김에 리팩토링"을 금지합니다.

가격·콘텐츠·정책처럼 **AI가 대신 정하면 안 되는 것**은 항목에 `착수 전 확인(사용자):`로 미리 적어 둡니다.
스레드는 그 지점에서 반드시 사람에게 묻고 갑니다.

## 3. 트랙이 다 끝나면 — 다음 고도화를 여는 법 ★

**이게 이 방법론의 진짜 루프입니다.** 백로그의 예정사항이 비면 트랙 하나가 끝난 것이고,
다음 고도화 주제를 **같은 방식으로 문서부터 다시 시작**합니다.

1. 저장소 **루트**에 주제 폴더를 만듭니다 (예: `online-multiplay/`).
   → `docs/` 밖에 두는 게 맞습니다. 이유는 [4장 마지막 줄](#4-지금-살아있는-트랙) 참고.
2. 스펙 문서와 백로그 문서, **두 개를 만듭니다.** 형식은 둘 중 하나를 고릅니다:
   - **현행 형식 그대로** — 지금 `engagement-growth/`의 두 파일을 본떠 만듭니다. 이 저장소에서 검증된 방식이고 가장 안전합니다.
   - **[`knowhow-docs/`](./knowhow-docs/) 템플릿** — 더 체계화된 형식(구조화된 완료 필드, `검증 명령:` 헤더 등). 원래 신규 프로덕트를 겨냥해 정리한 것이라, 이 저장소에 쓸 땐 **안 쓰는 필드를 억지로 채우지 말고 빼세요**(예: 조직 이슈 트래커 연계 6장 — 여긴 해당 없음).

   어느 쪽이든 **1장의 원칙(절 번호 참조 · 각주 역류 · 3단 상태 구조)은 동일**합니다. 바뀌는 건 표기 형식뿐입니다.
3. **스펙을 먼저 채웁니다.** 사람과 AI가 대화하며 범위·제외범위·제약을 확정하는 단계입니다.
   여기서 "이번엔 안 하는 것(Non-Goals)"을 명시하는 게 나중에 오버엔지니어링을 막습니다.
4. 스펙을 **스레드 하나가 소화할 크기의 일감**으로 쪼개 백로그에 넣습니다.
   각 항목에 `AI 모델(Sonnet/Opus)`과 `노력정도(낮음~최대)`를 답니다.
5. 백로그 상단의 **고정 프롬프트 안 경로를 새 파일 경로로 갱신**합니다. (빠뜨리기 쉬움 — 이게 곧 진입점입니다)
6. **[`DOCS_INDEX.md`](./DOCS_INDEX.md)에 등록**하고, **이 문서 0장의 파일 경로도 새 트랙으로 바꿉니다.**
7. 완전히 종료된 트랙 폴더는 `docs/history/<YYYY-MM-DD>_<폴더명>/`으로 옮깁니다.
   단 **백로그에 미완료 항목이 남아 있으면 옮기지 않습니다.**

즉 **"주제 하나 = 폴더 하나 = 추적 파일 하나 = 완결까지"**가 원칙이고,
새 사람이든 새 AI 에이전트든 **그 파일 하나만 보면 현재 작업 지점이 복구**됩니다.

## 5. 빌드·검증 — 환경 함정 먼저

```bash
export JAVA_HOME=/Library/Java/JavaVirtualMachines/temurin-17.jdk/Contents/Home
```

- ⚠️ **JDK 17이어야 합니다.** 시스템 기본 java가 더 높은 버전이면 Gradle이 숫자만 뱉으며 즉시 실패합니다.
- ⚠️ `local.properties`는 gitignore라 **클론 직후엔 없습니다.** `sdk.dir=$HOME/Library/Android/sdk`를 직접 만들어야 합니다.

일감 하나를 끝냈을 때 도는 검증 루프:

```bash
./gradlew :shared:testDebugUnitTest :app-android:testDebugUnitTest
```

환경 점검과 실기기 설치는 Makefile 쪽이 편합니다:

```bash
make doctor
```

- `make test` (검증) · `make dev` (디버그 빌드) · `make install-dev` (설치) · `make seed-engine` (KataGo 모델 주입)
- ⚠️ KataGo 모델을 안 넣으면 앱이 **조용히 스텁 AI로 폴백**합니다(즉시 착수하는 가짜 AI). `make doctor`가 경고해 줍니다.
- iOS 타깃은 기본 꺼져 있고 `-PenableIosTargets=true`로만 켜집니다. **2026-08-24에 한 번 깨졌다가 복구됐습니다**
  (`docs/GO_AI_COACH_ARCHITECTURE_ROADMAP.md` "플랫폼 누수 회귀 복구" 참고 — 에러 49개, 원인은 `import java.` 검사를
  통과해버리는 `System.currentTimeMillis()`/`kotlin.synchronized`/`Dispatchers.IO`였습니다).
  ⚠️ **평소 안드로이드 빌드/테스트가 그린이어도 이 타깃은 조용히 깨질 수 있습니다** — 아무도 안 켜기 때문입니다.
  그래서 `shared/`를 건드린 일감은 아래 명령까지 돌리는 것이 백로그의 규칙입니다:
  ```bash
  ./gradlew :shared:compileKotlinIosSimulatorArm64 -PenableIosTargets=true
  ```

## 6. 새 AI 에이전트(회사 계정 포함)에 붙일 때

새 조직/계정의 에이전트로 갈아타도 **넘길 것은 두 줄뿐**입니다.

1. `docs/HANDOVER.md`(이 문서)를 먼저 읽으라고 알려줍니다.
2. 0장의 **고정 프롬프트**를 새 대화창에 붙여넣습니다.

에이전트가 바뀌어도 유지돼야 하는 것:

- 문서 언어는 **한국어**입니다(코드 주석·커밋 메시지는 영어).
- 커밋 메시지는 `feat(scope): 설명 (backlog #N)` 형태로 **일감 번호를 답니다.**
- 일감 하나가 승인되면 **바로 로컬 커밋**하고, 푸시는 유의미한 단위가 묶였을 때 일괄로 합니다.
- **완료 승인 없이 문서를 완료로 바꾸지 않습니다.**

⚠️ 한 백로그에 **스레드 두 개를 동시에 붙이지 마세요.** 순차 실행을 전제로 설계돼 있습니다.
(2026-08-24에 두 스레드가 겹쳐 같은 백로그 파일을 동시에 편집한 사례가 있습니다 — 결과는 무사했지만
한쪽 커밋이 다른 쪽 상태 표기를 쓸어담았습니다. 새 스레드는 시작 전에 `git status`로 워킹 트리를 확인하세요.)

⚠️ 백로그에 `[진행중]` 항목이 남아 있는데 아무도 작업 중이 아니라면, **직전 스레드가 중단된 것**입니다.
코드부터 쓰지 말고 `git status` / `git diff`로 어디까지 갔는지 먼저 진단하세요.

## 6.1. ⚠️ 문서가 알려주지 않는 것 — 미병합 브랜치
