# Architecture — 7계층 원칙

작성일: 2026-06-17
전면 재작성: 2026-07-30 — 특정 앱(go-ai-coach)의 파일/패키지 매핑을 이 문서에서 걷어내고, 재사용 가능한 레이어 원칙만 남겼다. go-ai-coach의 현재 구현 매핑·갭·고도화 로드맵은 [GO_AI_COACH_ARCHITECTURE_ROADMAP.md](./GO_AI_COACH_ARCHITECTURE_ROADMAP.md)를 따른다.
레이어 순서 확정: 2026-07-30 — External Integration을 "물리 엔진과 무관한 최상위 횡단 계층"(7번)이 아니라, **3계층(Extended API)과 같은 패턴을 외부 SDK에 적용한 대등한 서비스 계층**(4번)으로 재배치했다. 이유는 "왜 4계층인가" 절 참고.

**성격**: 이 문서는 **특정 앱에 종속되지 않는 원칙 문서**다. "무거운 연산 엔진(또는 외부 서비스)을 감싸 도메인 로직과 UI를 제공하는 앱"이라면 go-ai-coach가 아니어도 그대로 적용할 수 있도록, 구현 세부사항이 아니라 **레이어 경계를 정하는 논리와 그 논리를 지켜야 하는 이유**만 담는다. 새 앱을 시작할 때 이 문서를 그대로 복사해 오고, "물리 엔진"을 그 앱이 감싸는 무거운 자원(다른 게임 엔진, ML 추론 서버, 외부 하드웨어 등)으로 바꿔 읽으면 된다.

---

## 왜 7계층인가

OSI 네트워크 모델에서 착안했다. OSI가 "물리적 배선부터 사용자가 보는 화면까지"를 계층별로 분리해, 각 계층이 자신의 책임만 지키면 다른 계층이 무엇으로 바뀌든(구리선이 광케이블로, TCP가 QUIC로) 영향이 없도록 만든 것처럼, 이 아키텍처도 "실제 연산이 어디서 도는가"부터 "사용자가 무엇을 보는가"까지를 계층별로 분리한다.

핵심 동기는 하나다: **하위 계층(특히 1~2계층)이 물리적으로 분리되어도 — 로컬 프로세스에서 원격 서버로, 원격 서버에서 다른 사용자의 기기로 옮겨가도 — 상위 계층의 코드를 한 줄도 고치지 않아도 되어야 한다.** 이건 "나중에 원격으로 옮길 수도 있으니 인터페이스를 하나 둔다"는 흔한 조언보다 더 엄격한 요구다: 계층 경계는 네트워크 경계가 놓일 수 있는 자리에 그어야 하고, 그 경계를 넘는 계약은 처음부터 "로컬이든 원격이든 똑같이 동작해야 하는 계약"으로 설계해야 한다.

## 큰 그림

```
7. Presentation                (UI 렌더링, 입력 처리)
        ↓ (UI 이벤트)
6. Session & Continuity        (이 상태가 누구/어느 기기의 것인가, 연속성)
        ↓
5. Application / Domain        (도메인 규칙 + 유스케이스 오케스트레이션)
        ↓ (포트만 아는 조합)
4. External Integration        (외부 SDK의 raw 포트 + 안정화 서비스 — 3계층과 같은 패턴, 외부 대상)
        ↕ (3계층과 대등, 서로 모름)
3. Extended API (Service)      (엔진 raw 계약을 조합 — 캐시, 신뢰도, 동시성 lifecycle)
        ↓
2. Middleware / Bridge         (물리 엔진에 대한 1:1 원시 계약 + 전송)
        ↓
1. Physical Compute            (실제 연산이 도는 물리적 위치)
```

화살표는 "누가 누구를 알아도 되는가"다. **상위 계층은 하위 계층의 인터페이스(계약)만 알고, 하위 계층은 상위 계층을 전혀 모른다.** 3계층과 4계층만 예외적으로 **서로를 모르는 대등한 형제 계층**이다 — 둘 다 5계층에게 서비스를 제공하지만, 하나는 물리 엔진을, 하나는 외부 SDK를 대상으로 한다는 점만 다르다. 이유는 4계층 절에서 설명한다.

---

## 계층별 정의

### 1계층 — Physical Compute (물리 연산)

**책임**: 실제 연산이 일어나는 물리적 위치. 로컬 프로세스일 수도, 원격 서버일 수도, 참여형 네트워크의 다른 피어 기기일 수도 있다.

**경계 원칙**: 이 계층은 자신을 호출하는 쪽이 누구인지, 왜 이 연산이 필요한지 전혀 모른다. 입력을 받아 출력을 내는 것 외에 어떤 상태·정책도 갖지 않는 것이 이상적이다.

**설계 요구사항**: "어디서 도는가"가 바뀌어도(로컬↔원격↔피어) 2계층이 정의하는 계약만 지키면 이 계층 자체는 자유롭게 교체될 수 있어야 한다.

### 2계층 — Middleware / Bridge (미들웨어/브릿지)

**책임**: 1계층의 원시 기능을 **1:1 계약**으로 정의하고, 그 계약을 실제로 물리 자원에 도달시키는 **전송**을 책임진다. "계약을 정의하는 것"과 "그 계약을 로컬 stdio로 구현할지, 원격 RPC/HTTP로 구현할지"가 이 계층 안에서 함께 다뤄진다 — 계약은 하나, 구현체는 여러 개(로컬/원격/피어) 있을 수 있다는 뜻이다.

**경계 원칙**: 제품 정책(사용자 등급, 화면, 가격)을 전혀 모른다. "무엇을 할 수 있는가"만 정의하고 "언제 왜 하는가"는 모른다.

**핵심 설계 포인트**: 이 계약은 로컬 구현체와 원격 구현체가 **완전히 동일한 인터페이스**를 만족해야 한다. 그래야 3계층이 "지금 로컬인지 원격인지"를 몰라도 된다. 원격 구현체는 반드시 실패·타임아웃·재시도 정책을 이 계층 안에서 흡수해야 하며, 그 실패가 3계층 이상으로 새어나가는 방식(예외 타입, 상태)도 로컬 구현체와 동일해야 한다.

### 3계층 — Extended API (엔진 서비스)

**책임**: 2계층의 원시 계약을 유스케이스 단위로 조합한다. 캐시, 결과 신뢰도/품질 라우팅, 동시 호출 lifecycle(진행 중 호출 추적, 늦게 도착한 결과 폐기, busy 상태 관리) 같은 "여러 번의 원시 호출을 안정적인 하나의 서비스로 만드는" 책임을 진다.

**경계 원칙**: 2계층의 계약만 알고, 5계층 이상(화면·세션 개념)은 모른다. 4계층(External Integration)과도 서로 모른다 — 둘 다 5계층 아래에서 각자의 원시 자원(엔진 vs 외부 SDK)을 서비스로 조합할 뿐, 서로를 참조할 이유가 없다.

**물리 분산 환경에서의 역할**: 1계층이 여러 물리 자원(여러 서버, 여러 피어)으로 흩어질수록, "지금 어느 자원을 쓸지 선택하고 그 결과를 얼마나 신뢰할지 판단하는" 책임이 무거워진다. 이 계층이 그 판단을 흡수해야 상위 계층은 "물리 자원이 여러 개"라는 사실 자체를 몰라도 된다.

### 4계층 — External Integration (외부 연동, "Extended API + α")

**책임**: 이 앱의 핵심 도메인과 무관한 서드파티 연동 — 결제, 로그인 프로바이더, 광고 SDK, 클라우드 동기화, 푸시 알림 같은 것들을 **안정적인 서비스**로 제공한다.

**왜 3계층과 대등한 별개 계층인가**: 3계층이 하는 일 — "raw 계약을 안정적인 서비스로 조합" — 을 외부 SDK에 그대로 적용한 것이 4계층이다. 다른 점은 딱 하나: 엔진은 "어디서 도는가"(1계층)와 "어떻게 도달하는가"(2계층)가 따로 분리될 만큼 무겁지만, 외부 SDK(결제/로그인/광고)는 이미 네트워크 너머의 서비스라 별도 물리 계층이 필요 없다. 그래서 4계층은 **1~3계층이 하는 일(raw 포트 정의 + 그 포트를 안정적인 서비스로 조합)을 한 계층 안에 압축**해서 수행한다 — "Extended API + α"라는 이름은 이 압축을 가리킨다.

- **α(raw 포트, 2계층에 해당)**: 플랫폼 SDK를 import하지 않는 순수 인터페이스. 도메인 패키지 쪽(5~6계층과 같은 위치)에 둔다.
- **Extended API 본체(안정화 서비스, 3계층에 해당)**: 그 포트를 실패/재시도/캐시까지 감안해 상위가 믿고 쓸 수 있는 서비스로 감싼다. 이 부분을 실제 SDK에 연결하는 구현체(어댑터)는 플랫폼 계층(UI/persistence 쪽) 파일에 둔다.

**경계 원칙**: 5계층 이상을 모른다. 3계층과도 서로 모른다(위 참고) — 이 둘은 "같은 패턴, 다른 대상"이라는 점에서만 형제일 뿐, 서로에게 의존하지 않는다.

**선택적 계층**: 이 계층은 **없어도 된다.** 결제·로그인·광고 같은 외부 연동이 필요 없는 앱이라면 4계층은 통째로 비워도 나머지 6개 계층은 그대로 유효하다.

### 5계층 — Application / Domain (어플리케이션/도메인)

**책임**: 이 앱이 존재하는 이유인 순수 도메인 규칙(플랫폼·UI에 의존하지 않는 규칙)과, 그 규칙을 실제 사용 흐름으로 엮는 유스케이스 오케스트레이션(시작/재개/되돌리기/저장 같은 앱 서비스 흐름)을 함께 담는다. 도메인 규칙과 오케스트레이션은 성격이 다르지만(전자는 순수 함수, 후자는 흐름 조합) 둘 다 "이 앱만의 것"이라는 공통점으로 하나의 계층으로 묶는다 — 별도 앱으로 옮기면 그대로 재사용 가능한 게 도메인 규칙이고, 그 규칙을 이 특정 제품의 흐름으로 엮는 게 오케스트레이션이다.

**경계 원칙**: 3계층과 4계층의 포트만 알고(둘 다 이 계층에게는 "서비스 제공자"로 동등하다), 6계층 이상(누구의 세션인지, 화면에 어떻게 보이는지)은 모른다.

### 6계층 — Session & Continuity (세션/연속성)

**책임**: "지금 이 상태가 누구의 것이고, 어느 기기의 것인가"를 관장한다. 로그인 상태, 기기 간 이어가기, 유료 상태처럼 시간적으로 유지되어야 하는 정체성/연속성이 여기 속한다.

**경계 원칙**: 5계층의 도메인 개념(무엇을 하는 앱인지)과 4계층(외부 연동 — 로그인 상태 확인, 결제 상태 확인 등)을 참조할 수 있지만, 7계층의 화면 표현은 모른다. 5계층과 자주 혼동되기 쉬운데, 구분 기준은 **"이 값이 도메인 로직의 세대(generation) 개념과 같은 카운터를 재사용하고 있는가"**를 항상 의심하는 것이다 — 도메인 상태 무효화 주기(예: 되돌리기마다 증가)와 세션/정체성의 유효 주기(예: 새 매치가 시작될 때만 증가)는 서로 다른 카운터여야 한다. 같은 카운터를 재사용하면 한쪽의 정상 동작이 다른 쪽을 오작동시킨다.

**4계층과의 관계**: 이 계층은 4계층(External Integration) 없이도 최소한의 역할(로컬 기본값 기준의 세션/연속성)을 할 수 있어야 한다. 4계층은 "있으면 더 풍부해지는" 의존성이지 필수 전제가 아니다 — 예: 로그인 연동이 없어도 "이 기기의 로컬 세션"이라는 개념 자체는 성립해야 한다.

### 7계층 — Presentation (프레젠테이션)

**책임**: 실제 화면 렌더링, 사용자 입력 처리. 스킨/테마/커스텀 UX가 이 계층 안에서 자유롭게 바뀔 수 있어야 한다.

**경계 원칙**: 도메인 로직이나 비동기 호출 순서를 전혀 모른다. 6계층이 노출하는 상태를 구독하고, 이벤트를 6계층 이하로 올려보내는 것이 전부다. 항상 최상위 계층이다 — 사용자가 실제로 보고 겪는 결과이므로, 이 자리를 다른 계층과 공유하거나 내주지 않는다.

## 4계층 압축

OSI의 7계층이 실무에서 TCP/IP의 4계층(링크/인터넷/전송/응용)으로 압축되어 설명되는 것처럼, 이 7계층도 아래 4개 핵심 계층으로 압축해 설명할 수 있다. **이 4개가 진짜 핵심 단위이고, 7계층은 그 안을 필요할 때 더 정밀하게 나눈 것**이라고 이해하는 것이 맞다 — 7계층을 먼저 정하고 압축한 게 아니라, 4계층이 본질이고 7계층은 그 세부 분해다.

| 압축 계층 | 포함 | 한 줄 요약 |
| --- | --- | --- |
| **Infra** | 1(Physical Compute) + 2(Middleware/Bridge) | 연산이 물리적으로 어디서, 어떻게 안정적으로 도달하는가 |
| **Service** | 3(Extended API) + 4(External Integration) | raw 자원(엔진이든 외부 SDK든)을 안정적인 서비스로 조합 — 대상만 다를 뿐 같은 패턴 |
| **Domain** | 5(Application) + 6(Session & Continuity) | 이 앱의 규칙과, 그 규칙이 누구의 것인가 |
| **Experience** | 7(Presentation) | 사용자가 보고 겪는 결과 |

3계층과 4계층이 압축 시 하나로 묶이는 이유는 우연이 아니다 — 애초에 "같은 종류의 일(raw 자원을 안정화된 서비스로 조합)을 다른 대상에 적용한 것"이기 때문에, 세부 구현을 따질 때만 둘로 나누고 큰 그림에서는 하나로 본다.

새 팀원에게 아키텍처를 설명할 때는 이 4단계로 시작하고, 실제 파일을 어디에 둘지 판단할 때는 7계층으로 내려가서 결정한다.

## 새 앱에 적용하는 법 (체크리스트)

1. **1계층을 먼저 특정한다**: 이 앱이 감싸는 "무거운 자원"이 무엇인가(외부 엔진, 추론 서버, 하드웨어 SDK)? 그것이 로컬에서만 도는가, 언젠가 원격/분산으로 옮겨갈 수 있는가?
2. **2계층 계약을 "로컬이 아니라 원격을 먼저 가정하고" 설계한다**: 지금 당장 로컬 구현체 하나뿐이어도, 인터페이스 시그니처에 실패·타임아웃이 자연스럽게 들어갈 자리를 만들어 둔다.
3. **3계층이 필요한지 판단한다**: 2계층 호출이 단 한 번으로 끝나고 캐시/신뢰도 판단이 필요 없다면 3계층은 얇아도 된다. 하지만 "생략"하지는 않는다 — 나중에 필요해지면 5계층 코드에 캐시 로직이 새어 들어가 있을 가능성이 높다.
4. **4계층 후보를 미리 목록화한다**: 결제/로그인/광고/알림/동기화 중 이 제품에 필요한 것을 먼저 나열한다. 착수 순서와 무관하게, 각 연동마다 "raw 포트(α)"와 "안정화 서비스(Extended API 본체)"를 나눠서 배치하는 규칙을 처음부터 지킨다 — 나중에 몰아서 분리하는 것보다 훨씬 싸다. 이 앱에 결제/로그인이 전혀 없다면 4계층은 그냥 비워 둔다.
5. **5계층과 6계층을 헷갈리지 않는다**: "이 규칙이 이 앱이라면 항상 참인가"(5계층) vs "이 값이 지금 로그인한 사용자·기기에 따라 달라지는가"(6계층)로 구분한다.
6. **경계를 코드로 강제한다**: 계층 경계 규칙을 문서로만 남기지 말고, 정적 분석/린트/아키텍처 테스트로 "N계층 패키지가 M계층을 import하면 실패"하게 만든다. 문서는 의도를 설명하고, 테스트는 그 의도가 깨지지 않았음을 보장한다.
