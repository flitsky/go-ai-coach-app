# 기능 유/무료 제공 원칙

작성일: 2026-08-13

본 문서는 **go-ai-coach** 앱의 기능을 "무료로 줄지, 프리미엄으로 잠글지, 어떻게 활성화 상태를 저장/복원할지" 결정할 때 참고하는 **원칙 문서**입니다. `premium-mode/README.md`(수익화 단계별 구현 로그)와 `auth-onboarding/README.md`(계정/로그인 구현 로그)가 "무엇을 어떻게 만들었는가"를 기록하는 실행 문서라면, 이 문서는 그 위에서 "왜 그렇게 하기로 했는가"를 담는 상위 원칙 문서입니다. 두 실행 문서와 마찬가지로 계속 갱신되는 히스토리 문서로 유지하고, 맨 아래 "결정사항"에 날짜별로 쌓습니다.

---

## 1. 앱 핵심 철학

- 로그인 없이 빠르고 간결하게 플레이 경험을 쌓게 한다.
- 유료 결제의 경우, 이번 출시 UI에는 없으나<sup>1</sup> 나중에 노출하더라도 플레이스토어(애플 추가 런칭 시엔 앱스토어 포함)에서 사용자가 스토어 계정 기반으로 구매한 이력이 앱과 연동되게 해준다.
  - 이 방법은 사용자 계정 정보를 몰라도, 스토어에 현재 로그인한 사용자의 구매 이력을 가져오는 방식으로 앱 자체 로그인 인증 없이 연동이 가능하다. **→ 맞는 이해입니다.** Google Play Billing 구매는 앱 로그인과 무관하게 기기의 Play 계정에 귀속되고, 앱 시작 시 `queryPurchases()`로 자동 복원됩니다. 2026-08-09에 완전 게스트(비로그인) 상태에서 재설치 후 자동 복원까지 실기 검증까지 끝났습니다(`auth-onboarding/README.md` 1.2절·142절).
- 사용자가 앱 내 활동 등으로 얻은 기능들
  - 기본적으로 로그인 없는 경험이 우선되므로, 앱 내 저장소(기기 로컬)에 기능 활성화가 저장된다.
    - 앱 삭제/재설치 시 초기화될 수 있음을 사용자에게 고지한다.
    - 나중에 구글/애플 로그인 등을 연동하면, 그때는 파이어베이스(또는 각 플랫폼 계정)에 저장해주도록 한다.
- 파이어베이스/OS 연동(추후, 천천히 결정되어 진행될 사안)
  - 쾌적한 플레이 경험을 먼저 제시하고, 사용자들이 자신의 데이터를 저장하고 싶어할 때쯤 로그인 연동 기능을 제공한다.

<sup>1</sup> 정확히는 "아직 안 만듦"이 아니라 **이미 만들어서 검증까지 끝냈지만 이번 출시에서 꺼둔 상태**입니다. Google Play Billing 9.1.0 연동, 상품 `premium_lifetime` 등록, 구매·복원 실기 검증까지 전부 완료됐고(`premium-mode/README.md` 8장 마일스톤), `ui/FeatureFlags.kt`의 `isPurchaseEnabled = false` 하나로 구매 버튼과 복원 조회만 꺼둔 상태입니다. 다시 켜는 비용은 "빌드"가 아니라 "플래그 하나 + 필요하면 새 SKU 등록" 수준입니다.

## 2. 기능 구현 레이어 원칙

기능은 다음 3단으로 일관되게 정리한다 — 이미 코드 구조가 이 모양입니다. 새로 만들 것은 2번째 레이어를 **단일 플래그 → 기능별 원장**으로 넓히는 것뿐입니다.

| 레이어 | 역할 | 현재 코드 위치 |
| --- | --- | --- |
| 기능 구현 최상위 집합 레이어 | 엔진 코어~미들웨어까지 고도화된 기능을 일관되게 노출 | `application/*`(topmoves, movereview, score 등), `shared`/`engine-android` |
| 기능 활성화 관리 도메인 | 기능별 무료/프리미엄 여부, 활성화 소스(광고/구매/프로모션) 판정 | `application/premium/PremiumState.kt`(현재 단일 플래그) |
| 프레젠테이션 레이어 | UX로 노출, 유저 상태에 따라 업셀/광고/구매 플로우 전개 | `ui/GamePlaySection.kt`, `ui/PremiumUiState.kt`, `ui/PremiumUpsellDialog` |

## 3. 플랫폼 확장 원칙

- **Google Play 우선 출시 → Apple App Store는 후순위.**
- Apple을 나중에 추가하더라도 **유저플로우 복잡도를 늘리지 않는다** — 즉 "Google은 A방식, Apple은 B방식이라 사용자가 겪는 화면/단계 수가 달라진다"는 결과를 피한다. 플랫폼별 내부 구현(Play Billing vs StoreKit)은 달라도 되지만, 사용자에게 보이는 팝업/문구/단계 구조는 동일한 틀을 재사용한다.
- 이 원칙은 `premium-mode/README.md`(결정사항 #6)·`auth-onboarding/README.md`(Step 1 재개정 Apple 버튼 선추가)에 이미 적용 중 — 상태 모델/게이팅 로직을 플랫폼 비종속으로 설계하고, 플랫폼 종속 부분만 어댑터로 분리.

## 4. 인사이트 — 서버 없이 "구글 업적"/"애플 유사 기능"으로 기능 활성화 관리가 가능한가

**결론부터: 업적(Achievements) 자체는 부적합하고, 대신 같은 SDK 안에 있는 "클라우드 저장" 기능이 진짜 후보입니다.**

- **업적/리더보드(Google Play Games 업적, Apple Game Center 업적)**: 게임화 표시용이라 부적합합니다. 다른 플레이어에게 공개되는 값이고, "해제됨/진행도" 외의 구조화된 데이터(예: 어떤 기능을 언제 얻었는지)를 담을 수 없습니다. 업적 해제 여부를 프리미엄 게이팅의 실제 판정 소스로 쓰는 건 원래 용도를 벗어난 편법이라 권장하지 않습니다.
- **진짜 후보 — Play Games Services의 Saved Games(Snapshots) / Apple의 iCloud Key-Value·CloudKit**: 둘 다 "자체 서버 없이, 플레이어의 스토어 계정에 묶인 작은 데이터를 클라우드에 저장"하는 OS/스토어 네이티브 기능입니다. 여기에 `{"unlockedFeatures": ["undo"], "promoClaimed": true}` 같은 작은 JSON을 저장하면, **로그인 화면을 새로 띄우지 않고도**(기기에 이미 로그인된 Play 계정/Apple ID를 그대로 재사용) 재설치 후에도 복원되는 엔타이틀먼트 저장소를 만들 수 있습니다. Play Billing 구매가 "로그인 없이 스토어 계정 기준으로 복원"되는 것과 원리가 같습니다 — 다만 대상이 "구매 내역"이 아니라 "임의의 작은 저장 데이터"로 넓어지는 것.
- **왜 지금 당장 하지 않는가**: (1) Play Games Services SDK 연동 + Play Console 설정이 새로 필요하고, Apple 쪽(iCloud)도 별도 구현이 필요해 "서버 안 만든다"는 목표는 지키면서도 실제 통합 비용은 결코 작지 않습니다. (2) Play Games 자동 로그인이 대부분 무마찰이긴 하나 100% 보장되지는 않아(사용자가 Play Games를 꺼뒀을 수 있음), 로컬 저장 폴백은 어차피 필요합니다 — 즉 이걸 먼저 만든다고 "로컬 저장+재설치 초기화 고지" 자체가 없어지진 않습니다. (3) 지금 핵심 철학(1장)이 "로그인 없이 간결하게"인데, 이 통합이 주는 이득(재설치해도 프로모션 획득 기능 유지)은 아직 실제 사용자 불만으로 확인된 적이 없습니다.
- **제안**: 지금은 착수하지 않고, "로컬 저장이라 재설치하면 프로모션으로 얻은 기능이 사라진다"는 게 실제 사용자 문의/불만으로 나타나면 그때 스파이크(spike)로 검증 후 도입을 재논의합니다. (세부 API 스펙은 이 문서 작성 시점에 깊게 검증하지 않았습니다 — 실제 착수 시 공식 문서로 재확인 필요.)

## 5. 파이어베이스로 데이터 구조화하는 방안 — 장단점

이미 프로젝트에 Firebase가 붙어 있으므로(Auth 인프라 존재, `docs/baas_solutions_comparison.md`에서 채택 근거 조사 완료) 기술적으로는 어렵지 않습니다. 다만 **아래 장단점의 핵심은 "어떻게 구조화하나"가 아니라 "로그인 정책과 묶여 있다"는 점**입니다.

**장점**
- 새 BaaS 도입 불필요 — Auth 인프라가 이미 있고, `application/auth/AuthState.kt` 설계 원칙(플랫폼 비종속)을 그대로 따르면 됨.
- 실계정(Google/이메일) 로그인 사용자에 한해 진짜 서버측 영구 엔타이틀먼트 확보 가능 — 기기 로컬 저장의 "재설치 시 초기화" 한계를 정면으로 해결.
- 데이터 구조 자체는 단순함 — `users/{uid}/entitlements/{featureId}` 같은 문서 하나면 충분하고, `premium-mode/README.md` Step 4 설계에 이미 이 방향이 언급돼 있음.

**단점 — 말씀하신 대로 지금 정책과 정면으로 상충함**
- **로그인 기능 자체가 지금 꺼져 있습니다**(`FeatureFlags.isLoginEnabled = false`, 2026-08-09 결정). Firestore에 뭔가를 저장하려면 실계정이 있어야 하는데, 지금 정책상 대부분의 사용자는 게스트로 남습니다 — 구조를 아무리 잘 설계해도 적용될 사용자가 거의 없습니다.
- **익명 로그인은 영구 폐기됐습니다**(2026-08-05 확정) — 이전 앱(장기)에서 재설치마다 허수 익명 계정이 쌓이는 문제를 실제로 겪었기 때문입니다. 즉 "로그인 없이도 Firestore에 안전하게 쓴다"는 중간 옵션 자체가 이 프로젝트에서는 없습니다 — 쓰려면 반드시 실계정이어야 합니다. 말씀하신 "익명 로그인해서 기능 활성화한 게 재설치 시 초기화되는 문제"는 정확히 이 이유로 이미 한 번 겪고 폐기된 경로입니다.
- 로그인을 다시 켜면, 2026-08-09에 껐던 이유(Google Play Data Safety 공개 의무, 앱 내 계정 삭제 기능 유지보수 의무)가 그대로 되살아납니다 — Firestore 구조화 자체보다 "로그인을 다시 켠다"는 선행 결정의 비용이 훨씬 큽니다.

**결론**: Firestore 데이터 구조화는 기술 문제가 아니라 **로그인을 다시 켤지 말지**에 종속된 문제입니다. 지금은 "로컬 저장 + 재설치 시 초기화 고지"로 충분하고, 로그인을 다시 켤 실질적 이유(사용자가 데이터를 잃기 싫어하는 신호)가 쌓이면 그때 로그인과 Firestore 저장을 함께 켜는 게 순서상 맞습니다 — 1장에서 이미 그렇게 쓰신 그대로입니다.

## 7. 결정사항

### 이미 다른 문서에서 확정된 사항 (이 문서는 인용만 함)
- Play Billing 구매는 앱 로그인과 무관하게 기기 Play 계정 기준으로 복원된다. (`auth-onboarding/README.md` 1.2절, 2026-08-09 실기 검증)
- Firebase 익명 로그인은 이 프로젝트에서 다시 켜지 않는다 — 재설치마다 허수 계정이 쌓이는 문제를 이전 앱에서 실제로 겪음. (`auth-onboarding/README.md`, 2026-08-05)
- 로그인 기능 전체를 이번 출시에서 끈다(`isLoginEnabled=false`) — 코드/인프라는 유지, 플래그로만 제어. (`auth-onboarding/README.md`, 2026-08-09)
- 구매 기능(영구 프리미엄) UI도 이번 출시에서 끈다(`isPurchaseEnabled=false`) — 인프라·검증은 완료 상태. (`premium-mode/README.md`, 2026-08-09)

### 이 문서에서 새로 제안 — 확인 필요
- 3장: Google 우선, Apple 후순위, 유저플로우 복잡도 비대칭 금지.
- 4장: Play Games Snapshots/iCloud 기반 서버리스 엔타이틀먼트 저장은 **지금 착수하지 않고 보류** — 로컬 저장 재설치 초기화가 실제 불만으로 확인되면 재논의.
- 5장/6장: Firestore 데이터 구조화는 로그인 재활성화와 **함께** 진행 — 로그인 없이 먼저 만들지 않는다.
- 6장 표의 "앱 내 활동/프로모션으로 얻은 영구 기능 = 기기 로컬 저장 + 재설치 시 초기화 고지" 원칙.
- (참고) 무르기는 이번 세션 초반에 무료로 전환했습니다. 유료 활성화(프로모션 경유 무료 전환) 방향으로 되돌릴지는 이 원칙 문서 확정 후 `premium-mode/README.md`에 별도 Step으로 기록하며 최종 확인 부탁드립니다.
